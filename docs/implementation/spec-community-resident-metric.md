# 看板社区人数、居民与会员权益住宿口径

状态：2026-10-22 用户已修正退房日与会员统计规则，更新 PR #105 中；尚未合并发布。以下规则替代此前“会员本人身份绑定后才计数”及“今日待退仍计社区人数”的看板统计方案。

## 已确认口径

- **总在住人数**是当日有效住宿区间内的住客，包含短住、长住、使用会员权益、免费与付费住客。
- 当前和历史均使用 `[arrival, departure)`：入住日计入，退房日期当天不计入；即使尚未办理退房，也不因旧的 CHECKED_IN 状态把退房日或逾期日期算入社区人数。未来预订不计实际住宿。
- 已完成续住或换房按有效住宿安排计算，换房当天只由新房间区间贡献，无空夜续住连续累计，有空夜重新开始。
- **当日居民数**是总在住人数中，连续已住满7晚的人与当日使用会员权益的住宿统计份额的并集。
- **在住会员**按当日实际使用会员权益的有效住宿统计，每笔订单每日最多计1人。无需确认实际住客是否会员本人，也不因缺证件、昵称差异、会员资料更正要求本人身份核对。
- 每笔订单每日最多1份，多个订单登记仍按同一住客的既有人数口径去重。一笔订单多人入住，只给唯一主要住客登记一个会员权益统计份额，用于名单展示和与长住人数去重；这不认定主要住客就是会员本人，同行人不自动都算会员。
- 同会员权益可用于不同住宿，会员ID只表示权益来源，不能据此把不同住客合成一个人或拼接长住。实际住客继续使用现有登记与昵称姓名近似去重口径；长住与会员份额重叠只计一次。
- 普通付费住宿即使能找到会员档案，也不因档案身份单独计入“在住会员”；此指标采用会员权益住宿口径。
- 追加住客没有独立实际入住日期时不继承订单起始日。缺少实际名单、主要住客唯一性、有效住宿安排或权益事实时，保留具体资料缺项，不制造人数或入住日期。

## 权益使用依据

- 按统计日读取 `coverage_items` 与 `entitlement_ledger`：已经实际核销的 `CONSUME` / `CONVERSION_CONSUME` 扣除 `RESTORE` 后，才构成权益使用。`HELD` 只是预留，已经释放或返还的份额不计。
- 一笔订单同一服务日最多贡献1份，不因换房、重复查询或多条账本记录重复计数。核对订单、会员、合同、权益批次与服务日的业务关联，保留确有冲突的缺项。
- 兼容受控历史转会员产生的无 coverage 核销事实，核对成功命令及对应会员业务链；不再读取或推断本人身份快照。
- 已确认转换追溯覆盖的服务日可早于合同建立/生效日，按真实已核销服务日统计。今天会员过期不抹掉历史权益使用；已返还、作废和更正按实际存储事实处理。
- 本次只改看板读取与统计，不新增会员本人绑定、不修改权益使用权限、订单生命周期、房态可用性、财务事实或退房办理规则。

## 展示与助手知识

- 保留当前名单的住客昵称（与昵称不同则并列姓名）、本房间住期、会员权益来源与短原因，说明统一用图标悬浮。
- 确认依据显示“使用会员权益”，不再出现“本人在住转会员”“证件身份一致”或“未记录本人入住关系”。真正缺项说明是住宿或权益依据缺项，不标成身份审核。
- 不新增“在住 · 今日待退”标签；退房日住宿直接不在当天社区名单中展示。房态仍负责实际退房办理。
- 当前名单不随历史筛选改变；历史曲线与逐日数据使用同一日期/权益口径。API不返回证件、电话或内部人员匹配键。
- 员工助手 `dashboard` 知识随本次版本同步；指标与知识修订为 `2026-10-22.2`。

## 最低验收

1. 给定10月20日入住、22日退房且仍为CHECKED_IN，20/21日计入，22日及之后不计当前社区人数、居民、会员与当前住宿时长。
2. 给定22日已完成续住或换房，覆盖22日的新区间仍计入；同人旧区间截止22日不重复计数，无空夜链继续累计。
3. 给定有效权益住宿且住客与会员的证件/昵称/姓名不同或没有证件，每日仍按1份计会员；不要求核对本人。
4. 给定多人权益住宿，会员只计1份，同行人分别按其实际连续时长判断长住；同一主要住客既长住又使用权益，居民不重复加人。
5. 给定同一会员权益用于不同实际住客的两笔住宿，不能按会员ID合并总人数或串接连续天数。
6. 给定仅预留、已释放/返还、取消或未来预订，不能作为当天会员权益在住；成功历史转换的净核销服务日可追溯展示。
7. 给定实际名单或日期不明，保留已知部分和具体缺项；不能因为权益已使用就假造住客名单或历史到店日期。
8. 类型、回归、实际API序列化、生产数据只读对照及桌面/窄屏预览通过；自动检查与生产发布/用户反馈分别记录。
