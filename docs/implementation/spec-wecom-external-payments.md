# 企业微信收退款同步与订单匹配

日期：2026-09-10。状态：PMS 本地实现与相关自动验证完成，已读取真实企业微信流水建立独立本地体验；生产同步、智能体消费和人工验收仍待进行，未部署。

## 已确认目标

企业微信继续保存原始收退款流水。PMS 每 60 秒统一同步必要字段，工作人员和智能体查询 PMS 中的流水；无新增流水时不调用模型。用可搜索的选择器替换企业微信交易编号输入框，推荐最多 3–5 笔，昵称、金额和时间为主要识别信息，编号仅供参考。找不到时打开完整清单；不新增刷新按钮。

每笔企业微信退款必须保存独立退款单号，并关联同一订单的原收款。选取只形成暂选，最终确认成功才匹配；取消不占用流水，并发确认只能有一笔成功。

## 资金与历史规则

- 同步外部流水不产生订单收退款事实；订单事实与匹配关联在同一事务提交，遵循既有 Preview / Confirm、授权、审计和幂等协议。
- 收款以企业、商户号和交易单号识别；退款以企业、商户号和独立退款单号识别，并保留对应原收款的商户单号。金额始终使用整数分。
- 一次选择对应一笔完整外部流水；实际金额不得被订单应收金额覆盖。退款只使用已确认成功的单笔退款金额，不使用原收款金额或累计退款金额代替。
- 已匹配流水不进入推荐或可选候选，完整清单可显示匹配状态和授权范围内的订单关联；同一来源不得重复计入住宿和会员收款。
- 已有手工记录核对成功后只补关联，不新增资金事实；歧义记录不自动认定。历史未登记且不再纳入新系统的流水归为“历史不纳入”，不计待处理，不触发智能体提醒。
- 用户确认历史边界为北京时间 `2026-09-01 00:00:00`（`2026-08-31T16:00:00Z`）。此前未登记流水默认历史不纳入，此后纳入匹配；首次导入作为基线不批量提醒。旧收款的新退款独立按退款事件判断；原收款完全不存在于 PMS 的跨系统退款不自动补造旧收款。
- 原有退款记录不重写、不伪造退款单号。新增退款必须有退款编号；原收款关联、同订单限制、可退余额和退款后净额转会员规则继续有效。
- 独立退款号使用 `refundReference` / `refund_reference`，不把原有企微退款的 `transaction_reference = null` 重新解释为另一种资金语义；原收款凭据继续通过 `references_fact_id` 追溯。
- 昵称用于人工识别及推荐，不单凭同昵称建立身份绑定。

## 同步与查询

- 使用自建应用的 access_token，按 expires_in 缓存；密钥仅通过后端配置注入，不进入前端、业务记录或日志。
- 使用 get_bill_list 按有限时间窗口查询；窗口不超过一个月，翻页至 next_cursor 缺失。next_cursor 仅为当次查询的分页位置，不当作跨轮永久增量游标。
- 日常窗口重叠查询以发现迟到记录；同步成功后推进检查点。失败保留原检查点并退避，补查停机期间的窗口；另覆盖更早记录的退款状态更新。
- 同一数据源的同步串行执行，页面数量不增加对企业微信的轮询次数。重复记录更新而不重复产生发现事件，基线历史导入不产生实时提醒。
- 昵称优先由官方 externalcontact/get 补充并缓存；QiWe 联系人及 external_userid 映射作为可配置补充，其应用上下文和实际昵称覆盖必须联调验证。解析失败时保存流水并明确显示昵称未取得。
- 查询 API 只读 PMS 数据库；支持收款/退款、日期、昵称、金额和处理状态筛选。返回同步状态与时间，不增加手动刷新动作。
- 按用户最新决定，界面的处理状态下拉仅列出“待匹配 / 全部 / 已匹配”，不再单列“历史不纳入”选项；历史流水仍可在“全部”中查看，历史纳入及不可匹配规则保持不变。
- 选择器自动刷新候选，保留暂选；后台重新校验已被他人匹配、退款状态变化或权限变化。

## 接入与范围

- 首先实现 PMS 同步、保存、查询、推荐和匹配。继续复用现有数据库、命令事务和事件投递基础，不额外引入缓存或消息队列产品。
- 启用同步需要明确企业、商户、物业映射及历史分界时间；未配置时不调用真实外部服务。生产凭证、真实数据迁移和部署不由本地实现自动执行。
- 为智能体提供查询及确认后登记能力；收退款发现事件与现有人员/住宿事件协议的扩展需保持双方一致。群路由、工作人员消息身份及确认消费属于后续智能体接入，不把现有 READ 凭证自动升级为财务写权限。
- 后台使用单独的 `qintopia_payment_worker` 数据库账号，只能更新外部流水、联系人及同步进度；资金事实仍由 `qintopia_runtime` 的既有命令事务写入。已匹配来源即使后续冲销，仍保留原始关联，不自动重新放入待选。
- 普通对外收款尚无已确认覆盖现有方式的通用支付回调。首版使用轮询；不改收款方式为小程序，不以 QiWe 普通消息直接证明付款成功。

## 最低验证与人工验收

1. 首次同步、多页、重复及迟到记录、失败恢复、退款状态更新、昵称不可用均有自动验证；单个同步器不会因多个页面重复启动。
2. 同步不改变订单资金；选择确认后才新增对应事实；取消、并发重复、金额篡改、跨物业、跨订单退款、无权限、陈旧 Preview 均不产生错误或部分写入。
3. 历史已有记录只关联一次；历史不纳入不进入推荐和发现提醒；住宿与会员不能重复使用同一流水。
4. 退款号保存并可追溯到订单及原收款；同一收款多次退款各自独立；既有退款后净额升级会员仍符合守恒。
5. UI 推荐不超过 5 笔，完整清单能搜索和查看状态；主字段为昵称、金额、时间；无刷新按钮，自动更新不清空暂选。
6. 自动检查后按主验收计划提交收款、退款、历史与并发三个检查点；真实接口延迟、机器增量负载和昵称覆盖单独标记联调结果。

## 接入配置与运行

迁移 `059` / `060` 只建字段、表及权限，不导入真实流水、不启用来源。维护人员在目标环境备份并执行正常迁移后，配置 `external_payment_sources` 的企业 ID，以及 `external_payment_accounts` 的商户号与 PMS 物业 ID 映射。企业同一商户不能映射到多个物业。`matching_since` 固定本次已确认的北京时间 2026-09-01 零点；`import_since` 是实际复查历史范围的起点，应覆盖需要核对的已有手录单号，不能晚于 `matching_since`。超出此起点的旧收款及退款要扩大历史查询范围后才可能核实，不能凭聊天记录证明到账。

配置示意（实际 ID、历史查询起点须从目标环境确定，不直接执行示意值）：

```sql
BEGIN;
INSERT INTO external_payment_sources(id, corp_id, matching_since, import_since, enabled)
VALUES ('source_qintopia', '<CorpID>', '2026-09-01 00:00:00+08', '<历史复查起点>', true);
INSERT INTO external_payment_accounts(source_id, merchant_id, property_id)
VALUES ('source_qintopia', '<微信支付商户号>', '<PMS物业ID>');
COMMIT;
```

为 `qintopia_payment_worker` 设置独立数据库密码，通过服务器密钥配置注入 `PMS_WECOM_WORKER_DATABASE_URL`。另外配置 `PMS_WECOM_SOURCE_ID`、`PMS_WECOM_CORP_ID`、`PMS_WECOM_APP_SECRET`、`PMS_WECOM_SYNC_ENABLED=true`，以现有进程管理器单独运行 `npm run wecom:worker`。不把数据库维护账号交给 worker。允许重复启动的进程通过 source advisory lock 防止同时同步；正常只需一个进程、最多两个数据库连接。密钥不写入应用表或前端。

每轮最多补查 7 个日窗口；正常近期轮询采用 10 分钟重叠窗口，另每轮复查一个历史日窗口，优先补查已知原单但退款明细未完整的记录。分页按 `next_cursor` 完成，失败窗口不推进，失败间隔从 2 分钟逐步退避到 15 分钟。若每个窗口只有一页，稳定运行通常约 120 次流水请求/小时，有待核实退款时可增至约 180 次/小时；首次补齐和分页另外计入。联系人最多每轮查询 20 个，缓存 24 小时，失败也缓存尝试时间。实际延迟与频率要真实联调测量，不能把 60 秒调度周期承诺为到账时限；旧原单退款可能要等历史复查。

UI 每 15 秒自动读取 PMS，时间戳用于识别同步延迟，无手动刷新入口。读取故障时保留暂选并自动重试；最终仍以服务端确认结果为准。

## PMS 与未来智能体的接口

- `GET /api/v1/external-payments?propertyId=...&kind=COLLECTION&recommended=true&amountMinor=...`：推荐最多 5 笔；退款用 `kind=REFUND` 和 `originalCollectionFactId`。省略推荐参数可按 `query`、`begin/end`、`amountMinor`、`status` 和 `beforeId` 查询完整清单。
- `GET /api/v1/external-payment-events?propertyId=...&cursor=0`：独立的 `pms.payments.v1` 持久事件，`DISCOVERED` / `MATCHED`，客户端将 `nextCursor` 作为不透明十进制字符串保存，成功处理后推进，按 `eventId` 去重。使用事件中的 `kind`、`billId` 加 `status=ALL` 调用流水查询可回读对应明细。首次基线和纯历史关联不提醒。现有 Agent OS 的旧事件解码器不能直接消费此协议，需要另行对接。
- 人员 UI 和智能体均使用既有 `POST /api/v1/command-previews`、`POST /api/v1/command-previews/:id/confirm`，收款传真实 `transactionReference`，退款传 `refundReference`、同订单 `referencesFactId` 和真实金额。Preview 冻结外部流水依据；Confirm 重新加锁核对，匹配与资金事实原子提交。单纯读取权限不能登记财务。
- 未来智能体可以订阅发现事件、查询候选、在群里提出建议，获得工作人员确认后调用上述命令；本次没有发送群消息，也没有实现群路由、人员确认消息的鉴权消费或真实 webhook 投递。

官方昵称解析已实现。QiWe 为后续覆盖补充：其 `userId` 与官方 `external_userid` 应用上下文、登录节点和昵称编码尚需实际账号联调，首版未启用 QiWe 抓取。昵称失败显示“昵称未取得”，不会伪造姓名或阻止流水保存。
