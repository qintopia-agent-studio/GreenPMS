## 目标与边界

对已确认的四个历史订单恢复真实合同金额，并把两笔真实合付款按订单分配。以房号作为本文核对标签，不记录住客姓名、订单 ID、事实 ID、交易号或连接凭据。

| 核对标签 | 目标合同金额 | 对应合付款分配 |
| --- | ---: | ---: |
| 303 | ¥180 | 第一笔 ¥360 中的 ¥180 |
| 306 | ¥180 | 第一笔 ¥360 中的 ¥180 |
| D03 | ¥180 | 第二笔 ¥310 中的 ¥180 |
| D04 | ¥130 | 第二笔 ¥310 中的 ¥130 |

D03 合同保持 ¥180；D04 从旧错误的 ¥0 恢复为有历史依据的 ¥130。原收款、原计价修订与旧匹配记录均保留，通过追加冲销、分配释放、新分配及计价修订完成，不发起实际收款或退款。总实际收款 ¥670 不变。

普通非会员 WECOM 订单的新建及金额更正必须大于0；不能以“合付款已记在另一订单”为由调成0。正式免费住宿与会员权益覆盖下合法的零现金路径保持原规则，取消、未到、撤销入住的既有生命周期金额处理不改写。

## 077 owner 专用维护方案

`packages/db/src/migrations/077_owner_historical_payment_reprice.sql` 提供普通 WECOM 新计价修订的零金额数据库防线，以及仅数据库所有者可执行的 `qintopia_reprice_fixed_historical_d04`。历史住宿安排修改的公开命令保持原合同金额不变，不通过改房或改期来承载本次重价。

维护函数使用直接 owner 会话（`current_user = session_user = 数据库所有者`）；撤销 PUBLIC 与 `qintopia_runtime` 的执行和写入权限，不向员工 API、Token 或助手开放维护入口。追加 `owner_historical_payment_reprices` 记录，运行时仅可读；该记录禁止更新、删除，并有每物业固定计划唯一约束。

函数只允许固定 D04 情形：已退房且住宿完成、非免费非会员 WECOM、固定房源与已核验住期、预期版本未漂移、当前合同0、政策基础价130、可追溯的历史130修订，无会员覆盖或权益流水等禁止依赖。追加 `REPRICE_ORDER` 修订、命令、回执和审计，并更新订单当前修订指针及版本；不新增或改写住宿房段，不改变库存、住期和历史收款。延迟约束在事务提交时复核整条维护证据链与0→130金额关系。

迁移安装与 owner 维护执行是两个独立步骤。安装迁移不会自动修复历史订单；上线发布、真实数据库写入仍按已有发布与用户授权执行。

## 固定计划、事务与核验

入口为 `scripts/operations/historical-payment-reconciliation.ts`，默认 dry-run。生产 CLI 将环境输入生成的计划 SHA 与已核验生产计划的固定 SHA 比对，并要求独立提供已审阅 SHA；不能用更换订单后自算的新 SHA 冒充原批准计划。实际输入与受控核对报告仅保存在不入库的验收资料中。导出执行函数也校验批准 SHA；正式执行要求显式 owner 连接，不允许隐式落到默认数据库。

dry-run 使用只读事务，报告四单合同前后目标、两笔分配及总收款基线。执行在同一事务内获得维护锁、既有资金锁与按稳定顺序取得的订单、账单锁，随后重新验证：物业、版本、当前金额、原事实类型/净额/币种/交易号/来源账单、未冲销状态、退款/留存/内部划转占用、账单成功状态/审核标记/来源启用/同号唯一性，以及旧有效分配和固定计划一致。

正式步骤是恢复 D04 合同、冲销两笔旧整笔收款并释放对应分配、按四个固定份额追加收款与分配。复用现有资金命令与账单绑定逻辑；失败回滚整组操作。提交前逐单重读合同与净收款，逐账单比对有效分配的订单和金额，并检查总收款守恒。保留带计划 SHA、幂等键、资源引用的命令回执与审计；重复或并发执行不能产生第二组成功事实。
