# 可配置会员产品实施规格

## 目标、决定与授权

管理员可以在设置中管理会员产品，员工从当前在售产品办理会员；修改产品以后，新订单使用新规格，历史会员权益保持原约定。

用户已确认名称、售价、适用房型、总夜数和有效期都可设置；2026-11-17 补充确认**首版有效期只支持月／年，不支持天**。用户要求文档完成后在本项目新开 low effort 对话，先同步最新代码，再完成开发、验证、人工验收步骤和 PR；**不合并、不发布、不写生产业务数据**。此前 2800 元独卫标间／大床通用会员，用户已报告上线、验收并开始使用；新功能须保护这些存量权益。

本规格采用讨论方案：管理员管理、产品不可变版本、停售仅影响新销售、订单快照不追随商品修改。详细工程步骤见 [开发清单](plan-membership-product-management.md)，人工验收以 [主计划](../../待开发项/QinTopia-PMS-分步开发与人工验收计划.md)末尾本功能章节为准。

本规格作为 [会员订单](spec-step-2b-membership-orders.md)、[会员住宿](spec-step-2c-member-balances-and-stays.md)和 [独卫通用会员](spec-private-bath-shared-membership.md)的增量，替代固定产品列表与固定一年限制；收款、生效、核销、退款、临时安排、历史纠错的其他既有规则继续有效。旧文档“不做通用会员产品编辑器”的阶段性范围由本次明确需求替代，不重开已验收资金流程。

## 最小完整功能

入口为「设置 → 会员产品」。同门店 ADMIN、SESSION 身份可以新增、编辑、复制、新售／停售和查看变更历史；普通员工保留既有会员办理权限，无产品管理权限；API Token 不获得管理能力。

| 内容 | 首版规则 |
| --- | --- |
| 名称 | 去掉首尾空白后非空；长度上限使用项目现有名称字段约定，前后端一致 |
| 售价 | 人民币正整数元，持久化为整数分，遵守现有整数范围；本期不增加免费会员发放流程 |
| 适用房型 | 当前门店房型目录多选、至少一种、不可重复；发布时必须存在且可售，不能接受外店或伪造 code |
| 权益单位 | 从房型销售单位推导：ROOM 对应间夜，BED 对应床夜；同一版本不能混用 ROOM 与 BED |
| 总夜数 | 正整数，遵守数据库 integer 和现有余额安全整数边界；选中房型共享一份额度 |
| 有效期 | 正整数 + 月／年，默认 1 年；不支持天、混合单位或无限期 |
| 销售状态 | 在售／停售；新建确认后在售，编辑停售产品后仍停售，需显式恢复销售 |
| 复制 | 只预填新建表单，确认后成为独立产品；不能复制产品身份或旧订单关联 |
| 历史 | 查看每次修改前后内容、操作者和时间；用户不必手工维护版本号 |

页面采用既有「填写 → 核对影响 → 确认 → 回执」流程。编辑核对明确“只影响此后新建的会员订单”；停售核对明确“已建订单与已售权益继续按原规格办理”。加载失败不能显示为空列表，冲突后保留输入并提示刷新核对；手机、键盘操作与错误提示沿用现有组件。

不增加商品草稿、审批、定时上下架、优惠券、节假日倍率、自动续费、自定义规则脚本、产品删除或旧会员批量改权益。房价调整与会员售价互不联动。

## 有效期与历史快照

持久化沿用 `validity_period`，只接受规范的 `P{正整数}M` 或 `P{正整数}Y`，例如 `P6M`、`P1Y`。不把年改成固定 365 天，也不把月改成固定 30 天；不接受 `P0M`、小数、负数、混合时长和天。计算结果必须是系统支持的合法 `YYYY-MM-DD`，超过日期或整数范围明确拒绝。

按门店当地生效日期，一次加上指定日历月／年；目标月份没有该日时取该月最后一天。直接加 N 月，不能逐月循环造成月末漂移。**保留现有到期日包含在内的业务口径**：服务日期 `<= valid_until` 可覆盖，到期日次日不可覆盖，住宿离店日不计一夜。

| 生效日 | 期限 | 到期日 |
| --- | --- | --- |
| 2026-11-17 | 1 年 | 2027-11-17 |
| 2026-11-17 | 6 个月 | 2027-05-17 |
| 2026-01-31 | 1 个月 | 2026-02-28 |
| 2026-01-31 | 2 个月 | 2026-03-31 |
| 2028-02-29 | 1 年 | 2029-02-28 |

普通新办仍以显式生效的门店日期起算；在住升级、管理员补录和日期更正继续使用其既有获准起算日，不擅自统一成付款日或建单日。TS 和 SQL 使用相同的日期规则和例表。

会员订单创建时锁住名称、标价、成交价、产品 ID／code／版本、房型集合、权益单位／总数及有效期；**DRAFT 也已经锁定**。新增订单明确保存期限快照；旧订单新增字段默认读作 `P1Y`，不重算其 `valid_from`、`valid_until`、合同、Lot 或已用夜数。历史补录事实也保存期限快照，旧补录同样兼容 `P1Y`。

编辑后，旧 DRAFT 可以继续收款、生效；旧 ACTIVE 的预订、入住、续住、换房、取消及扣减按各自快照处理。停售不使旧订单失效、不撤回余额、不阻止历史详情读取。更正生效日时用该订单的期限快照重算相应更正结果，不取当前产品期限；已有受保护事实仍经原纠错协议追加记录。

历史补录只能由既有授权管理员按真实历史规格选择本门店已存在的不可变版本，包括已停售产品的版本；明确显示版本内容，不默认套用最新在售版本。保留真实性、仍有效、重复与归属等原有门禁；技术 `created_at` 不作为真实售卖起点的证明。没有匹配版本时停止该笔补录，不能临时猜期限或追溯伪造产品历史。作废重建沿用原权限和事实来源约束，并携带实际所选版本快照。

## 最小数据模型

复用 `membership_products` 作为已形成的不可变版本表。其 `PUBLISHED` 表示版本已形成，**不再承担当前是否在售的判断**；原 `UNIQUE(code, version)`、产品行 UPDATE／DELETE 禁令不变。

新增一个目录头表 `membership_product_catalog`：

| 字段 | 约束与责任 |
| --- | --- |
| `code` | 全局唯一，匹配版本表既有 code；系统生成新 code，用户只编辑名称 |
| `property_id` | 非空门店外键；code 和归属创建后不可修改，目录头不可删除 |
| `current_product_id` | 当前不可变版本；数据库约束必须与目录头为同一 code |
| `sale_status` | `ON_SALE`／`OFF_SALE` |
| `revision` | 正整数，任何有效修改加一，用于冲突检测 |
| 时间及审计关联 | 沿用现有管理命令审计模式，能够回查操作者及前后内容 |

全部版本通过真实 `membership_products.code → catalog.code` 确定门店归属；无需给历史版本增加门店字段或放宽 append-only。编辑在同一事务内追加 `version + 1` 并切换目录头；停售／恢复只修改目录头。头指向同 code 的约束须由数据库执行，不能只靠前端。

首个版本与目录头在同一事务建立，使用事务结束时的约束检查新插入版本已有合法目录头，解决双方首次建立的顺序问题；不能使用互相要求“对方必须先存在”的普通 BEFORE INSERT 守卫。此检查只针对新增版本，不回写旧四模板。受限运行角色只能通过受控命令写入，无直接改版本、任意改头或执行初始化函数的能力。

新建销售订单须在事务内按所选产品的真实 code 校验：目录归属与订单门店一致、在售、所选产品 ID 等于当前版本、房型合法；不信任客户端提交的 code／单位／数量／期限。数据库对新订单 INSERT 校验期限快照与真实 product ID 所指版本一致，对 UPDATE 禁止修改快照；`DEFAULT P1Y` 只承接旧记录，不能替代新订单的明确写入和一致性检查。历史补录走其 ADMIN 专用协议，允许本门店历史版本但不能绕过审计；已有 DRAFT 激活不重新执行“当前在售”校验。

保留 `allowed_room_type_code` 与可空集合的历史兼容：旧 NULL 集合等价原单房型；新版本保存规范去重集合和稳定锚点。复用 082 的范围匹配，不重做权益账本。

## 事务、权限、读取与房型联动

新增 `MANAGE_MEMBERSHIP_CATALOG` 管理命令，使用明确的 CREATE／UPDATE／SET_SALE_STATUS 操作分支；复用现有 Preview／Confirm、审计、幂等和原回执恢复。操作由服务器分配产品身份与版本，更新／状态变更携带期望 revision；管理权限仅授同门店 ADMIN SESSION，不捆绑 `MANAGE_ROOM_CATALOG`，不允许 Token 自行申请或执行。

Preview 展示完整规格、前后差异和影响范围。Confirm 重新检查权限、目录 revision、所选房型及房型目录 revision；过时或事实变化返回现有 409 冲突协议，不能悄悄应用最新版本。记录产品与房型依赖，按现有固定锁顺序串行化同门店管理、销售确认和房型变更，事务失败不留版本、目录头或审计残片。不同管理员并发编辑至多一个成功；响应丢失沿原 Confirm 身份恢复，不换键重发。

销售预览亦记录所选目录 revision；预览后编辑／停售，确认必须失败并要求重新核对。已建立的 DRAFT 是历史订单，不属于过时销售预览。售卖与停售的并发结果须能解释为同一确定先后顺序。

读取必须分开：

1. 普通办理目录：仅调用者获准门店的在售当前版本，明确门店归属；多门店账号切换后不混用产品。
2. 管理目录：同门店所有目录头、状态、当前规格及历史，管理权限校验与写入一致。
3. 历史订单／回执：依原 product ID 或订单快照读取，不用当前在售列表补历史字段。
4. 管理员历史补录：按本门店 code 的不可变版本选择，独立于新售列表。

`/api/v1/meta`、会员详情、在住升级表单和助手上下文都须按这个区分修改。当前 `members.ts` 会用产品列表补历史有效期，不能直接给该列表加“在售”过滤而使旧详情报错。

新发布／恢复在售时校验房型有效。房型停用／删除继续考虑在售产品及历史合同／Lot 等已有保护，不能先停售产品就删除仍承担会员权益的房源。现有房型删除检查会扫描全局会员产品，须改为通过 code 关联目录头并限定当前门店，同时保留本店历史版本引用保护；别店相同房型 code 不应产生阻断。单独修改房型名称时显示当前房型名称，无法解析历史名称则诚实显示保留的 code，不兜底成其他房型。

同类多个 BED 房型可以共享床夜并分别预订、扣减；**不因此扩大现有跨房型换床规则**。ROOM 范围内的正常换房沿用已实现能力，范围外临时安排仍按原规格；总夜数可配置不改变每间房／床每晚扣 1 单位的规则。

## 迁移与初始化

基线为 `02c81a7`，当时最新迁移为 082；实施前先同步远端，使用实际下一可用迁移编号，不修改任何已发布迁移。

现有 017／082 在 `properties` 创建业务数据前就插入四个全局产品；`seedDemo` 后续才创建门店。迁移必须同时支持空库和已有业务库：

| 检测结果 | 处理 |
| --- | --- |
| 零门店、零业务引用，只有已知四模板 | 建新结构成功，目录头暂为空；保留四模板原样 |
| 唯一门店，旧产品及历史引用归属一致 | 建四个在售目录头，当前指向原版本；不改原产品与业务事实 |
| 多门店、同产品跨门店引用、未知旧产品或其他归属歧义 | 以可诊断错误原子失败，先明确映射，不猜 demo 门店、不复制业务订单掩盖问题 |

已知模板 ID 为 `membership_product_shared_bath_single_v1`、`membership_product_private_bath_single_v1`、`membership_product_shared_bath_quad_v1`、`membership_product_private_bath_shared_v1`。原售价分别 1620／2160／936／2800 元，均 30 单位、`P1Y`，最后一种共享标间与大床。识别时检查完整预期规格，不能只认 ID 而掩盖被改写的数据。

空库 seed 在创建门店之后、插入会员订单之前，通过仅直接数据库 owner 可执行的初始化函数建立头；撤销 PUBLIC 和 runtime 执行权，按已有 `migrate.ts` owner 身份约束执行。此函数只初始化已知未绑定模板，重试不能重新启售、改头或改归属；后续新门店通过正式管理命令创建自己的产品，不复用别店 code。

新迁移仅向 `membership_orders` 新增期限快照列；`historical_membership_backfills.validity_period` 已在 050 存在，只扩展其原约束和相关写入／守卫，不能重复加列。同步扩展产品期限约束，更新实际相关 SQL 守卫中写死一年、固定总数或单房型的判断。readiness 同步验证列、约束、函数体、owner、search_path、触发器、权限和命令注册，保留既有保护。迁移前后比较原四产品完整业务内容以及旧订单、合同、Lot、收款、账本、审计事实；不得重算日期、余额或重新发权益。

生产迁移验证将来通过现有备份、隔离恢复演练和受控发布执行，本次不连接生产试迁移。新期限／新产品已经出售后，旧镜像不理解新语义；不能承诺仅退镜像即可安全回退。保持事实，按正式恢复流程处理，必要时前向修复。

## 页面、助手与验收边界

表单和详情显示真实产品名称、价格、房型、总夜数与期限，消除固定四产品、30 夜及“一年”的业务硬编码；历史参考价格来源文档不改成新销售事实。新命令加入助手覆盖清单，同 PR 更新 `assistant-knowledge.ts`、相关 `assistant.ts` 简短步骤和实际运行上下文。

助手解释产品管理入口与权限、旧会员不变、停售影响和共享余额。当前可售产品数据来自按门店授权的运行时查询；无数据时明确不能确认当前在售情况，不能从知识示例猜产品或余额。模拟问答不代替真实模型验收。

最低自动验证覆盖：新建 20 夜／6 个月、多房型 5+3 共用后剩 12；旧 DRAFT／ACTIVE 在编辑和停售后的保持；普通办卡、在住升级、历史补录及纠错；月末／闰年／到期日；并发编辑、销售与停售竞争、跨门店／Token 拒绝、幂等及丢回执恢复；全新迁移→seed、存量升级和歧义原子失败。完整任务及证据要求见开发清单。

交付须分开列实现、自动检查、浏览器检查、人工业务验收、真实助手问答、PR／CI／对话关联。任何一层通过都不代替下一层；不以 CI 绿灯推断数据库和 E2E 已经运行。
