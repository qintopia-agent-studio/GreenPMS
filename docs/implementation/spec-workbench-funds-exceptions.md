# 工作台资金异常处理增量实施规格

## 1. 文档职责与已确认决定

本规格记录2026-10-05用户确认的增量方案，尚未实施。它补充而不替换[多订单收退款分配与客户留存款规格](spec-payment-allocation-retained-funds.md)中的资金、事务、权限及追溯约束。

- 用户入口收敛为：**工作台“异常”发现问题 → 点“处理” → 根据真实原因进入匹配、补收、纠错、退款或留存 → 对应金额处理完成后自动退出异常**。
- 已收款先落实关联；关联后的多余款项有三个处理出口：实际退款、纠正真实错误、客户确认留存。不能通过随意改订单金额、假退款或假留存使数字相等。
- 已确认且登记完成的留存属于正常客户款，不继续作为未处理异常；仍可从订单“资金视图 → 客户留存待用”查询与使用。
- 未处理的资金不受住宿日期、订单终态或工作台浏览日期限制；昨天取消、上个月退房留下的问题今天仍可见。
- **本期不增加已退房／已取消订单改价能力，不扩大管理员终态金额修改权限。** 少量历史价错保留待核对，不妨碍交付常见资金处理流程。
- 不新增独立台账、退款审批／意向状态机、客户钱包、会员储值或平台结算能力；不改变原支付渠道的实际退款方式。

开发任务和依赖见[开发计划](../../待开发项/QinTopia-PMS-工作台资金异常-开发计划.md)；人工操作步骤、预期和验收状态统一维护在[主人工验收计划](../../待开发项/QinTopia-PMS-分步开发与人工验收计划.md#2026-10-05-工作台资金异常处理增量计划已确认待开发)。本规格不代表开发或人工验收已完成。

## 2. 当前实现基线与缺口

| 现有能力 | 本次处理 |
|---|---|
| 同物业企微收款按金额分配多个普通住宿订单；退款、冲销、留存、再使用具备原始资金关联 | 复用，不能再造资金事实或替换原流水 |
| `TodayPage`读取带`workDate`的订单，异常主要是住宿生命周期问题 | 保留住宿待办；新增独立资金读取，不直接套用按住宿日期取数的接口 |
| 订单列表“多收待核对”比较净收款与当前住宿金额，不扣已登记留存，也不直接展示差额 | 不把该筛选原样作为新的异常判定；原筛选含义本期不悄悄改写 |
| `REPRICE_ORDER`只允许`RESERVED`、`CHECKED_IN`，且仍受权限及特殊订单限制 | 只复用允许的状态；`CHECKED_OUT`、`CANCELLED`、`NO_SHOW`保持拒绝 |
| 管理员“修改历史安排”修改已完成住宿的日期／房间，保留成交价、收款和完成状态 | 不能当作历史改价入口，也不能撤销退房后绕行改价 |
| 已退房普通直接订单已有补收、退款等入口，但尚无本次资金异常汇总 | 导航复用，不重写对应命令 |

以上是基线分支的源码事实，不据此推断生产已部署。已开始使用的人工验收数据库不得重置。

## 3. 范围：异常不是简单的金额不相等

### 3.1 本期主动汇总的资金问题

1. **收款待匹配／分配**：现有同步与匹配模块中可归属于普通住宿、尚有未分配部分的企微收款。会员独占、平台结算、未成功或证据异常的流水，沿用既有用途与可用性判断，不能当作可自由使用的余额。
2. **订单多余款未处理**：普通直接住宿订单的有效净收款超过真实应收，且超出部分尚未被有效留存覆盖。覆盖预订中、在住及已取消／未到／已退房等状态；能做哪些操作仍由现有权限与状态决定。
3. **成功退款待核对**：已同步的成功退款尚未正确归属原收款及订单份额，或对应来源已被既有退款核对门禁冻结。突出核对原因，不把这笔已退款重复当作还可留存、可分配的现金。

### 3.2 沿用而不扩建的能力

- 真实少收沿用现有“待补收”查询和收款入口；处理面板或完成匹配后的结果可提供相应入口。**本期不重建应收催收清单，也不自行新增付款到期规则，不把全部正常未付预订／定金订单塞进异常。**
- 金额或归属录错时按证据进入现有金额调整、冲销或分配纠正入口。错的是收款登记不能通过改房费抵消；真实退款不能用冲销代替。
- 未匹配款没有合法来源订单时，保持待核对。不能自动建假订单、强行把钱挂到无关订单或创建无来源留存；无订单退款／留存能力不在本期新增范围。
- 管理员也不能为消除异常而改已退房／已取消订单价格。显示当前不支持的原因、保留原资金及待办，少量真实案例另行核查。

## 4. 金额口径、去重与关闭条件

### 4.1 订单多余款

对资金链有效且属于本期范围的单张订单，以最小货币单位计算：

- `N`：现有有效净收款投影，已经包含退款、冲销和内部转出／转入的净影响，不另重复扣一次。
- `C`：该订单权威当前住宿应收金额；取消订单的当前金额沿用既有业务计算，不能以初始房价代替。
- `R`：仍归属于该源订单的有效留存余额，扣除已经使用、实际退款、解除的部分。
- `unresolvedExcessMinor = max(N - C - R, 0)`。

该公式只描述“订单多余款尚未处理的部分”，不是原收款可分配额度，也不是执行退款／留存的授权。必须复用有效资金事实及留存余额规则；链损坏、来源异常、金额溢出或读取不完整时返回明确异常，不用`max`或空结果掩盖错误。混合收款来源的可留存／可退份额仍按现有来源级校验限制。

### 4.2 原收款及退款

- 原收款未分配额复用有效分配／释放事实计算；不能按“原金额减订单当前房价”推算。
- 真实退款、取消订单和内部留存使用均不自动释放原收款可分配额度。
- 同一原交易存在尚未完成归属的成功退款时，沿用冻结规则。在处理面板优先提示退款核对；不得推荐将冻结金额继续匹配、留存或使用。
- 未核实付款人昵称不等于款项归属客户；归属仍需现有确认依据。

### 4.3 去重与金额展示

- 未分配收款以原收款流水为唯一身份；订单多余款以源订单为唯一身份，同一订单多来源在行内汇总、详情可追溯各份额。
- 原收款未分配部分和已分配订单的多余部分是不同金额段；原流水只是来源引用时，不再生成一条相同金额的“余款”记录。
- 成功退款待核对与受影响来源／订单之间建立关联。可在不同记录上提示阻断原因，但**不可将关联提示再次计为一笔现金或金额合计**。
- 本期不展示将“未分配、订单多收、退款待核对”简单相加的资金总余额。标签计数表示唯一待办记录数，不表示客户数、订单数或现金总额；规则在接口及测试中固定。

### 4.4 自动退出与重新出现

- 完成合法分配后，原收款未分配部分减少；归零后该匹配待办退出。
- 实际退款并成功登记／关联后，对应订单净收款或退款核对待办更新；仅点击入口、选择退款意向或填了表单不算完成。
- 留存登记成功后，对应金额计入`R`，退出未处理异常，在留存清单继续展示；不能继续要求把已留存款再退一次。
- 正确更正现有允许修改的记录后，由服务器重算是否仍存在异常，不能人工勾选“处理完”强制隐藏。
- 部分处理只消除相应金额；解除尚未使用的留存后，未决余款可重新进入异常。留存使用／退款按原事实更新，不能产生上游余额回弹。
- 不提供无事实依据的“忽略／关闭异常”按钮，不自动退款或自动留存。

## 5. 操作体验与工作习惯

### 5.1 工作台列表

在既有“异常”标签内分区展示“住宿事项”和“资金待处理”，不是新台账或新的五状态页面。

资金行最少展示：客户／付款人线索（未核实时明确标注）、来源订单／房间或收退款单号、需要核对的金额、一句话原因、来源日期、单一主入口“处理”。取消订单可以显示“已取消，仍有600元未处理”，不能只显示订单金额0。

- 资金数据按门店汇总，不使用浏览日期筛除历史事项，明确提示“资金事项包含历史未处理款项”；不影响住宿分区原日期语义。
- 默认按原资金事实发生日期从早到晚稳定排序；日期不能冒充精确的“异常产生时间”，本期不为此新增事件时间表。
- 资金分区有独立分页。标签计数由后台按完整筛选范围返回，不能用第一页长度代替全部数量。
- 首屏加载失败显示“无法读取资金待办／重试”，计数显示未知而非0；资金读取失败不抹掉已成功读取的住宿事项。
- 桌面与手机均保持金额、原因、“处理”可见，不增加密集的固定三按钮列。

### 5.2 处理面板与已有入口

| 发现的原因 | 展示与路由 |
|---|---|
| 收款未匹配 | 选合法目标订单后进入原“登记收款／分配”流程，保留原流水线索；不自动猜客户或提交 |
| 取消等导致多余款 | 展示应收、净收、有效留存、仍待处理金额；按能力提供“登记实际退款”“登记客户留存” |
| 怀疑记录错误 | “核对／纠正”下展示可用的原有纠正入口与限制，不将改房费设置成默认操作 |
| 成功退款待核对 | 引导核对原收款份额及成功退款流水；已有留存的部分进入“登记留存款实际退款”，不得绕过留存预留 |
| 少收款 | 沿用现有待补收／收款入口，不为了相等改价，也不新增催收规则 |
| 历史终态金额确有错误 | 说明暂不支持在线金额更正，保留待办与来源详情；无伪造可执行按钮 |

- 面板只做解释和导航；写入继续走原表单、Preview、Confirm、结果恢复机制。
- 链接参数只作为导航线索，打开后必须重新读取权威对象及允许操作；不可信参数不能变成金额、来源或客户授权。
- “登记实际退款”明确说明系统记录已发生退款，不调用支付渠道发起退款。外部退款未做完或回执未知时保留待办；系统不能替代操作人员在渠道侧核查是否已退款。
- 客户留存仍要求核实归属、联系方式／依据和客户确认；“暂时没退”不能自动解释成同意留存。
- 从工作台进入操作后，返回仍定位“异常”及原筛选，重新查询待办；失败／未完成命令保留原恢复入口，不因跳转丢失草稿或恢复证据。
- 当场取消／退房后可复用命令结果区域提示“仍有款项需处理”，允许前往工作台；不以余额为由额外阻断退房、库存释放或其他合法操作。
- 不在本期新增经办分派、退款承诺登记、提醒调度或审批流程；交班以现有操作审计和未处理事实为准。

## 6. 查询、契约与安全设计

以下为拟实施接口，不是当前已存在接口：

`GET /api/v2/workbench-funds-exceptions?propertyId&query&limit&cursor`

- `propertyId`必填；复用现有认证、门店`READ`边界，跨门店拒绝。不得因是工作台就暴露额外客户资料或授权读全部门店。
- 不接收`workDate`或默认今天／最近30天等隐含截断；关键词只在允许的客户线索、订单与交易标识范围查询。
- 分页使用稳定游标，排序键为来源日期、类型、唯一ID；默认50、最多100。返回`items`、全范围唯一记录数`totalCount`、`hasMore`、`nextCursor`、`generatedAt`及继承的只读／同步提示。
- `kind`为读取原因类别：`UNALLOCATED_COLLECTION`、`ORDER_EXCESS`、`UNATTRIBUTED_REFUND`，不是持久化处理状态。
- 每条返回稳定`key`、来源引用、币种、明确含义的金额字段、日期与原因。未知金额用显式未知，不强塞0；有来源关系时返回关联提示引用，而非复制可用余额。
- 提示能力与写权限分别处理：查询结果不授予写权限；页面及写命令继续校验命令授权、功能开关、原资金来源、额度、留存占用、退款冻结和订单状态。
- 列表、金额、计数应在一致的读取快照中计算；关键来源查询失败则明确报错，不返回伪装完整的空队列。游标间允许正常并发变化，但页面以`key`去重，确认时重新核对。
- 复用资金开关。关闭后不放开新分配／留存写入，既有资金事实、留存预留与追溯读取不能消失；界面说明当前只读或受限，不修改v1默认行为。

### 数据库和写入边界

本期优先使用现有收退款、分配、释放、留存及订单金额数据构建**只读聚合**，不新增“异常余额”账本、不回填人造收款、不维护可以与资金事实失步的“已处理”标志，也不新增退款意向表。

不修改终态金额权限、取消／退房语义、原始流水、资金写命令或既有事件载荷。若代表性数据查询性能证明需索引，仅采用必要的增量索引并履行既有迁移检查；不得借优化修改金额含义、运行身份权限或CI。

## 7. 典型状态与回归要求

| 场景 | 预期 |
|---|---|
| 收款1000，尚未分配 | 一个原收款待匹配事项；不是B已收600，也不能直接建无来源留存 |
| A分配400，B尚未收款 | 原收款待匹配600；B没有已收600，不能凭订单房价合成收款 |
| A400／B600均已分配，取消B | 原收款未分配0；B待处理600；不得双报原流水余600 |
| B留存600 | B未处理0，资金异常退出，留存清单600，原收款仍未分配0 |
| B留存200，其他400尚未处理 | B资金待处理400、留存清单200；登记成功退款400后待处理0 |
| B留存600，C使用400，再退留存200 | 不新增现金，不恢复原分配额度；留存余额0，保留使用与退款历史 |
| B尚有600，渠道成功退款但未归属 | 明确待核对与来源冻结，不能建议再次退款／留存；不重复合计该600 |
| 历史已取消／已退房仍有余款 | 任意工作台浏览日期均可找到，不因离店日过去而退出 |
| 真实应收1000，只收800 | 使用原待补收入口，不改价至800、不登记假留存；正常未付预订不一律进入本期余款异常 |
| 已入住普通订单实际价格录错 | 有权限时走既有调整金额流程，提交后重算，不改实际收退款 |
| 已退房／已取消订单金额录错 | 管理员也不出现可执行改价操作，保留问题，不绕行撤销退房 |
| 两人同时处理、提交超时、重复确认 | 继续原幂等／额度锁／恢复约束，不能重复花费；前端不能仅按本地金额隐藏待办 |
| 超过一页、跨门店、证据缺失、读取失败 | 不漏历史页、不越权、不伪报0，不把无法处理的钱隐藏掉 |

应覆盖纯函数、数据库聚合、权限／接口契约、浏览器往返与失败恢复；新测试与原资金和房态回归均按实际影响选取。完整工程工作包、命令与完成门槛见开发计划。未解决的既有全量回归失败不得通过修改CI、弱化检查或重置人工库规避。

## 8. 非目标与回退

- 已退房金额更正、终态价格权限、无订单客户钱包、平台结算、会员储值、自动真实退款、催收到期策略、退款审批／意向状态机、人工一键忽略异常全部不在本期。
- 新工作台查询／展示退回旧入口时，现有分配、退款、留存、使用事实必须完整保留；不能用回退清理业务数据。
- 生产上线、迁移执行和现有资金开关开启仍走项目发布及验收流程；本计划不授权部署。
