# 工作台资金异常处理增量实施规格

## 1. 目标与最小实现

用户已确认：**工作台“异常”发现未处理款项 → 点“处理”进入已有页面 → 完成真实业务操作 → 重新查询后退出异常。** 本增量已实现并完成相关自动验证，待人工验收。

按2026-10-05用户要求，应用“奥卡姆剃刀”技能：只补现有功能缺少的资金查询和入口衔接，不把小功能做成新的一套管理系统。

本期只增加三个能力：

1. 从现有资金事实查出本门店仍需处理的款项，历史订单也能找到。
2. 在已有工作台“异常”标签里显示金额、原因和一个“处理”入口。
3. 直接复用已有订单、收退款、分配、留存页面；操作完成后刷新待办。

**不另建处理面板、资金台账或工单流程，不新增钱包、退款意向状态机、认领分派、自动提醒、审批或一键忽略异常。已退房／已取消订单金额更正暂缓，管理员权限也不放开。**

本规格补充[原资金规格](spec-payment-allocation-retained-funds.md)，不替换其资金不变量。任务顺序见[开发计划](../../待开发项/QinTopia-PMS-工作台资金异常-开发计划.md)；人工步骤和状态只维护在[主验收计划](../../待开发项/QinTopia-PMS-分步开发与人工验收计划.md#2026-10-05-工作台资金异常处理增量已实现待人工验收)。

## 2. 什么进入异常，什么不进入

| 情况 | 本期处理 |
|---|---|
| 普通住宿适用的企微收款还有未分配部分 | 显示待匹配金额，去已有选单／收款流程匹配；不自动猜客户或关联订单 |
| 普通直接住宿订单有未处理的多余款 | 显示未处理金额，去订单详情按实际情况退款、纠错或留存 |
| 成功退款已同步但尚未完成归属核对 | 显示待核对原因，沿用原收款来源冻结，不把已退资金再当作可用款 |
| 客户已确认且已经登记留存 | 不再计为未处理异常；仍可在“资金视图 → 客户留存待用”查询和使用 |
| 真实少收 | 沿用现有“待补收”查询和收款入口，不为了相等改房费；本期不新增催收或付款到期规则 |
| 正常未付预订／分次付款 | 不因订单金额与实收不同就一律判作本期多余款异常 |
| 已退房／已取消的成交金额确实录错 | 保留问题并说明暂不支持在线改价，查看原订单后另案核对，不绕行撤销退房 |

会员独占、外部平台结算、未成功或证据异常的流水沿用现有用途与可用性限制，不自动变成普通住宿可用款。没有合法来源订单时，也不能强挂无关订单或创建无来源留存；无订单退款／留存能力本期不新增。

## 3. 必须正确的金额和去重规则

### 订单多余款

在资金链有效且属于本期范围时，复用现有投影，以最小货币单位计算：

- `N`：有效净收款，已经包含退款、冲销和内部转出／转入的净影响。
- `C`：权威当前住宿应收金额，取消后不能仍用原始房价。
- `R`：仍归属该源订单的有效留存余额，已扣使用、实际退款和解除。
- **未处理多余款 = `max(N - C - R, 0)`。**

不再次从`N`扣一遍退款或内部转出；不从原收款金额减当前房价来推算分配余额。公式仅用于待办显示，不授予退款或留存额度。金额矛盾、来源损坏或读取不完整时明确报错，不能用0掩盖。

### 原收款、成功退款及去重

- 原收款未分配额复用现有有效分配／释放记录计算；取消、真实退款和留存使用均不自动恢复原收款可分配额度。
- 未分配款按原收款识别；订单多余款按源订单识别；同订单多来源汇总后仍可追溯各份额。
- 原流水作为已分配订单的来源引用时，不再生成同一金额的另一条“余款”。
- 成功退款未归属时，优先显示待核对与既有冻结限制。冻结按原收款来源生效，不能隐藏同订单其他独立来源：订单行取`min(max(N-C-R,0), 未冻结未预留来源余额)`，冻结部分由退款待核对项承载，核对完成后按全量事实重算。可在关联订单上提示，但不能把同一待退款项重复计成现金；不显示将不同原因金额机械相加的总余额。
- 原付款人昵称不能自动当作款项归属客户；客户留存仍走现有归属核实与确认。

### 退出条件

完成分配、实际退款登记、合法纠错或有效留存后，由真实事实重算；只打开表单、口头说要退款、填写草稿都不算完成。部分处理只减少对应金额，剩余金额继续显示。解除未使用留存后，未决余款可以重新出现。

不新增可手工勾选的“已处理”字段。读取失败不能显示空队列或已清零；确认时仍由原命令校验余额、来源、权限、并发与幂等。

## 4. 页面怎么做

### 工作台

沿用现有“异常”标签，保留住宿事项，补上资金事项。每行只需：**客户／付款人线索、订单／房间或交易单号、金额、一句话原因、处理入口**。没有核实的客户信息要明确标注；来源日期可直接复用已有数据，不新增“异常起算时间”记录。

资金事项独立于住宿浏览日期，显示“包含历史未处理款项”；翻页不能漏历史事项，不能把第一页数量冒充全部。优先沿用现有分页样式；展示完整计数时由服务端可靠计算，不为本期新增统计看板。

保留必要的加载、空态、错误／重试、无权限和手机适配。资金读取失败不清空原住宿事项，也不变成金额0。

### 点“处理”之后

- **已有订单的问题：直接进入原订单详情及相关操作区。** 不再加一个重复展示同样信息的中间面板。
- **尚未关联的收款：进入已有选单／收款流程。** 保留可核对或复制的原交易单号；只补必要导航线索，不复制一套流水选择器，不自动关联或提交。
- 根据现有权限和状态提供原操作；不能为了每条都凑三个按钮而显示不可执行的退款、留存或改价。
- “登记实际退款”说明仅登记已发生退款，不向渠道发起退款；有留存预留的款项继续走原留存退款入口。
- 合法在住改价继续走原金额更正；已退房／已取消不能改价，现有管理员“修改历史安排”也不能代替。
- 返回工作台仍定位异常标签及原筛选，并重新查询。失败／超时使用既有恢复入口，不能丢草稿或据本地猜测隐藏待办。
- 取消／退房后回到工作台仍能看到余款。优先复用已有金额摘要，不为本期另加阻断弹窗，更不能因余款阻止合法退房或库存释放。

导航参数只是线索；打开页面后重新读取权威对象。写入继续走原表单、Preview／Confirm和恢复机制，不增加第二套资金写逻辑。

## 5. 最小技术改动

| 层级 | 必要改动 |
|---|---|
| 数据查询 | 基于现有订单金额、有效资金事实、分配和留存记录做只读聚合；不套用工作台按住宿日期截断的订单查询 |
| API | 优先复用已有接口；现有接口无法完整表达跨日期汇总时，仅补一个只读查询，沿用门店认证、参数和分页惯例 |
| 前端 | 工作台增加资金行与必要导航；原处理页只在衔接确有缺口时做最小调整 |
| 验证 | 验证金额、跨日期、部分处理、去重、权限、原入口及返回刷新，不另建测试框架 |

不在计划阶段预建通用异常服务、工单模型、缓存、定时任务、事件订阅或复杂接口扩展字段。新增查询的实际路径、字段与测试随实现一起明确，只返回这次界面确实使用的数据。

默认不新增业务表、不回填余额、不维护退款意向或人工关闭状态。没有性能证据不新增索引；确需索引时只做必要增量迁移，不借此修改资金语义、权限或CI。

以下校验不能简化掉：门店隔离；分页不漏项；同一资金段不重复；未知金额不当0；功能关闭后历史事实仍可追溯；写入继续检查原来源冻结、预留、金额、权限与订单状态。不修改v1默认行为、既有事件或资金写命令的业务含义。

## 6. 最小验证场景

1. 原收款1000：未分配1000 → A分配400后剩600 → B分配600后归零；没有关联的钱不能伪装成B已收。
2. 取消B：原收款未分配仍0，B未处理600；留存200后只剩400异常；全部正确处理后退出。
3. 留存600 → C使用400 → 留存实际退款200：不新增现金、不恢复上游可分配额度，历史可追溯；解除留存的未决金额可重新出现。
4. 跨月已取消／已退房余款、超过一页、切换浏览日期：仍能找到，不重复计数或计款。
5. 成功退款未归属、提交失败／结果未知、两人竞争：不能提前退出、重复花费或绕过原冻结与恢复机制。
6. 在住允许改价、终态仍拒绝、真实少收走原补收、只读／跨门店及读取失败：不伪造纠错、不越权、不伪报0。

测试复用项目现有工具与独立合成库，不重置用户正在操作的人工验收数据，不改CI或放宽检查。人工步骤以主验收计划为准，原资金功能尚未完成的验收不能被这次增量替代。
