# QinTopia PMS 需求与运行逻辑审计报告

## 1. 审计结论

QinTopia PMS 的产品核心没有失控。房床库存、日期计价、订单与 Stay、履约变更、会员权益和人工资金事实可以组成一条完整且一致的运营主线。外围智能体 API、PostgreSQL 并发互斥、幂等、审计和恢复也都是原始目标的一部分，不应简单归类为过度设计。

当前主要问题不是功能数量，而是以下四类治理和运行风险：

1. 多份新旧文档仍同时保留 `done` 与待实施内容；主计划和 90 天规格已在本次审计收口中统一为 `awaiting-review`、`implementation_authorized: false`，但仍缺少一页唯一的当前需求索引。
2. 若干关键业务时点没有定论，包括提前退房、逾期入住、追溯换房、待清洁可售性和会员多合同分配。
3. 最新运营流程与当前可执行合同存在明确差距，最典型的是 7 夜以上报价、免费入住渠道、会员选择、创建时人工定价和服务端 allowed actions。
4. 15 阶段计划把核心业务、UI 重构、基础设施和全量验收绑成一条严格串行链，交付方式已经膨胀，容易重复建设和反复改网格。

因此，本审计的结论是：

- **产品方向：合理，可以继续。**
- **当前需求权威链：不合格，需要先收口。**
- **当前计划：已明确标记为尚未授权实施。**
- **当前代码：核心基线可运行，但不满足最新运营流程。**
- **建议动作：为剩余 7 项业务/架构 gate 指定最晚决策里程碑，再把 15 阶段压缩为 6 至 7 个可独立验收的运营里程碑。**

本报告不授权开发。用户明确说“开始实施”之前，不应修改业务代码、数据库、API、测试或 UI。

## 2. 审计边界与方法

本次只审计当前目录，不读取旧 PMS、FewohBee、其他仓库或 Git 历史。审计对象包括：

- 当前核心规格、房态目标、昵称增量、90 天规格和最新分步计划；
- 登录工作人员的关键用户旅程，包括入口、字段渐进显示、操作步数、反馈、错误恢复、返回上下文、响应式和无障碍；
- contracts、domain、PostgreSQL migrations、commands、queries、API 和 Web 当前代码；
- 单元、领域、集成、契约和 E2E 测试结构；
- README、Docker、备份恢复和测试运行脚本；
- 用户在当前任务中明确给出的最新决策和实施门禁。

证据分类：

| 分类 | 含义 |
|---|---|
| 已确认冲突 | 两个当前声明不能同时成立，或最新需求与当前代码直接相反 |
| 开放决策 | 业务结果会因选择不同而改变，不能由开发者自行推断 |
| 实现差距 | 最新需求已经明确，但当前代码尚未实现 |
| 范围治理 | 功能本身可能合理，但交付组织、文档权威或工程成本失衡 |
| 可接受复杂度 | 复杂但直接服务核心业务和数据正确性，不应删除 |

详细证据位于 [EVIDENCE-MAP.md](./EVIDENCE-MAP.md)。

## 3. 必须保留的核心

下列能力是 PMS 主线，不属于需求膨胀：

| 核心能力 | 保留原因 |
|---|---|
| 房间/床位逐日库存和双向互斥 | 决定能否避免重复销售，是系统存在的基础 |
| 44 房、91 床、77 基础库存和 90 个销售入口口径 | 已由真实业务事实核定，直接影响库存和计价产品 |
| 日期驱动的 1/7/14/30 档计价和政策版本锁定 | 已有真实价格事实，且续缩换必须可复算 |
| 一个 Order、一个 Stay、追加 amendment/segment/revision | 同时满足当前运营视图和历史审计 |
| 正常住宿、免费入住、内部占用、维修锁房不被折叠成同一事实 | 免费入住已有真实居住人和零金额边界；内部占用的精确业务分类仍需用户确认 |
| 会员逐日 coverageSet、冻结、核销、释放和并发守恒 | 会员不是折扣，必须保留具体日期和权益事实 |
| 独立 COLLECTION/REFUND/REVERSAL 及其计价修订依据 | 符合人工经营事实，并能追溯原始预订、续住、缩短和换房，但不把 PMS 扩成支付或会计系统 |
| Web 与 API 共用领域规则和事务 | 避免工作人员与外围智能体出现两套业务结果 |
| Preview/Confirm、幂等、Receipt 和中断恢复 | 是外围智能体可靠写入所必需的协议，不应从 API 删除 |
| PostgreSQL 并发、备份恢复、readiness 和契约测试 | 直接保障库存、权益和命令结果的可信度 |
| 90 天连续时间轴和超长住宿侧栏输入 | 是已经确认的高频排房效率需求，不等于无限时间轴 |

## 5. 关键问题详解

### GOV-01：实施批准状态已在审计收口中修正

初审时，分步计划 frontmatter 同时写了 `status: pending` 和 `approved: true`，90 天规格还要求接收任务后直接实施。用户随后明确要求：完整讨论、审阅文档后，只有收到“开始实施”才可以修改。

这不是文字瑕疵。审计收口已把两份待开发文档统一改为 `status: awaiting-review` 和 `implementation_authorized: false`，90 天规格也明确必须等用户说“开始实施”。

剩余治理要求：

- 任何后续任务都以当前 `implementation_authorized` 和用户最新消息为准。
- 用户明确说“开始实施”后，再由一次文档变更把该字段切换为 true。
- 旧文档中的自动执行指令不得高于当前门禁。

### GOV-02：没有单一当前需求权威

核心规格和旧房态目标写 `done`，新计划又把同一能力列为 pending。旧文档要求显示 Receipt、Claim 和“阻断”，新计划则禁止工作人员看到这些技术词。昵称旧规格保留“首个昵称 +N”的已完成证据，新规则要求全部昵称直接显示。

处理建议：

- 增加一页 `CURRENT-REQUIREMENTS-INDEX`，只记录当前有效范围、批准状态、覆盖关系和未决 gate。
- 旧 `done` 文件冻结为 historical baseline，不再作为当前验收入口。
- 新计划只引用历史基线，不复制整段旧验收。
- 测试通过数量必须绑定具体 commit 或工作树摘要，不能作为未来增量完成证明。

### DOM-01：整段选择不能抹去变更审计

用户已经确认两个诉求必须同时成立：点击任一天定位完整订单/Stay，但续住前后不能显示成没有边界的一段住宿。开发计划和核心规格现已固化为“两层结构”，当前代码仍未实现。

已确认模型：

- 选择容器是整个 Order/Stay，点击任一有效日期都打开同一个订单上下文。
- 区块内部保留原始预订、续住、缩短和换房的视觉分界。
- 右侧默认显示“当前有效行程”，另有只读“变更记录”按 amendment 展开。
- 换房后可跨多行共同高亮，但每个 segment 保留房源和生效日期。
- 不为了审计把一次连续 Stay 拆成多个订单，也不把历史快照行直接伪装成当前行程。

实施时还必须让每笔资金事实沿 `Order -> pricing revision -> amendment` 反查到对应原始预订或变更；这与 FIN-03 是同一条审计链。

### DOM-02：提前退房与缩短语义冲突

当前 `CHECK_OUT` 可以立即释放全部未来库存，但不会改变订单退房日期，也不会按缩短后晚数重新报价。最新计划则把“提前退房或缩短住宿”列为动作，并明确缩短需要重价和人工退款参考。

这会造成一种危险状态：房源已经释放并重新可售，但订单仍保留原退房日和原合同金额。

实施前必须选择：

- 提前退房必须原子执行“缩短、重价、释放未来库存、退房、创建清洁任务”；或
- 业务明确允许“提前离店但合同金额不变”，并为它建立独立命令、原因和清晰文案。

普通 `CHECK_OUT` 不应静默承担两套语义。

### DOM-03：缺少状态乘营业日期矩阵

当前命令多数只检查订单状态，不检查操作日期是否合理：

- RESERVED 可以在入住日前提前办理 CHECK_IN；
- 已过退房日的 RESERVED 也可以正常 CHECK_IN；
- CHECKED_IN 可以把 MOVE 的生效日设为历史日期；
- SHORTEN 可以缩到当前营业日前，可能改写已经履约的日期；
- 未到没有明确最早或最晚办理时点。

在实施入住、退房、续住、缩短、换房、取消和未到之前，必须先核定一张矩阵：

| 动作 | RESERVED | CHECKED_IN | CHECKED_OUT | 日期限制待确认 |
|---|---|---|---|---|
| 办理入住 | 候选 | 禁止 | 禁止 | 是否只允许到店日及其后；过期订单是否走补录命令 |
| 办理退房 | 禁止 | 候选 | 幂等查询 | 早于计划退房日是否自动进入提前退房流程 |
| 续住 | 候选 | 候选 | 禁止 | 新退房日必须晚于当前；在住新增权益立即核销 |
| 缩短 | 候选 | 候选 | 禁止 | 在住时不得追溯改写已履约日期 |
| 换房 | 候选 | 候选 | 禁止 | 生效日能否早于营业日；未来换房何时锁房 |
| 取消 | 候选 | 待确认 | 禁止 | 入住后不应复用普通取消 |
| 未到 | 候选 | 禁止 | 禁止 | 何时才允许判定未到 |

表中“候选”不是审计给出的业务答案，只表示当前需要用户确认。

### DOM-04：待清洁与可售关系存在语义歧义

旧房态设计把清洁作为不改变夜间 Claim 的履约任务，新计划写成“待清洁，完成后恢复可售”。这句话可能只是人员可见状态顺序，也可能暗示清洁期间库存不可报价；仅凭当前文案不能证明实际报价和排房结果已经改变。

推荐业务拆分，仍需用户确认：

- 夜间库存可售性与房间当前清洁就绪状态分开。
- 待清洁可以不占用未来夜间库存，但在未完成前不能办理下一位住客实际入住。
- UI 可显示复合状态，例如“待清洁 / 今晚可售”，而不是把待清洁等同于库存不可售。
- 如果业务确实要求待清洁期间完全不可售，则必须创建明确的库存 Claim，而不能只靠颜色或任务状态阻断。

### DOM-05：免费入住与内部占用的精确边界尚未批准

已确认的免费入住事实包括：有真实入住人、使用与普通住客相同的资料、金额为 0、不使用会员权益，并记录义工或接待相关原因。现有房态基线把内部占用定义为没有住客的 Block，但用户明确表示仍在考虑两者如何区分，尚未批准最新计划中的完整分类表。

因此，审计只确认两者不能被默认为同一事实，不把以下内容擅自升级为经营规则：

- 哪些具体场景必须创建内部占用；
- 内部占用是否永远没有责任人或使用人信息；
- 商务接待与内部团队使用如何划界；
- 两者在报表和房态上使用什么最终名称。

这项决策最晚应在首次正常/免费建单里程碑前完成。

### MEM-01：会员多合同分配没有业务规则，现有模型只支持单合同

新流程要求工作人员选择会员本人，由服务端从该会员全部有效合同和 Lot 中分配权益。当前 Quote、Order 和定价服务都绑定单个 `memberContractId`，且 coverage 写入函数把全部 coverage 固定到同一个合同。

这不仅是 UI 改动。若允许一单跨多个合同覆盖，需要明确：

- 合同和 Lot 的确定性消耗顺序；
- 同一日期只允许一个 coverage 的唯一性；
- Order 关联 memberId 的方式；
- coverage item 的真实 contractId/lotId；
- 并发锁顺序和余额复算；
- Receipt、Query 和审计如何展示跨合同来源。

可选规则例如“最早到期优先，再按稳定 ID”，但这会改变真实权益消耗，不能由开发者代替业务批准。

## 6. 已确认需求与当前实现的主要差距

### PRC-01：日期落档尚未成为服务端权威

价格事实已经确认：付费住宿的 1/7/14/30 档只由连续住宿总晚数决定，`TRANSIENT/WEEKLY/MONTHLY/CUSTOM/FIXED_TERM/ROLLING` 不是六套公式。

当前 API 仍要求 `stayType`，Web 仍要求工作人员选择。服务端只特别拒绝 7 夜以上的 `TRANSIENT`，却可能接受一晚 `MONTHLY` 这种相互矛盾的经营标签。用户遇到的 104 房 10 夜无法报价就是这一差距的直接结果。

建议：

- 计价档位永远由服务端根据日期推导。
- 旧 `stayType` 不得控制价格。
- 需要区分“付费住宿的人工档位标签”和“正常/免费业务类型”。若这些付费标签仍有报表意义，应另设可选业务标签；若没有用途，应从新写入合同弃用。`FREE` 仍需由独立稳定的业务类型字段表达，不能随付费标签一起删除。
- `/api/v1` 兼容字段只能被忽略或校验一致，不能让客户端覆盖服务端推导。

### PRC-02：自动报价会产生永久写放大

现有 Quote 是可恢复的持久命令，每次都写 Quote、Command execution、Audit 和 Receipt，并永久保留。新计划要求日期或房源变化后自动、防抖触发报价。

如果照现状实现，拖选和反复改日期会把大量临时试算变成永久命令事实，并快速增加数据库、审计和恢复噪声。

推荐方案，仍需架构确认：

1. 日常编辑使用只读“住宿金额试算”Query，复用相同计价领域函数，不写经营事实。
2. 工作人员点击“创建订单”进入订单概述时，再创建一个持久、可恢复、与表单绑定的正式 Quote/Preview。
3. Confirm 继续重新校验库存、政策、权益和权限。
4. 外围智能体仍可使用现有持久 Quote 命令，不降低其恢复保证。

### ORD-01 至 ORD-03：首次创建事务仍不符合最新流程

当前存在三项相互关联的差距：

- 免费订单仍要求渠道，且没有 `freeStayCategoryCode=VOLUNTEER|RECEPTION`。
- 人工指定最终价只能在建单后另发 REPRICE，无法与首次订单原子确认。
- Confirm 强制 reason code 和 note 都非空，而最新正常创建流程不要求工作人员填写原因。

这些应在同一个“首次创建合同”里解决，避免先创建错误中间状态再补改。

### ORD-04 和 ORD-05：订单读模型与动作模型不足

当前 `segments` 返回不可变快照链，续住和缩短会产生重叠记录。工作人员真正需要的是：

- 当前有效且不重叠的住宿行程；
- 完整 amendment/revision 历史；
- 当前状态和营业日期下服务端允许的动作；
- 每个动作的业务化禁用原因。

房态 `allowedActions` 当前只覆盖创建、打开订单、Block 释放和清洁，不能驱动入住、退房、续住、缩短、换房、取消、未到和资金操作。订单详情则直接渲染几乎全部按钮，依赖服务端事后拒绝。

建议先完成权威订单 read model 和服务端 action policy，再做右侧操作区。

### FIN-03：资金事实尚不能直接对应具体变更

用户已确认：每笔新 COLLECTION/REFUND 由服务端自动保存本次操作所依据的不可变 pricing revision；REFUND 还必须继续引用原 COLLECTION。一个 revision 可以关联多笔分次资金事实，工作人员不选择内部 revision ID。该关联只是业务追溯依据，不表示外部到账、结清、核销或会计分摊。

当前 `collection_facts` 只有 `order_id`、`references_fact_id`/`reverses_fact_id`、`transaction_reference` 和 `command_id`，没有 pricing revision 外键。现状能回答“这张订单发生过哪些收退款”和“退款引用哪笔收款”，不能直接回答“这笔补收或退款由哪次续住、缩短或换房产生”。

实施要求：

- 新 COLLECTION/REFUND 的 Preview 绑定本次依据的 pricing revision，Confirm 时 revision 变化必须陈旧拒绝且零写入；
- 数据库验证 revision 与资金 Fact 属于同一 Order；
- 历史资金 Fact 的关联允许保持真实 `null`，不得虚构回填；
- Query/Receipt/OpenAPI 提供稳定关联，工作人员 UI 派生显示“原始预订收款、续住补收、缩短退款”等业务关系；
- 退款仍以原 COLLECTION 为金额上限和来源关系，不能只靠 pricing revision 代替。

### STA-01 和 STA-02：生命周期投影会误导工作人员

历史已完成的住宿日期被投影为 `IN_HOUSE`。若 Web 把枚举直接翻译成“在住”，查看历史日期时会误认为住客现在仍在房。

同时，逾期未退是当前实现已经识别的重要异常，但最新简化生命周期只写“已预订、在住、已退房/待清洁、可售”，容易把逾期异常丢失。

建议：

- 当前状态与历史当日状态分开表达。
- 历史日期使用“历史住宿”或专门的历史状态，不复用当前“在住”。
- 逾期未退保留主状态“在住”，附加明确异常“逾期未退”，并继续阻断当日库存。

## 7. 安全、隐私与运行边界

### SEC-01：READ 权限不足以表达 PII 边界

当前物业级 READ 主体可以通过 `/api/v1/meta` 和会员 Query 读取完整身份证号、手机号和微信号；房态 READ 也会返回住客昵称。原始要求只定义 READ 小于 WRITE，没有确认字段级隐私范围。

这对工作人员会话和外围只读 Token 的风险不同。建议用户确认：

- 只读外围智能体是否可以批量读取完整身份证号；
- 会员搜索是精确身份证匹配后返回脱敏结果，还是允许列表遍历；
- 房态昵称是否只对特定运营主体可见；
- 是否增加独立 `MEMBER_PII_READ` 或用途型 scope；
- 审计入口如何记录敏感字段查询。

在决策前，不应把“物业 READ”自动解释为“可读取全部个人敏感信息”。

### DB-01：数据库事实归属约束还不完整

当前数据库约束了 append-only、current revision 归属和部分资金关系，但仍有若干跨事实归属主要依赖应用命令正确：

- amendment 与 revision 是否属于同一 Order；
- segment 的 amendment 是否属于该 Stay 的 Order；
- coverage 的 Contract、Lot、Order、Property 是否一致；
- Order 的 member contract 是否属于同一 Property；
- policy version 和 inventory unit 是否属于订单 Property。

应用层路径已有大量事务测试，但 PMS 被定义为唯一权威，数据库至少需要约束或触发器验证最关键的父子归属，防止未来代码错误形成结构合法、业务错误的数据。

### OPS-02：本地 MVP 可运行不等于生产部署完成

当前 Docker 镜像用 `tsx` 运行源码，包含开发依赖，未见非 root 运行和完整响应安全头策略。对本地或内网演示可以接受，但如果“可投入日常运营”意味着公网或正式生产部署，需要单独的发布门禁：

- 非 root、最小运行镜像；
- TLS 终止和 secure cookie 强制策略；
- CSP、frame、referrer 和敏感 API `Cache-Control: no-store`；
- 密钥管理、日志脱敏和备份保留；
- 数据库、镜像和恢复演练的运行责任人。

不建议在当前 UI 讨论阶段顺手扩大成完整云平台建设，应在部署前单独批准。

## 8. 真正的范围膨胀在哪里

### 8.1 不是膨胀

- 房床互斥、锁版计价、会员覆盖和人工资金事实；
- 外围智能体可靠命令协议；
- 真实 PostgreSQL 并发、事务回滚、幂等和恢复；
- 90 天时间轴加 366 夜侧栏输入；
- 工作人员中文业务流程；
- 正常、免费、内部占用和维修不被折叠成一个含糊事实；其精确分类仍按 DOM-05 确认。

### 8.2 已出现交付膨胀

1. 15 个阶段每一阶段都默认要求 Web、API、领域、数据库和四层测试，即使某阶段只是展示调整。
2. 90 天虚拟化被放在阶段 14，前面 13 个阶段可能先围绕旧分页网格反复开发，再整体重写交互状态。
3. “全部昵称直接显示”与可变行高、90 天窗口、边缘滚动、移动替代视图和 200% zoom 同时实施，属于一个高风险网格架构项目，不应拆散后重复改布局。
4. 自建数据库测试进程树监管器规模较大，且依赖 POSIX `ps`。它解决的是本地并发测试管理，不应继续扩成产品平台能力。
5. Feishu Base 当前只需要外部申请引用模型。实时同步、回写正确性和工作流托管不应进入核心发布阻断路径。

### 8.3 明确延期或排除

| 范围 | 建议 |
|---|---|
| 多住客/同行人档案 | 延期。当前只承诺每张床订单的主要居住人；整房同行人需另行确认 |
| 飞书实时同步和强依赖回写 | 延期。保留外部 record_id 引用，核心正确性不依赖 Base |
| 支付平台、微信支付接口、Webhook、银行对账 | 排除 |
| 会计应收、收入确认、自动核销、自动退款 | 排除 |
| 通用公式、低代码、动态定价引擎 | 排除 |
| 旧 PMS 兼容、历史迁移、双写和切换机制 | 排除 |
| 无限时间轴、默认 180/365 天网格 | 排除，保留 90 天窗口和 366 夜侧栏 |
| 超过当前 44 房/90 销售入口的通用甘特平台 | 延期到真实规模需求出现 |

## 9. 建议核定的 7 个剩余 Gate

| Gate | 必须回答的问题 | 最晚决策里程碑 | 审计推荐，但不是已确认事实 |
|---|---|---|---|
| G2 | 提前退房与普通退房的关系 | 里程碑 5 | 提前退房使用原子“缩短、重价、退房”命令；普通退房只用于计划边界 |
| G3 | 各状态下动作允许在哪个营业日执行 | 里程碑 5 | 建立状态乘日期矩阵；追溯补录使用独立权限和原因 |
| G4 | 待清洁是否影响夜间可售 | 里程碑 4 | 清洁是就绪任务，不占未来夜间库存；入住前必须完成 |
| G5 | 免费入住与内部占用按什么经营条件区分 | 里程碑 1 | 免费入住保留真实住客；内部占用保持独立事实，具体分类由用户定义 |
| G6 | 一名会员多个合同/Lot 如何消耗 | 里程碑 2 | 业务确认后采用确定性顺序，例如最早到期优先加稳定 tie-break |
| G7 | 自动显示金额是否创建永久 Quote | 里程碑 1 | 编辑期使用只读试算，进入订单概述时才创建持久正式报价 |
| G8 | READ Token 能看到哪些会员和住客敏感字段 | 里程碑 6 | 默认脱敏，完整 PII 使用独立 scope 或受控运营会话 |

已确认并从 Gate 移除的事项：

- 同一 Stay 使用整单选择容器，内部保留原始预订与 amendment/segment 审计边界；
- 每笔新 COLLECTION/REFUND 自动绑定本次操作依据的 pricing revision，REFUND 同时引用原 COLLECTION；
- “入住即核销整段已冻结权益，入住后普通缩短不恢复”是当前最新已确认规则。

另外一项仍应在对应里程碑前确认：

- `method` 是否仍是 COLLECTION/REFUND 的必填经营事实；

## 10. 建议的增量路线

保留“一步实施、一步人工验收”，但不再把 15 个顺序阶段视为 15 次全栈重建。

| 里程碑 | 目标 | 主要人工验收 |
|---|---|---|
| 0. 权威与 Gate | 冻结当前需求索引，为 G2 至 G8 记录负责人和最晚决策里程碑 | 用户审阅文档并明确“开始实施”；不要求与首个切片无关的 Gate 全部提前完成 |
| 1. 报价与首次建单 | 日期自动落档、自动试算边界、中文订单概述、一次确认、原子手工最终价、正常/免费字段 | 104 房 10 夜能报价；正常和免费订单各创建一笔 |
| 2. 会员选择与覆盖 | 选择 memberId、多合同/Lot 规则、全额/部分/零余额、并发冻结 | 普通订单默认无会员字段；勾选后完成三种覆盖 |
| 3. 权威订单读模型 | 当前行程、变更历史、Stay 选择、服务端 allowed actions、订单详情契约 | 点击任一天定位整段，同时看见原始与变更边界及对应资金摘要 |
| 4. 最终房态网格 | 全昵称、比例、正常业务语言、90 天虚拟化、边缘滚动、内部/维修区分 | 桌面、平板、移动、320px、200% zoom 人工检查 |
| 5. 履约与变更 | 入住、退房、续住、缩短、换房、取消、未到及会员时点 | 按状态乘日期矩阵逐项验收，重点验提前退房 |
| 6. 资金、智能体与发布 | 多笔收退款、计价修订依据、原收款引用、人工差额、外围 API 恢复、PII scope、并发/备份/全量回归 | 从原始预订/续住/缩短追溯资金事实，完成受限 Token、真实 PostgreSQL 和浏览器 E2E |

这一顺序先固定计价和订单事实，再固定订单读模型，随后一次性建设最终网格，避免在 14 天分页网格上完成大量动作后再改成 90 天虚拟时间轴。

## 12. 给独立审计者的重点挑战

独立审计者不应只确认本报告，应主动寻找：

1. 本报告把核心复杂度误判为必要的地方；
2. 本报告把可逆 UI 决策误判为业务阻断的地方；
3. 任何会导致库存重复销售、权益多扣少还、金额不可复算或历史被覆盖的遗漏；
4. Web 与外围智能体 API 可能出现不同事实路径的地方；
5. 当前测试通过但错误需求被测试固化的地方；
6. 可以删除、延期或简化而不损害核心旅程的范围；
7. 需要用户而不是开发者决定的经营事实。
8. 工作人员是否能在不理解 Quote、Preview、Confirm、Receipt、Claim、policy/revision ID 的情况下完成正常、会员、免费和变更旅程；底层可靠协议不应被误删，也不应被直接搬成多次人工确认页面。
9. 每条旅程是否只在需要时展示字段，是否存在“应用选区后再创建”“单独技术确认页”“成功后进入 Receipt 页”等重复步骤，以及失败、中断、陈旧数据和返回房态时是否保留可理解的上下文。
10. 桌面、平板、移动、键盘、屏幕阅读器、320 CSS px 和 200% zoom 下，核心任务是否仍可完成；没有运行浏览器证据时必须明确标为未验证，不能从 CSS 或测试名称推断体验通过。

可直接使用 [EXTERNAL-AUDITOR-PROMPT.md](./EXTERNAL-AUDITOR-PROMPT.md) 发起第二轮独立审计。
