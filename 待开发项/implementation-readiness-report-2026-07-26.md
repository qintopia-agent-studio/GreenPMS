## PRD Analysis

### Functional Requirements

FR1: 操作员执行命令时，主流程统一表达为“填写 -> 核对确认 -> 界面即时反馈”；步骤数对应人的业务决策，不对应 Preview、Confirm、Receipt 等技术阶段。

FR2: 服务端预检仍然保留并绑定当前表单；操作员打开核对页时自动取得预检结果，不需要手动点击“生成服务端预览”。

FR3: 核对页本身不得写入 Order、Stay、Claim 或其他业务事实；只有一次明确的最终确认才允许服务端重新校验并原子写入。

FR4: 成功后关闭命令弹窗、刷新权威界面状态，并以非模态提示和可选下一步入口反馈；不得要求操作员进入独立技术回执页。

FR5: 工作人员主流程不得出现 Preview、Confirm、Receipt、Command、effect、Quote/Receipt/Command/Correlation ID、幂等键、内部对象 ID、raw JSON、内部枚举及协议字段名。

FR6: 核对页应使用业务标题，展示住客、房源、日期、总晚数、渠道、政策基础金额和最终金额等当前决策所需信息；去掉“服务端变更差异”“有效至 + quote id”和“完整 effect”。

FR7: 普通付费订单展示住宿总晚数和金额；免费订单展示免费总晚数、免费类型和具体原因；会员订单仅在会员模式下用中文展示总晚数、权益覆盖晚数、未覆盖晚数及未覆盖金额。

FR8: 正常创建订单不要求操作员填写自由文本原因；只有人工偏离政策基础价时，才显示并强制填写独立的调价原因。

FR9: 命令协议仍保存与命令类型匹配的稳定操作意图 reason code，操作员不可见；外围智能体不得绕过 reason、预检、显式确认或审计。

FR10: 创建订单时的人工目标价必须与初始订单在同一个原子命令中形成首个完整 pricing revision，不得先按原价建单再执行第二条改价命令。

FR11: 人工目标价为非负人民币整数元，同时保存政策基础价与差额；任何后续 revision 不继承旧的手工目标价。

FR12: 新建非会员正常住宿必须选择 YOUMUDAO、CTRIP、MEITUAN 或 WECOM；前三个渠道必须提供非空渠道订单号，WECOM 必须保存空渠道订单号。

FR13: 免费入住必须保存义工或接待类型和具体原因，金额为 0，渠道、渠道订单号及会员权益均为空；历史空分类不得虚构回填。

FR14: 会员住宿渠道为空；普通订单完全隐藏会员覆盖信息，只有显式选择会员权益时才展示会员资料与覆盖摘要。

FR15: 房源标签应统一去重，已经包含房号的名称不得再次拼接相同 code，例如不得显示“105 · 105”。

FR16: 房态中的订单选择必须以服务端稳定 orderId/stayId/sourceReference 为身份；换房后同一 Stay 的原房和新房分段应共同高亮，不得按昵称、颜色或相邻日期推断。

FR17: 操作后的中断恢复只向操作员说明中文业务状态；系统必须先查询服务端结果，确认不会重复写入后再允许继续。

FR18: 正常住宿状态统一显示“已预订 -> 在住 -> 已退房”，退房后的清洁任务独立显示“待清洁/已完成”，内部状态词和 Claim/阻断信息不进入主界面。

FR19: 全站机器信息应逐页盘点并分类为“取消、改写、保留在技术审计”；获权技术审计能力与操作员日常订单详情必须分离。

FR20: 通用命令弹窗外观可统一收敛，但续住、缩短、换房、取消、未到、资金等尚未实施阶段的业务规则、表单和验收不得在当前阶段提前改变。

FR21: 渠道手续费、平台提成和实得金额属于后续收款对账的数据模型与经营语义，本检查点只记录需求，不实施或预埋跨层字段。

FR22: API、数据库、审计与开发者故障排查仍保留 Preview、Confirm、Receipt、command、correlation、幂等、稳定内部 ID 和不可变引用；UI 隐藏不等于删除协议。

### Non-Functional Requirements

NFR1: 幂等与恢复：双击、重放、响应中断、断网恢复均不得重复产生 Order、Stay、Claim、revision、coverage 或资金事实。

NFR2: 原子性：最终确认必须重新校验授权、版本、库存、权益和计价，成功事实与永久结果同事务提交；失败不得产生部分写入。

NFR3: 陈旧保护：表单变化、库存或价格变化、预检过期后不得提交旧结果，应以中文业务错误要求重新核对。

NFR4: 数据完整性：内部稳定 code、ID、DTO 和审计事实继续保持机器可读；不得为了中文展示修改持久化语义或虚构历史值。

NFR5: 安全与权限：Web 与外围智能体使用同一授权和领域规则；READ 主体不得获得写操作，Token 不得扩大主体权限或绕过高风险确认。

NFR6: 可用性：所有常规页面信息必须能帮助操作员完成判断；隐藏文字、Tooltip、屏读名称同样不得转移暴露技术协议。

NFR7: 可访问与响应式：桌面、平板、手机、320 CSS px、200% zoom、键盘与屏幕阅读器均不得发生内容重叠、不可达或横向溢出。

NFR8: 交互稳定性：后台刷新、投影轮询、弹窗开关和动作完成不得丢失仍有效的选择、表单、滚动位置或焦点。

NFR9: 性能与竞态：自动预检需要防抖、取消过期请求，并保证迟到响应不能覆盖最新表单结果。

NFR10: 测试完整性：修改旧 E2E 断言时必须改写为新的业务行为断言，不得以删除断言、降低覆盖或减少测试数量代替修复。

NFR11: 阶段治理：采用“一阶段一人工验收”，当前阶段不得夹带未开始阶段；已验收行为发生回归时必须回到当前切片修复并重新验收。

NFR12: 单一写入路径：优先复用现有 Command service、Quote、pricing、coverage 和恢复机制，不建立第二条业务写入路径。

### Additional Requirements

- 当前第四步 4.1 尚处于 `awaiting_user_acceptance`，4.2 需要独立、可追踪的状态和验收停点，不能只作为 4.1 文档末尾的无状态附录。
- `apps/web/src/ui.tsx` 是多个阶段共用的热点模块，同一时间只应有一个写入负责人；其他任务只能做只读审查或独立测试。
- 当前检查点不得读取旧 PMS/FewohBee，不得重置用户工作树，也不得顺手重构无关模块。
- 后续资金语义、会员主档编辑、内部占用及待清洁是否阻断可售均有未决边界，当前不得自行补完。

### PRD Completeness Assessment

业务目标和主要安全约束已经足够清晰，但需求分散且存在三处待验证冲突：一是“4.2 只改 UI”与创建时原子改价可能需要合同/领域改动；二是“全部命令统一”与阶段 9 至 13 尚未启动的停点约束；三是 4.2 对内部 ID 在订单详情中的保留说法，与上位计划要求日常订单详情主区域不显示内部 ID 不完全一致。后续覆盖检查必须把这三项作为阻断候选，而不能留给实现者自行选择。

### Missing Requirements

**Critical - FR10 原子创建与调价：** 4.2 不能把“先建原价订单，再紧跟改价命令”作为可选实现。第二条命令失败会留下与操作员最终确认不一致的原价订单，也会制造两个 revision/恢复边界。应明确只接受现有 CREATE_ORDER 原子携带人工目标价的路径；若当前合同不支持，4.2 必须停下并重新决定是否允许跨层，而不是由开发者自行选。

**Critical - FR20 阶段边界：** 当前 4.2 位于阶段 8 的第四步验收中，却要求统一创建、换房、续缩、资金等全部命令。可以在共享组件层统一隐藏机器外壳，但不得改变阶段 9 至 13 的业务表单、原因、金额或动作规则。计划需要把“共享呈现框架”和“各命令业务内容”拆成两个范围。

**High - FR3 核对页零写入：** 应补充明确验收：打开、关闭、返回修改和预检失败均不产生业务事实。

**High - FR7/FR14 会员摘要：** 应把“隐藏 coverageSet 技术字段名”改成“会员模式保留中文业务摘要；普通和免费模式完全不显示会员覆盖模块”，消除误删会员判断信息的风险。

**High - FR9 reason code：** API 行为不能留作“拒绝或补默认值”二选一。上位规则已经给出稳定操作意图 reason code；计划应固定 Web 自动提交匹配 code、note 为空，API 对缺失或不匹配行为按现有合同精确验收。

**High - FR12 渠道回归：** 将 YOUMUDAO/CTRIP/MEITUAN 渠道订单号必填、WECOM 必须为空纳入 4.2 创建订单 E2E 回归，防止表单收敛时重新变为可选。

**Medium - FR19 信息清单：** 清单应在编码前交付并由用户确认；至少包含页面、原文、处理方式、保留的业务替代文案和所属未来阶段。否则“全站排查”无法判断是否完成。

## UX Alignment Assessment

### UX Document Status

仓库没有单独命名的 UX 文档，但 UX 资料实际存在于：

- `docs/implementation/room-status-ui-development-goal.md`
- `docs/implementation/room-status-grid-implementation-spec.md`
- `design-system/qintopia-pms/MASTER.md`
- `待开发项/房态与订单运营流程分步开发计划.md` 的工作人员语言、目标主流程与阶段验收

设计系统能够支持紧凑运营界面、对话框、非模态反馈、响应式和无障碍要求；架构已有服务端预检、持久结果、幂等恢复和 committed DTO，也能够支持隐藏技术协议后的两步操作员旅程。

### Alignment Issues

1. **旧 UX 资料与新工作人员语言冲突。** `room-status-ui-development-goal.md` 仍要求页面持续显示 `asOf/freshness`、冲突对象代码、Receipt 链接，并把 Preview/Confirm/Receipt 作为可见步骤；`room-status-grid-implementation-spec.md` 也把这些旧呈现标为 done。新分步计划虽声明覆盖旧术语，但未在旧文档中加醒目的 superseded 标记，后续任务可能按旧验收恢复机器信息。

2. **成功结果形态存在旧新冲突。** 分步计划的目标主流程和阶段 2 仍写“成功页”，4.2 则决定取消独立成功页，改为弹窗关闭、界面状态变化、toast 和可选“查看订单”。应将上位计划中的旧“成功页”同步改成“成功反馈”，否则验收无法确定是否允许第三层页面。

3. **非模态反馈需要持久结果兜底。** 旧 UX 正确要求“不能只显示 Toast”。4.2 已包含界面状态变化和恢复，但还应明确：刷新失败或提交结果未知时，保留可恢复的中文业务状态，不得在 toast 消失后让操作员无法判断是否已创建。

4. **自动预检缺少焦点与取消合同。** 4.2 没有写明自动预检加载期间的按钮状态、关闭弹窗是否取消/忽略迟到响应、返回修改后旧结果失效、错误摘要聚焦，以及 Escape/关闭后的焦点恢复。设计系统和旧 UX 已要求这些能力，应加入验收而非依赖现有实现碰巧正确。

5. **会员摘要文案可能误删决策信息。** “coverageSet 概念不对操作员显示”应只指隐藏英文协议和技术结构；会员订单仍必须显示中文的覆盖晚数、未覆盖晚数和未覆盖金额。否则核对页不再帮助操作员判断权益是否正确。

6. **内部 ID 的可见边界需要精确定义。** 4.2 一处说内部 ID 只保留在订单详情，一处又说日常操作员不依赖内部 ID。应区分“工作人员可识别的订单号”和“数据库/命令内部引用”；前者可在订单详情出现，后者应只存在于技术审计、日志和 API。

7. **全站清理与阶段治理未对齐。** 令牌页、资金页、续缩换等页面包含机器语言，但分步计划把部分内容放在未来阶段。当前可以输出全站盘点和统一共享弹窗外壳，却不能借“全站收敛”提前重新定义未来业务页面。

### Warnings

- 4.2 没有独立的线框或状态矩阵，但不是实施阻断；现有设计系统足以支撑。真正缺失的是命令弹窗的明确状态表：自动预检中、可确认、已过期、提交中、结果未知、成功关闭、失败未执行。
- toast 必须使用克制的 live region，并与页面真实状态变化绑定；仅靠颜色或短暂提示不满足 WCAG 2.2 AA 和中断恢复需要。
- 4.2 应继续验证 375/768/1024/1440、320 CSS px、200% zoom、键盘、Escape、焦点圈定与返回焦点，不能只跑文案单元测试。

## Epic Quality Review

### Critical Violations

1. **一个检查点打包了多个不可同风险交付的故事。** 当前 4.2 同时包含共享命令弹窗状态机、全站机器信息盘点、创建时人工改价、换房后 Stay 选择恢复、订单详情文案和跨全部命令回归。它们涉及不同用户价值、代码热点和失败模式，无法作为一个可快速签收的独立故事。

   建议拆为：

   - 4.2A：共享命令外壳，只收敛自动预检、一次确认、即时反馈和恢复状态；
   - 4.2B：当前已验收页面的操作员文案清理，以用户先审阅的全站清单为输入；
   - 创建订单原子改价回归到阶段 2/其返工检查点；
   - 换房后选择恢复回归阶段 11，或仅修复阶段 7 已承诺的“稳定 Stay 选择”回归并明确不改换房业务。

2. **存在违反既有架构的可选实现。** D 节允许“创建后紧跟一条改价命令”，但上位计划明确要求初始人工价和订单在同一个原子命令中形成首个 revision。故事把关键事务选择留给实现者，不能进入开发。

3. **存在前向依赖和未来阶段侵入。** “全部命令统一”要求验证续住、缩短、换房、取消、未到、资金等阶段 9 至 13 的完整业务表现，而这些阶段尚未实施和验收。当前故事因此无法独立完成，也无法判断失败属于 4.2 还是未来业务缺失。

4. **资金验收写入了错误业务规则。** 风险项 3 的“收款金额与最终合同金额一致”与核心规格允许分次收款、保留 `collectionDifference`、不推导结清语义直接冲突。该断言会把阶段 13 的资金经营规则提前并错误地带入 4.2，必须删除。

### Major Issues

1. **故事标题偏技术收尾，用户价值不够可验收。** “操作员视图收尾”容易扩展成无限的全站清理。应改成可验证结果，例如“操作员用填写和一次核对完成当前已支持的命令，不看到技术协议”。

2. **命令覆盖集合没有冻结。** 计划写“全部命令”，却没有命令矩阵列出哪些已上线、哪些只改共享外壳、哪些属于未来阶段完全不碰。开发者只能通过搜索代码自行扩大范围。

3. **状态机验收不完整。** 没有逐态定义自动预检中、可确认、返回修改、预检过期、提交中、结果未知、失败未执行、成功关闭及重复结果的 UI、可用按钮和焦点行为。

4. **全站盘点没有交付门禁。** C 节要求输出清单，但没有规定编码前用户确认，也没有要求记录页面、原文、判定、替代文案、所属阶段。它会变成边搜边改，增加遗漏和返工。

5. **验收口径与宣称范围不匹配。** 收尾验收只举创建、换房、退房和清洁；没有为维修 Block、会员命令、取消、续缩、收退款等“全部命令”给出独立验收，因此无法证明全站完成。

6. **代码地图明显不足。** “全站逐页面排查”只列出 `ui.tsx`、`InventoryPage.tsx` 和一个房态上下文组件，没有列出订单详情、今日履约、订单列表、会员、令牌、样式、共享类型、API 客户端及具体测试文件。主任务势必在开发中重新发现范围。

7. **4.2 没有独立状态。** 文档 frontmatter 仍是 4.1 的 `awaiting-user-acceptance`，没有 `4.2: planned/in_progress/awaiting_acceptance/accepted`，导致 4.1 是否通过、4.2 是否开始和返工属于哪一项无法追踪。

8. **测试门禁过于笼统。** “全部测试套件通过、数量不减少”不足以证明行为正确；需要列出聚焦 unit、contract、PostgreSQL、各命令 E2E、响应式/无障碍和恢复场景，并明确哪些数据库测试因 UI-only 理论上不应改变。

### Minor Concerns

- 4.2 B 节的“coverageSet 概念不显示”措辞不够精确，容易误删会员覆盖业务信息。
- 4.2 C 节将订单详情保留内部 ID 解释为“供开发者排查”，但系统并没有已定义的开发者 UI 权限或技术审计视图。
- “toast + 刷新”没有规定刷新失败时如何保持成功或未知结果的可见性。
- 4.1 的历史变更日志已经很长，继续把 4.2 需求、发现和实施结果混写在同一日志会降低可读性和交接可靠性。

### Quality Recommendation

当前 4.2 不宜按原样作为一个九步左右的大任务一次开发。先完成一次短的计划修订，把跨阶段项移回所属阶段，再用两个可独立验收的 4.2 故事推进。每个故事都应具备冻结范围、状态矩阵、具体文件/测试地图和单独人工停点。

## Summary and Recommendations

### Overall Readiness Status

**NOT READY AS WRITTEN（原计划不宜直接重新启动开发）**

方向是正确的：操作员只做“填写、一次核对”，技术协议留在服务端和开发排查层，成功通过界面变化与可恢复反馈表达。但当前工作安排把多个阶段、不同风险和一个错误资金断言混进同一检查点，容易造成主任务步骤膨胀、长时间改动和跨层返工。

### Critical Issues Requiring Immediate Action

1. 删除“创建后再紧跟一条改价命令”的可选路径；初始人工价只允许在 CREATE_ORDER 原子事务中形成首个 revision。若现有合同不支持，应将该项移回阶段 2 并单独决定是否授权跨层。
2. 把“全部命令统一”拆成“共享呈现外壳”与“各阶段业务内容”。当前只修改已实现、已进入验收范围的命令外壳；阶段 9 至 13 的业务表单和规则留在未来。
3. 删除“收款金额与最终合同金额一致”断言。4.2 不校验结清；分次收款、净收款与差额由阶段 13 负责。
4. 将换房后选中丢失标记为阶段 7 稳定 Stay 选择的回归修复，而不是借 4.2 改换房业务或计价链。
5. 解决旧 UX 文档与新计划的冲突，并把“成功页”统一改成“成功反馈”；明确旧 Preview/Receipt/机器信息只保留为后端合同，不再是操作员可见步骤。

### Recommended Next Steps

1. 先暂停按旧提示词扩大编码，仅修订计划文档；不需要回滚已经安全完成的 4.1 工作。
2. 建立 4.2A“共享命令外壳”故事：冻结命令清单，补齐自动预检到结果恢复的状态矩阵、焦点/无障碍合同和聚焦测试。
3. 建立 4.2B“当前页面信息减负”故事：开发前先输出全站清单，由用户确认“取消、改写、未来阶段”分类后再动 UI。
4. 把创建订单改价移入阶段 2 的返工检查点；把换房高亮移入阶段 7 回归；把渠道实得和资金差额继续留在阶段 13。
5. 为 4.2 建立独立状态字段和人工停点，不再与 4.1 的 `awaiting_user_acceptance` 共用一个模糊状态。
6. 将会员覆盖规则明确为：普通/免费订单隐藏模块；会员订单保留中文覆盖晚数、未覆盖晚数和未覆盖金额。
7. 增加三渠道订单号必填、WECOM 订单号为空的创建订单回归，防止 UI 收敛再次把必填变回可选。

### Final Note

本次审计识别出 4 个关键违反项、7 个主要计划缺口和若干文档/无障碍问题。核心问题不是 UX 方向错误，而是切片方式不合理：应先把计划拆小、归位，再重新启动 4.2 开发。这样主任务的工作量会从一个跨阶段的大改，收敛为两个可以分别验证和及时停下的 UI 检查点。
