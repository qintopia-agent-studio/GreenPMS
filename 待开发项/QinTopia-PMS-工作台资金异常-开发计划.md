## 一、只解决这个问题

**工作台异常能找到还没处理清楚的钱，显示金额和原因；点击后到已有页面处理，完成后自动退出异常。**

钱尚未关联时先匹配；多余款按退款、纠正真实错误、客户确认留存处理；真实少收沿用原补收。已登记留存不继续报未处理异常，昨天或上个月留下的款项不能因日期过去而消失。

2026-10-05按用户要求采用“奥卡姆剃刀”技能收敛：不另建处理面板、资金台账、工单系统、钱包、退款意向状态机、分派提醒或审批；不预设整套未来接口。不新增已退房／已取消改价，不扩大管理员终态权限。

## 二、三个开发步骤

### P1：补上可靠的资金查询（已实现、已验证）

- 开始前检查分支、上游变化与他人未提交文件；复用合适目录，保护现有人工验收数据。
- 复用已有资金、分配、退款和留存投影，查未分配收款、订单多余款、成功退款待核对。
- 订单未处理多余款按`max(净收款 - 当前应收 - 有效留存余额, 0)`计算；退款和内部转移不重复扣，来源异常不能按0掩盖。
- 跨日期、门店隔离、分页和去重一起做好。现有接口不够用时，只补一个遵循既有惯例的只读查询；不新增状态表、缓存、任务调度或资金写逻辑。
- 就近补金额／查询／权限测试；完成后确认历史款项不漏、原流水与订单不重复计钱。

### P2：接入现有工作台和处理入口（已实现、已验证）

- 工作台“异常”保留住宿事项，增加简洁资金行：来源、金额、原因、一个“处理”按钮；做好加载、失败／重试、空态和手机展示。
- 有订单的直接去原订单详情。未关联收款进入现有选单／收款流程，保留原交易单号；只补必要导航，不增加中间处理面板或复制表单。
- 退款、留存、纠错、补收仍使用原命令和权限。已退房／已取消金额错误说明暂不支持，不为清空异常绕过门禁。
- 操作后返回原异常标签并刷新；部分处理保留剩余金额，留存成功不再报异常，失败／超时继续原恢复机制。
- 不因余款阻止入住退房或库存释放，不新增付款到期规则；原工作台住宿分类和日期行为不变。

### P3：最短可信验证与人工交付（工程完成，待人工验收）

- 跑受影响的资金／工作台单元、独立库查询与权限测试；验证退款冻结、留存、部分处理、并发和幂等没有被新入口绕过。
- 在独立合成环境检查桌面／手机、跨日期、超过一页、处理往返、读取失败及命令结果未知恢复；不重置用户正在操作的人工库。
- 沿用`npm run typecheck`、`npm test`、`npm run build`、`node --test scripts/check-pr-tests.mjs`；数据库类测试通过既有锁runner运行。既有失败与本次引入的问题分开记录，不改CI或放宽门禁。
- 更新主验收计划、提供可访问预览与必要截图，按3组检查交给用户验收；提交PR，不擅自合并或部署。

不用人为再拆很多阶段；只有现有代码出现明确责任边界、且可独立推进时才并行。若使用子代理，遵从用户当前模型要求，各自独占文件，禁止同时修改同一文件。

## 三、范围与改动幅度

| 保留的必要改动 | 明确不做 |
|---|---|
| 现有资金事实的只读汇总、必要查询接口 | 新账本、业务状态表、通用异常引擎 |
| 工作台资金行、必要导航和刷新 | 新台账页、重复处理面板、第二套资金表单 |
| 复用现有合法金额更正、匹配、补收、退款、留存 | 已退房／已取消改价、扩大管理员终态权限 |
| 针对性测试和人工验收 | 新测试框架、放宽原CI、生产发布 |

以查询和界面衔接为主，默认不需要业务数据库迁移；有实际性能证据再考虑必要索引。不按假想规模提前设计，不虚估固定工期。虽然保持小改动，资金判定仍按A 级验证。

## 四、验收与完成标准

人工操作只维护在主验收计划，分3组：

1. **钱看得见**：未分配、分次匹配、取消余款、跨日期历史事项与分页。
2. **处理后正确退出**：退款、留存、部分处理、解除后重现，以及失败不误关。
3. **边界不被放开**：在住合法纠错、终态继续拒绝、原补收、权限、读取失败、手机和原住宿操作。

已退房金额更正在[延期清单](deferred-work.md)中，不是本期交付阻塞，但不能伪装已修好；跨日期资金查询不能延期。原资金功能的待验收项也不能被本次自动检查替代。

完成时分别记录：已实现、已验证、待人工验收、PR状态。截图和日志放已忽略的`.local-workspace/`，不提交业务快照或凭据。回退仅撤新查询／展示／导航，所有真实资金和审计事实保留。

本轮已按本计划实现。原人工一／人工二验收库未重置；只在新独立合成库准备数据，供用户继续人工验收。
