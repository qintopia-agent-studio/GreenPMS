## 一、交付目标及停止线

交付一个前台可用的闭环：工作台异常能找到本门店历史未处理资金，显示具体金额和原因；点“处理”复用正确的现有入口；成功后根据真实资金事实更新待办；已确认客户留存转为正常留存记录，不继续报未处理异常。

**多余款项三个出口保持简单：退款、纠正真实错误、客户留存。** 尚未关联的先匹配，真实少收沿用现有待补收入口，不为了凑齐三个出口改错账。

本期不做已退房／已取消订单改价，不扩大管理员终态写权限，不新增独立台账／钱包／退款意向或审批状态机，也不实现无合法来源订单的退款／留存。少量无法在线更正的历史价格问题保留可见，另案核查。

本计划完成标准是“工程验证完成，可人工验收”，不是合并、发布或生产上线。已有资金功能的待验收状态不能由本计划或自动测试替代。

## 二、分层改动与复杂度

| 层级 | 拟改动 | 明确不改 |
|---|---|---|
| 数据查询 | 新增跨日期资金异常聚合，复用有效收退款／分配／留存数据，处理去重、分页、完整计数与证据异常 | 不重建资金余额、不回填收款、不新增可手工关闭的异常账本 |
| API／类型 | 新增只读查询契约，门店隔离、数据完整性及只读提示 | 不修改既有命令参数、权限模型及v1／事件默认契约 |
| 工作台 | 异常标签内增加资金分区，金额＋原因＋“处理”，独立加载与分页 | 不改变房态、入住退房及住宿日期筛选语义 |
| 操作衔接 | 处理面板导航到已有分配、收退款、留存及合法纠错入口；返回后重读待办 | 不复制一套资金写逻辑，不绕过Preview／Confirm或恢复机制 |
| 测试／验收 | 增加聚合、权限、失败、跨日、部分处理、桌面手机及现有链路回归 | 不改CI流程、不放宽测试入口、不重置用户正在操作的人工库 |

这是**以查询和前端衔接为主的中等规模增量**；涉及资金判定，按A 级验证，但范围明显小于新增“退房后金额更正”。默认无需业务表迁移；如确需性能索引，先以查询计划证明必要性，再做最小增量迁移。此处不虚估固定工期或承诺已经完成。

## 三、工作包与依赖

所有工作包初始状态均为“待开发”。

### W0：基线与验收准备

- 开始实现前核对Git分支、上游变化、其他任务写入范围和已有未提交文件；复用当前合适目录，不因新切片自动新建worktree。
- 对照已确认规格，固定计算口径、去重键、查询契约与不支持场景；不再重复设计台账或历史改价。
- 为新测试准备独立数据库和合成场景；不得重建、清空或复用正在进行人工验收的数据来跑破坏性fixture。
- 记录现有全量回归已知失败，不把它们自动归因于本轮，也不能据此跳过相关检查。
- 完成门槛：实现边界、独立测试目标和文件责任清楚，资金事实不被初始化脚本覆盖。

### W1：只读资金判定与查询

- 在`packages/db/src`新增聚合模块及就近单元测试，复用原资金有效性、分配余额和留存余额规则。
- 实现未分配收款、订单未处理多余款、成功退款待核对三类读取原因。
- 订单多余款扣除有效留存；真实退款／转出已在净收款里体现，不重复扣减。来源冻结与不完整证据不能按可用余额处理。
- 同一资金段不重复计数；跨日期读取、稳定游标、完整范围计数与列表一致性一并实现，不能先取第一页再在浏览器汇总。
- 校验原命令会产生的状态变更能令待办减少、消失或重新出现，而无需增加“标记处理完成”写接口。
- 完成门槛：规格状态表的金额推导和查询测试通过，真实来源可追溯；未做任何资金写规则扩展。

### W2：只读API与权限契约（依赖W1）

- 在`packages/contracts/src`、`apps/api/src`添加新DTO、schema和查询路由。
- 门店`READ`权限、分页、参数边界、未知金额、同步／读取异常及功能关闭后的历史读取行为都有明确契约。
- 状态显示不等于命令授权，写动作继续使用已有服务端校验。使用现有运行身份验证，不临时授予更宽数据库权限。
- 完成门槛：API／权限／运行身份测试通过，旧v1、现有外部流水接口与资金事件无非预期变化。

### W3：工作台资金分区（依赖W2；契约固定后可先做组件）

- 在`TodayPage`的异常标签内增加资金分区，保留原住宿异常内容。
- 新增查询客户端和展示组件，金额、原因、来源及“处理”在桌面和手机可读。
- 资金不随浏览日期被过滤；独立加载、错误、重试、分页和完整计数；加载失败不能显示已清零。
- 不新增独立台账页，不固定塞入三枚不适用的按钮，不把已留存款与未处理款混在一起。
- 完成门槛：组件及浏览器只读检查通过，历史页、手机布局和原有今日到店／在住／离店不回归。

### W4：处理入口与结果返回（依赖W2、W3）

- 匹配待办先选择合法目标订单，再进入原收款／分配流程；导航线索不能作为授权或自动提交的资金事实。
- 多余款根据来源、订单状态和权限，提供原退款、留存及适用的纠正入口。实际退款与留存退款不能走错资金预留通道。
- 已预订／已入住订单仍可按现有限制调整金额；终态金额错误明确说明不支持，不提供假按钮、不撤销退房绕行。
- 确认成功后重读订单及工作台；部分处理保留余款，失败／超时保留恢复入口；返回保留异常标签和筛选。
- 取消／退房结果可提示余款待办，但不能因资金余款额外阻止合法住宿操作。
- 完成门槛：原Preview／Confirm与幂等恢复未绕过，处理前后金额一致，不新增实际渠道调用或自动付款。

### W5：回归、评审和人工验收交付（依赖W1—W4）

- 执行下节测试矩阵，按实际风险补覆盖，不修改CI、全局测试范围或既有保护以换取绿色结果。
- 复核退款、留存、解除、再次使用及并发导致待办变化时，无重复计款、提前退出、漏历史事项或跨门店泄露。
- 对实现和规格做最终差异核查；记录当前未支持的历史改价／无订单处理边界，不宣称所有异常都能在线消除。
- 更新主验收计划为“已实现，待人工验收”，准备独立合成数据、可访问预览、截图和3组人工检查。用户原来正在操作的场景原样保留。
- 将可审阅变更交付到PR。远端CI、人工验收、合并和部署分别记录，不合并为一个“完成”。

依赖主线：**W0 → W1 → W2 → W3／W4 → W5**。契约确定前不并行发明不同金额口径。

## 四、并行开发约束（如使用子代理）

沿用用户当前允许的子代理模型配置，不自行替换；不为本计划强制创建子代理。

| 写入责任 | 独占范围 |
|---|---|
| 后端负责人 | 新DB查询及其就近单元测试、相关contracts和API；共享schema／服务注册文件只由该负责人改 |
| 前端负责人 | `apps/web/src`中的工作台、处理组件、客户端、样式和前端单元测试 |
| 回归负责人 | 新增`tests/integration`、`tests/contract`、`tests/e2e`中的本切片测试；不改生产实现或工作流 |
| 主负责人 | 文档、集成审查、验证记录与PR交付；需要修改他人范围时先结束该范围写入再接手 |

不同时改同一文件；上游或其他任务的改动必须保留。复杂度和高风险不构成自行增加模型或数量的理由。

## 五、自动验证矩阵

| 验证层 | 必须证明 |
|---|---|
| 金额／分类单元 | 未分配1000→600→0；B取消600；留存扣除；部分退款／部分留存；解除重现；原收款余额不回弹；异常链不伪报0 |
| DB聚合与边界 | 历史终态、超过一页、混合资金来源、关联去重、全范围计数、跨门店、留存与原流水交叉引用 |
| 冻结与并发 | 成功退款未归属的来源仍冻结；退款／留存／使用竞争后重查；重放不产生新的金额或重复待办 |
| API／权限 | READ只能读取授权门店；写权限独立；失效会话、无权限、功能关闭、未知参数、游标、金额范围、读取失败 |
| 原业务回归 | 现有资金分配、退款、留存、再使用、冲销与事件兼容；在住合法改价、终态改价继续拒绝；原工作台住宿分组 |
| 浏览器 | 桌面和手机：异常列表、处理往返、分页、保留筛选、局部失败与重试、部分处理、命令结果未知恢复 |

通用检查沿用项目入口：`npm run typecheck`、`npm test`、`npm run build`、`node --test scripts/check-pr-tests.mjs`。数据库集成／契约／E2E通过项目现有锁runner进入独立测试库，文件名及精确命令随实现落地记录；不能把默认`test:e2e`或重置脚本指向用户人工验收库。

对文档阶段只做链接、格式、来源与状态检查；不声称业务测试已覆盖尚未编写的实现。

## 六、人工验收及未完成事项

人工验收统一按主验收计划的新章节执行，不在本文维护第二套操作清单。三组检查覆盖：

1. **钱看得见**：未匹配、分次匹配、取消余款、历史订单、跨日期与分页。
2. **处理后正确退出**：退款、留存、部分处理、使用／解除和失败恢复。
3. **权限与不支持边界**：合法在住纠错、终态拒绝、正常待补收、冻结、只读、手机及原房态操作不受阻。

已退房金额更正登记在[延期清单](deferred-work.md)，不是本期验收阻塞；但上述明确不支持的案例必须可见、不能伪装成功。跨日期资金查询属于本期核心，不得延期换取界面先交付。
