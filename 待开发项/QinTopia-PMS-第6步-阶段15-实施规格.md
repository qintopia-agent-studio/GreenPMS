# 第 6 步：完整旅程回归与发布验收

## 目标

证明第 1 至第 5 步已经实现的计价、订单、库存、会员、资金、履约和房态能力可以在同一套 PostgreSQL 事实、命令、权限、审计和恢复协议上组合运行。阶段 15 不以“各阶段测试分别通过”为完成标准，而以完整经营旅程、数据库失败关闭、备份恢复和可运行发布资料共同通过为准。

用户最终集中人工验收前，阶段 15 只能推进到 `awaiting_user_acceptance`，不得标记 `accepted` 或 `done`。

## 四个小步骤

1. **旧断言批量收口与 E2E 分批**：先静态搜索已验收 UI 的旧标题、旧文案和旧交互定位，集中修正；然后把全部 E2E 文件固定分为互不重叠的 A/B 两批，本步不再启动全量首败扫描。
2. **关键浏览器 A 批与证据矩阵**：一次构建、一次数据准备，集中运行已修正的受影响文件、两条 Stage 15 金标旅程、命令恢复、渠道计价、超长住宿和最小响应式/无障碍冒烟。
3. **机器发布门禁**：单元、PostgreSQL 集成、Contract、计价、权限、并发、迁移、readiness、备份恢复、冷启动和 Compose 每类只做一次最终运行；失败时只重跑受影响类别。
4. **剩余浏览器 B 批、发布资料与集中人工抽查**：代码稳定后只运行不含 A 批文件的剩余 E2E；A/B 结果合并为完整浏览器证据。用户只查看四个主入口和两条预置旅程的最终经营结果，不重做 4.1 至 4.7 及第 5 步已通过的逐项操作。

## 省时与上下文约束

- 全量 E2E 不用作日常诊断工具。开发循环先用静态搜索收口，再把所有 E2E 显式分为互斥且完备的 A/B 两批；除失败重试或产品代码变更使证据失效外，每个已通过文件只运行一次。
- 只修正文案、locator、等待时间等测试代码时，只重跑该 E2E 文件；修改共享测试帮助函数时，重跑使用该帮助函数的组。
- 修改业务代码、数据库边界、公共 API、命令外壳或共享页面状态时，才扩大到对应集成/Contract/E2E 组。A 批通过后若产品代码发生变化，只使受该边界影响的已通过文件失效，不无条件重跑整批。
- A/B 任一批若只暴露旧测试断言，修正后重跑失败文件并与已通过部分合并为最终证据；若暴露真实产品缺陷，修复后按受影响边界扩大回归。
- A/B 证据必须覆盖运行时存在的全部 E2E 文件，记录各自的明确文件清单和同一产品代码快照；不得通过遗漏文件来减少数量。
- 成功运行只记录命令、通过数、耗时和日期；不把完整成功日志带入对话。失败时只读首个有效错误、相关 `error-context` 和 trace。
- PostgreSQL 共享测试锁要求相关套件串行；不共享数据库或端口的构建、静态检查和独立基础设施检查可在不争用资源时并行。
- 人工验收服务 `http://127.0.0.1:4196` 不受自动化影响；E2E 固定使用 API `4101` 和 Web `4174`。
- 每次进度汇报必须使用“大步骤 6 / 第 N 小步骤”。第 1 小步骤完成后建议用 `Continue in new chat` 携带精简交接摘要，不携带完整测试日志。

## 已冻结的业务边界

1. Web、外围 Token 客户端和测试工具只能调用同一套 Quote、Preview/Confirm、幂等、事务和审计能力，不新增第二条业务写路径。
2. 普通住宿资金继续遵守 4.6：企业微信/银行转账记录交易号，现金记录必填收款人，其他记录必填说明；退款逐笔引用原收款，企业微信原路退回。
3. 住宿升级会员继续遵守 4.7：同住客、匹配产品、有效企业微信住宿收款整笔转入、差额新交易号、原子生效与专用权益核销；不扩展为通用跨订单分摊。
4. 外部渠道订单不登记单笔住宿收退款；渠道订单号和当前应结金额保留为后续财务滚动核对依据。
5. 超长住宿允许 30 夜以上至 366 夜，房态只展示连续 30 夜，但 Quote、确认和库存冲突必须校验完整区间。
6. 清洁工作流、内部占用、会员合同退费、微信接口、自动退款和财务对账不在当前发布门禁内。
7. 手机端经营流程不在本阶段重新设计；保留既有 320/375px、平板、200% 缩放和覆盖式抽屉自动门禁，集中移动端 UI 优化按用户要求后置。

## 核心发布不变量

### 命令与事务

- Confirm 只能使用当前、未过期且 effect hash 一致的 Preview；陈旧或冲突结果必须零业务写入。
- 同一幂等键只允许同一请求重放；换 payload 必须稳定拒绝。
- 网络中断后只查询原确认键，不能生成新确认键盲目重试。
- 未决命令恢复记录由账号与物业作用域共同隔离，并以浏览器共享存储协调同一浏览器的多个标签页；任一标签页存在未收口命令时，其他标签页的同物业写入口必须同步暂停。
- 损坏的本地恢复记录按账号和物业隔离，写入口保持暂停；工作人员必须先核对服务端业务记录，再通过受控确认清除本物业记录。
- 数据库约束必须覆盖直接 PostgreSQL 写入，不能只依赖应用服务校验。

### 住宿升级会员

- 非 `APPLIED` 的 `CONVERT_STAY_COLLECTIONS_TO_MEMBERSHIP` 命令只允许零业务事实。
- `EXECUTING` 或 `REJECTED` 命令不能挂载 amendment、会员订单、会员资金、转入桥、住宿资金或权益事实。
- 已成功转换的会员订单只能由原转换命令在同一事务补齐资金；其他未完成命令不能绕过资金关闭。
- 以上加固通过新迁移 `035_stage13_conversion_execution_state_guards.sql` 实现，不改写已经执行的 033/034。

### 发布环境

- 普通生产构建不预填账号或密码，也不公开演示密码；只有明确的开发环境或 `VITE_DEMO_LOGIN=true` 验收构建显示演示账号。
- 普通生产构建默认不发布可下载源映射。
- readiness 必须精确验证 001 至 035 的迁移清单、关键函数、约束、索引、触发器绑定和函数体标记；未知未来迁移失败关闭。
- 恢复目标必须是新数据库；恢复脚本不得删除或覆盖已存在目标。恢复、迁移或 readiness 任一步失败时保留本次创建的目标供人工核对，绝不自动删除同名数据库。

## 完整经营旅程证据

### 普通企业微信住宿

同一订单必须串联：查询可售、自动报价、创建订单、分次收款、入住、续住、换房、缩短并重计价、逐笔引用原收款退款、退房。浏览器断言工作人员文案和关键页面状态，数据库断言 amendment、pricing revision、资金引用、库存释放和最终状态。

### 升级会员

从已退房普通住宿进入“升级会员”，完成表单、业务核对、确认、订单重载、住宿金额归零、原收款转入标记、7 夜专用核销、23 夜剩余权益、会员详情双向追溯，以及退款和二次升级禁用。

### 既有组合旅程

- 免费入住：建单、入住、日期/房源变更、退房和零金额事实。
- 会员购买与入住：建档、会员订单、多笔收款、显式生效、30 夜发放、冻结、入住核销和余额。
- 维修锁房：设置、房床互斥、释放。
- 外围智能体：受限 Token 查询、写入授权、Preview/Confirm、幂等重放、中断恢复和跨物业隔离。
- 房态：30 夜跨月、全物业余量、楼栋/房间/床位、超长住宿第 30 夜以后冲突、抽屉和页面滚动隔离。

## 自动化门禁

第 1 小步骤先收口已验收 UI 与旧断言的静态偏差，并固定 A/B 两批明确文件清单；第 2 小步骤运行 A 批，证明两条 Stage 15 金标旅程和共享交互边界。两步都禁止通过降低业务断言、删除测试或把 UI 改回旧版来取得通过。

第 3 小步骤在代码稳定后执行以下机器门禁，每类只做一次最终运行，不能沿用该类最后一次产品代码改动之前的结果：

```bash
npm run verify
npm run test:integration
npm run test:contract
npm run test:pricing-facts
npm run db:ready
npm run verify:restore
npm run verify:cold-start
npm run verify:compose
npm audit --offline --omit=dev
git diff --check
```

其中 `npm run test:contract` 已包含普通生产 Web 构建，不再单独重复执行 `npm run build`；E2E 仍使用自己的验收构建。

第 2 和第 4 小步骤分别对明确、互不重叠的 A/B 文件清单执行同样的受控 E2E 命令。下面只是命令模板；实际执行时必须把占位符替换成经核对的显式 spec 路径，不得将占位符原样交给 shell：

```bash
E2E_API_PORT=4101 E2E_WEB_PORT=4174 npm run test:e2e -- <本批明确文件清单> --reporter=dot
```

每批各做一次构建和数据准备。A/B 合集必须等于当前全部 E2E 文件，交集必须为空；通过数与 Playwright `--list` 清单核对后才能作为完整浏览器门禁。

## 集中人工验收

自动门禁全部通过后，只要求用户做约 10 至 15 分钟的发布级抽查，不重复此前已经逐项通过的 4.1 至 4.7 和第 5 步清单：

1. 使用最终运行地址登录，查看房态、今日履约、订单、会员四个主入口可正常载入。
2. 抽查一条普通住宿完整旅程结果：最终已退房、资金净额和逐笔退款引用正确、房态已释放。
3. 抽查一条升级会员结果：住宿金额 0、原住宿收款可追溯、会员剩余 23 夜、订单与会员可双向跳转、不能再次升级或退款。
4. 查看一页机器证据摘要：外围 Token、数据库不变量、备份恢复、冷启动、Compose 和 A/B 完整 E2E 只展示结论、通过数和耗时，不要求用户阅读原始日志。
5. 确认没有阻断发布的中文文案、权限、恢复或页面可用性问题后，明确回复“第 6 步通过”。权限、并发、网络中断、损坏恢复记录和备份恢复由机器证明，不要求用户手工制造。

## 最终边界审计收口（2026-08-03）

第 4 小步骤完成 B 批前，最终独立审计发现以下五项发布阻断；它们属于本阶段已经冻结的命令恢复、数据库直接写入、readiness 和恢复安全边界，不扩展业务范围：

1. 未决报价恢复必须与普通命令恢复一样，按账号和物业跨标签同步暂停其他写入口，并在 Preview 前失败关闭。
2. 房态存在未收口报价恢复时，恢复入口必须独立于当前订单选择保持可达，不能被订单上下文永久遮住。
3. readiness 必须精确校验会员资金事实 append-only、已生效会员订单身份不可变的函数体和触发器绑定；删除、禁用或错绑均返回未就绪。
4. 住宿升级会员有差额时，转换命令只能拥有一笔 `DIRECT_WECOM` 会员收款；无差额时必须为零笔，并且金额、币种和交易单号必须与 amendment 中已经核对的 `remainingPayment` 完全一致。
5. 恢复库的 `schema_migrations` 必须严格等于当前迁移清单的一个连续前缀；任何中间缺项、顺序异常或未知未来迁移都必须在升级前失败关闭并保留目标库供人工核对。

自动检查只重跑受这些代码修改影响的单元、集成、Contract、readiness、恢复和命令恢复 E2E；此前未受影响且已经通过的门禁证据继续有效。五项全部通过后，才可把阶段状态推进到 `awaiting_user_acceptance`。
