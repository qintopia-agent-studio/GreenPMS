# 运营主管受控纠错与房态异常修复

## 1. 目标与权威边界

本轮交付五个检查点，其中 9.3 至 9.5 是一个连续开发发布组：

1. 计划退房日仍在住时保留库存安全阻断，但房态显示原订单日期和“待退房”；计划退房日以后仍在住时显示原历史区间和“未退”，不阻断今天及未来库存。
2. 建立物业内、主体级、精确到命令的运营主管权限；不新增万能管理员、SQL 入口或任意事实修改能力。
3. 为未来可重复出现的操作错误提供已完成历史住宿日期/房源整组纠正；保持订单身份、住宿人、价格、资金和终态不变。
4. 为未来可重复出现的会员录入错误提供三类受控纠正：会员档案字段纠正、既有会员链真实生效日纠正、尚无有效会员链时的历史办卡补录。主管只输入可核验的源事实，合同日期、权益批次和日期派生状态由系统整体计算。
5. 为错误且权益完全未使用的会员链提供原子作废重建：保留会员档案，按真实历史住宿和真实收款重建正确链；错误金额不得硬编码，真实退款、跨会员身份或不满足资格的已使用权益必须失败关闭。

人工验收步骤和完成状态以 `QinTopia-PMS-分步开发与人工验收计划.md` 第 9 步为准。本规格定义字段、状态机、命令、事务、并发、权限和自动测试规则。既有 4.1、4.7、8.5、8.6 规则继续有效；冲突时以本规格对上述五项的更窄规则为准。

隔离验收库可以使用“鹏哥/小尚”“Cathy/晶晶”等同名合成夹具和 CNY 936.00 代表金额，但这些名称、金额和生产记录都不是业务键、资格条件或硬编码。本规格不预设生产订单、会员、合同、收款或权益 ID。主管必须从受权限约束的页面选择记录；Preview 与 Confirm 由服务端按本规格重新验证全部身份、版本、日期、权益和资金图。只读生产快照已确认三组真人记录均不满足相应永久命令资格，后续只能在补齐权威事实后由固定目标的一次性过渡程序处理。

## 2. 基线与现有能力结论

- 9.1/9.2 已完成人工验收并在本地 `main` 提交为 `e257994`；`origin/main` 与生产版本仍为 `2f1b52fa6e70965f24f2575ab9514248fef28c14`。该提交尚未推送或部署，生产管理员映射仍须在部署前核实。
- 现有房态在计划退房日为 `CHECKED_IN / IN_HOUSE` 的订单生成一段 `[businessDate, businessDate + 1)` 合成阻断，同时把该合成边界暴露成 `sourceStartDate/sourceEndDate`。Web 由此把安全阻断误识别为今天至明天的普通订单。
- 现有库存层通过退房日 Stay blocker 在 Quote、Preview、Confirm 阶段失败关闭同房/同床冲突；该安全守卫不得删除或放宽。
- 现有 `COMPLETE_STAY` 只适合把特定错误预订原子完成为历史住宿，不支持已经 `CHECKED_OUT / COMPLETED` 的安排日期纠正。
- 现有会员订单只有 `DRAFT / ACTIVE`，合同只有 `ACTIVE / EXPIRED`，没有可表达“错误办卡已作废”的终态；在住升级是正向原子转换，没有逆转换命令。
- 现有 `READ / WRITE` 是物业级粗门禁，`WRITE` 可进入全部写命令；不能区分普通员工、管理员和只供系统派生的命令，也不能在撤权后统一阻断历史恢复与幂等重放。

## 3. 全局不变量

### 3.1 追加式事实与单命令原子性

- 不删除订单、Stay、会员、合同、权益、资金、命令、Receipt、Audit 或历史修订。
- 不覆盖原订单日期、原会员资料值、原合同日期、原会员收款或原权益流水；状态终结和当前投影只能由受控命令及其追加事实产生。
- 每次纠错只能通过一个类型明确的 Preview/Confirm 命令完成；Confirm 在一个 PostgreSQL 事务中成功或全部回滚。
- Preview 固化资源版本、相关事实集合哈希、权限快照所需标识和系统推导结果；Confirm 在锁后重建效果，任一变化返回 `PREVIEW_STALE`。
- 幂等重放只能返回同一主体、同一物业、同一命令类型、同一规范化请求的原结果；并发 Confirm 最多产生一组业务事实和一个最终 Receipt。

### 3.2 禁止能力

- 不提供 SQL 控制台、数据库凭证、表格字段编辑器、任意 JSON Patch、任意 `UPDATE/DELETE`、任意事实 ID 冲销或万能 `ADMIN`。
- 普通员工继续可以使用已经存在且受命令协议、事务和审计约束的重价、冲销、退款、会员收款纠错、撤销入住和权益余额纠正；本轮不因新增管理员而收窄一线现有业务能力。
- 上述单项命令不得被客户端拼装成本轮历史纠错。每类错误只能进入本规格对应的 typed 命令；服务端按命令自身资格在一个事务中校验和写入完整结果。
- 错误记账冲销不是实际退款。任何金额若曾真实收取且现在需要退回，必须停止纠错命令并走另行确认的真实会员退款流程；金额是否为 CNY 936.00 不影响该边界。

### 3.3 用户界面

- 所有危险操作先显示中文只读 Preview，明确列出原事实、拟追加事实、保持不变项和失败关闭原因。
- 页面不得暴露内部协议名、数据库表名、SQL、内部 ID 或可编辑的派生字段。
- 会员页提供一个“修改会员记录”入口，再按资料、生效日、历史补录或错误链重建进入相应受控流程；不提供散落的合同、资金、状态或权益字段编辑入口。用户界面统一使用“修改会员资料”“修改会员生效日”等运营语言，不显示“纠正”“纠错类型”、内部命令名或数据库术语；技术命令名与追加式纠错事实名称保持不变，以维持契约和审计稳定。
- 自动刷新沿用上一轮刘珊反馈的结论：数据过期时保留当前真实上下文和草稿，只暂停写入并静默刷新；不得重载未变化页面、丢失焦点/选区或反复闪烁禁用。

### 3.4 永久能力与一次性过渡程序

- 管理员页面只承载未来仍可能重复发生、资格可以稳定表达的错误类型。同名隔离合成夹具用于证明通用状态机，不为 108、Cathy、晶晶真人或固定金额增加分支，也不承诺永久命令能直接处理其当前生产记录。
- 只属于本次系统切换、且无法满足通用命令资格的少量异常，不扩宽管理员权限。它们进入版本化的一次性过渡程序：只读 dry-run、固定目标清单与输入哈希、生产快照核对、幂等执行、单事务或明确的纠正集合原子性、完整 Audit/Receipt，失败全部回滚。
- 一次性程序不得是临时 SQL，不进入管理员页面，不复用数据库超级权限，不直接覆盖历史。正式执行前必须针对当时生产事实重新 Preview 并取得人工批准；本地快照不能证明生产实时状态。
- 原始生产快照只作为不可写证据库保留。任何可写演练副本在启动 API 前必须清除或失效生产 Web 会话、API Token 和密码凭据，再创建隔离身份；最终人工验收使用从空库重置的合成数据库，不连接原始或升级验证快照。
- 通用命令发现真实收退款、已使用权益与新有效期不兼容、跨会员身份/需合并会员、事实缺失或不可唯一推导时一律失败关闭。只有经单独规格和代码审查的一次性过渡程序可以评估其中确属切换期的数据异常。

## 4. 检查点 9.1：计划退房日“待退房”与逾期“未退”

### 4.1 冻结语义

住宿安排仍采用半开区间 `[arrivalDate, departureDate)`。计划退房日不是新增住宿一晚。

| 服务端事实 | 房态显示 | 原订单日期 | 今天库存 | 今天以后库存 |
|---|---|---|---|---|
| `CHECKED_IN / IN_HOUSE` 且 `departureDate = businessDate` | `在住` + `待退房` | 必须显示原 `arrivalDate -> departureDate` | 继续阻断 | 按原安排不自动延长 |
| `CHECKED_IN / IN_HOUSE` 且 `departureDate < businessDate` | 原历史区间 + `未退` | 必须显示原 `arrivalDate -> departureDate` | 不阻断 | 不阻断 |

正式新增：

- `RoomStatusOperationalAttention = DUE_OUT`，中文为“待退房”。
- `RoomStatusBlockingFactKind = DUE_OUT`，只表示计划退房日尚未完成退房的库存安全事实，不是 Claim，也不是新增住宿区间。
- `RoomStatusIntervalDto.orderDepartureDate`，与已有 `orderArrivalDate` 配对。所有订单身份、打开订单、返回房态和页面日期文案使用原订单日期字段；不得从合成阻断边界推断订单日期。

计划退房日的合成事件可以继续作为单日安全投影存在，但必须满足：

- 携带 `DUE_OUT`，冲突类型为 `DUE_OUT`，并引用唯一 Order、Stay 和实际库存单元；
- 不进入普通订单候选、普通住宿来源卡片或普通订单区间日期文案；
- 保留“打开订单”和“办理退房”旅程；桌面、手机、Tooltip、无障碍名称和返回锚点均显示真实订单日期与“待退房”；
- 整房阻断整房；床位阻断同床位以及现有整房/床位互斥范围，不改变兄弟床位现有可售语义。

逾期“未退”继续沿用 `OVERDUE_IN_HOUSE`：只投影原历史区间和异常任务，不生成今天至明天区间、不生成当前 Claim、不阻断当前或未来。

### 4.2 库存与并发

- 保留 `loadDepartureDayStayBlockers`、Quote fingerprint、Preview fingerprint、Confirm 锁后效果重建和 `assertUnitAvailable`。
- 补充创建订单与退房并发测试。退房先线性化完成时，新建可继续；新建在退房提交前观察到仍在住事实时必须以 `PREVIEW_STALE` 或 `INVENTORY_CONFLICT` 失败且零业务写入。
- 补充营业日切换前后 Quote/Preview/Confirm 陈旧竞态，不允许昨天的“未退”或今天的“待退房”结果跨日误用。

## 5. 检查点 9.2：运营主管命令级权限

### 5.1 授权模型

保留 `READ / WRITE` 作为物业级粗门禁，新增主体命令授权和 Token 命令上限。运行时有效写能力为：

`主体有效 ∩ 物业 WRITE ∩ 主体 exact command grant ∩ Token exact command ceiling ∩ 发布特性开关`

- 命令授权只允许规范化后精确匹配；无通配符、前缀、命令组推断或 `ADMIN`。
- 主体 command grants 按物业分别存储和投影；多物业主体不得把一个物业的命令能力带到另一个物业。
- 角色模板只用于受控配置一组 exact grants，运行时不因角色名自动放权。
- 本系统只设普通员工和管理员两个工作人员层级。本规格中的“运营主管”即新增管理员，不再引入审批员、财务员、超级管理员或其他中间层级。
- 普通员工以信任和可审计为原则，保留当前工作人员页面已经交付的受控业务动作；迁移不得把当前合法业务旅程意外关闭，也不得继续让 `WRITE` 隐式代表全部写命令。
- 普通员工 exact grants 冻结为：
  - 会员：`CREATE_MEMBER`、`CREATE_MEMBERSHIP_ORDER`、`RECORD_MEMBERSHIP_PAYMENT`、`CORRECT_MEMBERSHIP_PAYMENT`、`ACTIVATE_MEMBERSHIP_ORDER`、`CORRECT_MEMBER_ENTITLEMENT_BALANCE`；
  - 订单与履约：`CREATE_ORDER`、`RESCHEDULE_STAY`、`EXTEND_STAY`、`SHORTEN_STAY`、`MOVE_UNIT`、`REPRICE_ORDER`、`CANCEL_ORDER`、`MARK_NO_SHOW`、`REVOKE_CHECK_IN`、`CHECK_IN`、`CHECK_OUT`、`COMPLETE_STAY`；
  - 库存与资金：`LOCK_MAINTENANCE`、`RELEASE_MAINTENANCE`、`RECORD_COLLECTION`、`RECORD_REFUND`、`REVERSE_FACT`、`CONVERT_STAY_COLLECTIONS_TO_MEMBERSHIP`。
- 管理员继承上述普通员工 exact grants，并额外获得：
  - 系统管理：`ISSUE_TOKEN`、`ROTATE_TOKEN`、`REVOKE_TOKEN`、`COMPLETE_CLEANING`；`COMPLETE_CLEANING` 在清洁特性开关关闭时仍不可执行；
  - 专用纠错：已交付的 `CORRECT_ORDER_OCCUPANT`，以及随 9.3 至 9.5 实现的 `CORRECT_HISTORICAL_STAY_ARRANGEMENTS`、`CORRECT_MEMBER_PROFILE`、`CORRECT_MEMBERSHIP_EFFECTIVE_DATE`、`BACKFILL_HISTORICAL_MEMBERSHIP`、`VOID_ERRONEOUS_MEMBERSHIP_AND_RECONVERT_STAY`。未来命令只有在契约、状态机和特性开关同时交付后才成为有效能力；9.2 不提前授予未知或未实现命令。
- `REFRESH_MEMBER_COVERAGE`、`ADD_MEMBER_ENTITLEMENT_LOT`、`ADJUST_MEMBER_ENTITLEMENT`、`EXPIRE_MEMBER_ENTITLEMENT` 没有工作人员直接入口，只允许作为受控命令内部派生效果，不授予任何人工主体。`PLACE_INTERNAL_USE`、`RELEASE_INTERNAL_USE`、`BACKFILL_COMPLETED_STAY` 保持不可新执行的历史兼容类型。
- `CREATE_QUOTE` 是不写经营事实的价格试算，继续由物业 `READ` 门禁控制，不纳入写命令 profile，也不得据此获得 Confirm 能力。
- 权限授予/撤销不提供给普通员工或管理员。初始人员映射通过代码审查的部署配置和受控迁移完成，不接受手工 SQL；通用权限管理 UI 不在本轮。

### 5.2 执行与恢复

- 同一授权器覆盖 Preview、Confirm、stored Preview、历史 Preview 回放、Command/Receipt/结果读取、find、resolve 和恢复。
- Confirm/resolve 在事务内锁定并重新验证主体、物业 grant、command grant 和 Token/session；必须先鉴权再返回幂等 replay。
- 授权撤销和 Confirm 以锁顺序确定线性化结果：撤销先完成则旧 Preview 不得执行；Confirm 先完成则该一次命令有效，后续读取仍按当前权限重验。
- Token 的命令上限必须是调用者当前有效命令集合的子集，不得扩大物业、WRITE、命令范围或有效期。
- Token 管理由管理员执行。管理员只能管理同物业内有效主体的 Token；签发或轮换后的 command ceiling 必须同时是管理员当前有效能力、目标主体同物业 grants 和调用 Token 自身 ceiling 的子集，且不得超过调用 Token 的有效期。跨物业目标按不存在处理。
- `/me`、房态、订单、会员和恢复页面只渲染服务端返回的 allowed actions；Web 不得从 `WRITE` 自行推导按钮。

### 5.3 拒绝、审计和数据库角色

- 跨主体/跨物业资源返回 `404` 防枚举；同物业缺命令能力返回 `403`。
- 鉴权拒绝不得写 Preview、command execution、Receipt、业务事实或幂等键；只允许在独立事务追加脱敏安全审计。
- 审计包含物业、主体、命令类型、阶段、拒绝原因、凭证种类/fingerprint、correlation ID 和幂等键哈希；不记录 Token 明文或个人敏感字段。
- migration owner 与 API runtime 数据库角色分离。runtime role 禁止 schema/role/trigger DDL、`DISABLE TRIGGER`，并对 append-only/protected facts 撤销 `UPDATE/DELETE`；应用所需状态迁移只能通过最小表/列 DML 和数据库守卫完成。

## 6. 检查点 9.3：已完成历史住宿安排整组纠正

新增唯一命令 `CORRECT_HISTORICAL_STAY_ARRANGEMENTS`。不复用 `COMPLETE_STAY`、`RESCHEDULE_STAY`、重价或退款命令。

### 6.1 v1 资格与状态机

- 输入为同物业 `correctionSet`，至少一项，每个 `orderId` 唯一；任何需要交换或联动的记录必须在同一集合中一次确认。隔离验收库可以使用“鹏哥/小尚”同名合成的两笔已完成订单验证整组交换，但生产快照中的 108 是一笔仍在住的合并住宿，不满足本命令资格，不得作为可执行样例或据此放宽门禁。
- 每项旧状态必须严格为 `order = CHECKED_OUT`、`stay = COMPLETED`，并携带当前 `expectedVersion`。
- v1 只纠正最终有效历史住宿安排的日期和/或库存单元；不改 Order/Stay ID、住宿人、会员、来源、渠道号、价格、收退款、结算结果或生命周期终态。
- 新日期必须形成非空半开区间，至少一个受控字段变化；目标房/床必须与原订单销售 kind 和计价产品适配。
- 若真实记录不是上述终态、需要改住宿人归属、需要按新日期重价或需要改变资金，必须失败关闭并另立状态机，不扩宽本命令。

### 6.2 原子性与投影

- 按 Order、Stay、房间、服务日稳定排序锁定整组订单、当前安排修订、segments、历史占用证据、相关会员覆盖/权益和资金基线。
- 先从全部输入计算“整组最终状态”，再校验历史占用；相互交换不因逐单中间态产生假冲突，集合外冲突必须整体拒绝。
- 每个订单追加一条 typed `CORRECT_HISTORICAL_STAY_ARRANGEMENT` amendment 及新 revision/segment；旧 amendment/revision/segment 保留。
- 约束触发器在事务末验证每个输入恰好一条纠正 amendment、before/after 与 expectedVersion 一致、终态/身份/资金不漂移、整组最终安排无冲突。
- Receipt 按订单列出 before/after 日期与房源、新 amendment/revision/segment ID，并显示未变化的住宿人、金额和收款摘要。

## 7. 检查点 9.4/9.5：可复用会员受控纠错

会员页通过一个受控入口分流到四条 typed 命令。四条命令解决不同事实错误，不得由客户端拼成通用编辑器，也不得互相绕过资格条件。

### 7.1 共同输入与边界

- 主管只能选择同物业现有会员及相关事实，填写真实业务日期、必填原因和证据说明；服务端固化 `expectedVersion` 与会员、订单、合同、权益、资金、住宿关联集合哈希。
- `actualMembershipDate` 表示会员开始日期，不是收款日期、录入时间或修改提交时间；合同和权益从该日期开始计算。
- `payment.businessDate` 与 `replacementDirectPayment.businessDate` 表示企业微信账单显示的实际收款日期，只记录物业当地自然日，不接受小时、分钟、秒或时区。收款日期只用于资金核对，不参与合同或权益日期计算，与会员开始日期无需相同，也没有先后顺序限制；二者均不得晚于物业营业日。
- 所有新事实的 `createdAt/recordedAt` 使用服务端当前精确时间，只用于审计并禁止客户端输入或伪造。后续普通收款、补款、收款更正或冲销不得改变会员开始日期。
- Preview 必须区分主管输入的源事实、系统推导字段、拟追加事实和保持不变项。API 不接受合同截止日、权益余额、派生状态、冲销金额或目标数据库字段。
- 会员 ID、物业、订单归属和自然人身份不得通过这些命令改变。手机号指向其他会员、源住宿属于其他会员、需要会员合并或跨会员搬迁事实时失败关闭。

### 7.2 会员档案常见录入纠正

新增 `CORRECT_MEMBER_PROFILE`：

- v1 字段白名单为 `fullName`、`nickname`、`identityCardNumber`、`phone`、`wechat`；沿用建档时的规范化、必填/选填、长度和格式规则，至少一项实际变化。
- `phone` 继续是全局唯一业务键。事务内锁定目标会员及规范化手机号唯一性范围；手机号已属于另一会员时明确失败且零写入，不自动合并、覆盖或迁移两位会员的订单、合同、权益和住宿。
- 追加 typed 资料修订和 before/after 审计，再更新当前资料投影；原资料值与历史订单住宿人快照继续可追溯，不隐式改写历史住宿人或交易事实。
- Receipt 显示修改字段、修改前后值、原因、证据、操作人和时间，不显示被遮蔽的敏感字段全文。

### 7.3 既有会员链真实生效日纠正

新增 `CORRECT_MEMBERSHIP_EFFECTIVE_DATE`：

- 目标必须是同一会员的一组精确互链、尚未作废的 membership order、contract 和 entitlement lot；只允许输入新的 `actualMembershipDate`、原因和证据。
- 系统以产品既有期限规则重算 `validFrom`、`validUntil` 和 Lot 日期，并在 Preview 展示完整 before/after。原日期通过追加 amendment 保留，不直接覆盖历史。
- 已经使用权益并不一律拒绝。只有所有 coverage 与带服务日的 ledger 使用事实都能唯一归属，且每个服务日仍落在新的有效期内时才允许；缺少服务日、落在新有效期外或关联不完整时失败关闭。
- v1 只纠正纠正前真实有效且纠正后仍应有效的 `ACTIVE` 链：物业营业日必须同时位于旧、新订单/合同/Lot 有效区间内，Lot 不得已有 `EXPIRE` 事实。仅有 `ACTIVE` 状态但旧日期已经过期的脏链不得借日期纠正恢复权益；若新日期会使链过期、需要新增/撤销到期扣减、恢复权益或改变任何合同/权益状态，命令失败关闭并转一次性过渡程序或未来专用生命周期命令。
- 会员与订单身份、订单/合同生命周期、产品、成交价、资金、总权益、已用数量、可用余额和 ledger 事实必须保持不变。管理员不能借改日期补钱、换产品、改余额或重开已作废链。

### 7.4 尚无有效链时的历史办卡补录

新增 `BACKFILL_HISTORICAL_MEMBERSHIP`：

- 适用于会员档案已存在、但目标会员/物业尚无可代表该次真实购买的非作废会员链；资格检查必须同时覆盖当前 membership order 以及切换期可能存在的 `membership_order_id IS NULL` legacy `ACTIVE` contract/Lot，任何一种有效链已存在、重复外部交易引用或事实无法唯一归属时都必须拒绝。
- 主管选择会员与产品，分别填写会员开始日期、企业微信收款日期、真实收款金额、交易引用、原因和证据，并核对系统固定显示的收款渠道“企业微信”；不输入或选择成交价。沿用已确认的“会员费只支持企业微信”业务边界，不扩展现金、银行转账等会员费渠道。收款是本次新增的源事实，不得借此修改或冲销任何既有资金事实。
- 会员开始日期和企业微信收款日期均不得晚于物业营业日，且不要求相等或满足固定先后顺序。历史链是否仍可补录只由会员开始日期推导的合同有效期判断，收款日期不得改变合同、Lot 或权益日期。
- 系统复用当前会员产品、收款和激活规则，在一个事务中创建 membership order、真实 COLLECTION、contract 和 entitlement lot；订单标价和成交价都固定为所选已发布产品的当前标价，`price_adjustment_minor = 0` 且 `price_adjustment_reason = NULL`，合同期限、Lot 数量和余额全部由系统计算。真实 COLLECTION 金额是独立源事实，只要为正数即可少于或多于成交价；系统仅显示收款差额，不阻止明确生效、不推断结清，也绝不据此自动改价。
- Preview 必须冻结所选产品 ID、版本、成交价、币种、期限规则、权益类型/数量和适用范围；纠错根事实保存并逐项约束这些快照，数据库不得接受“整套换成另一个已发布产品但内部自洽”的替换图。
- v1 只补录截至物业营业日仍在有效期内的会员链。真实购买已经过期时，需要同时表达合同过期和权益到期扣减，不属于“晚录办卡”的最小状态机，转一次性过渡程序。
- order、contract、lot、COLLECTION 和 Audit 的 `recordedAt` 均为当前服务端时间；会员开始日期和企业微信收款日期保存为两个独立的自然日事实。历史补录不得伪装成当时已经在系统录入。
- 真实退款、跨会员收款、缺失或冲突交易证据、需要追溯改写既有住宿/权益时失败关闭；历史折扣价、特批成交价等不等于产品标价的切换期异常也不扩大永久管理员的改价权限，统一转版本化一次性过渡程序。

### 7.5 错误且未使用会员链的原子作废重建

保留复合命令 `VOID_ERRONEOUS_MEMBERSHIP_AND_RECONVERT_STAY`，但不绑定真人或固定金额：

- 旧链必须是同一会员、同一物业精确互链的直接办卡，且权益完全未使用：不存在 coverage 或任何 ledger 事实，可用余额等于产品总权益，不存在住宿转换 bridge。仅凭余额看似完整不能放行。
- 系统自动选取旧订单全部未冲销直接会员收款；旧金额可以是任意合法金额，不得硬编码 CNY 936.00，也不允许主管挑选部分事实或输入冲销金额。
- 源住宿必须与该会员、物业和产品身份一致，严格为 `CHECKED_OUT / COMPLETED` 的普通 WECOM 住宿，尚未转换，资金图完整且可唯一推导；所有历史服务日必须落在系统根据 `actualMembershipDate` 计算的新有效期内。
- 主管只选择旧会员订单、源历史住宿，填写会员开始日期、原因和证据；存在真实直接差额收款时，另填写企业微信收款日期和交易引用。系统推导旧收款逐笔冲销、住宿净收款转入、新会员成交价、直接会员差额、新合同期限、产品总权益、历史住宿逐日核销和剩余权益。
- 旧会员订单上的直接收款属于本次要归零的错误记账，只逐笔追加 `REVERSAL`，不得把旧错误金额重新计入新会员链。新链的直接会员差额严格等于 `新会员成交价 - 住宿净收款转入`；差额大于零时主管只补充真实差额收款日期和交易引用，金额仍由系统计算，差额为零时禁止新增直接收款。新链净收款必须严格等于成交价。
- 若外部证据表示实际收款需要退回，或真实直接会员收款与系统推导差额不一致，命令拒绝；不能把真实退款伪装成冲销，也不能输入金额凑平。隔离验收库可以用“Cathy/晶晶”同名合成记录和 CNY 936.00 作为不同金额场景中的代表样例；生产快照中的真人记录因身份或来源住宿事实不足，不满足本命令资格，不得作为管理员页面可直接处理的承诺。
- 源住宿只允许从未出现退款、退款冲销或其他非 `COLLECTION` 资金事实；“退款后又冲销退款、当前净额看似恢复”仍属于发生过真实退款的链，必须拒绝。差额收款日期与交易引用必须保存到纠错根事实，并与 Preview、资金事实逐值一致；换成另一个未使用交易号或另一收款日期仍应使旧 Preview 失效。
- 同一事务追加旧收款 REVERSAL；将旧 order/contract/lot 终结为 `VOIDED` 并追加 `VOID` 权益事实；保留会员档案；创建新 order/contract/lot；复用住宿正向转换资金图；按历史服务日追加 `CONVERSION_CONSUME`；最后写 Audit 和 Receipt。任一写点失败全部回滚。

### 7.6 锁、约束与结果

- 四条命令以及普通会员激活先按稳定顺序锁定会员/规范化手机号和实际涉及的订单、合同、Lot、住宿、资金、服务日；需要新增付款证据时，再由数据库资金事实或纠错根事实触发器取得规范化交易引用 advisory lock。取得引用锁后不得再等待此前未锁定的既有业务行，避免普通收款与主管纠错形成引用锁/行锁环路；锁后重新构建效果，Preview 后任一依赖变化返回 `PREVIEW_STALE`，不得依赖 PostgreSQL deadlock 终止竞争操作。
- 普通住宿与会员资金事实继续遵守已确认规则：交易引用不构成全局业务键，同号的普通事实允许保存，050 不扫描、清洗或回填历史重复。只有 `BACKFILL_HISTORICAL_MEMBERSHIP` 的新增收款与 `VOID_ERRONEOUS_MEMBERSHIP_AND_RECONVERT_STAY` 的差额收款属于主管命令声明的排他付款证据：写入前必须在两张资金事实表中从未出现，并在专用追加式 claim 中永久占用规范化引用。所有带引用的新资金事实都取得同一 advisory lock 并检查该 claim；普通事实之间同号仍可依次成功，普通事实与主管排他证据并发时先取得锁并完成者决定结果，另一方若会造成排他证据复用则原子拒绝。claim 只能由 `SECURITY DEFINER` 根事实触发器生成，runtime 不获得 claim 表写权或内部函数执行权。
- deferred constraints 分别验证资料修订唯一且无跨会员搬迁、日期纠正不改变资金/产品/余额、历史补录链与真实收款完整互链、错误链恰好作废一次且新旧资金守恒。数据库直接构造部分结果必须失败。
- 所有纠错新增事实的 `createdAt/recordedAt` 必须绑定本次服务端事务时间；历史业务日期只进入明确的业务日期字段，不得通过直接数据库组合伪造历史录入时间。
- 每个命令的幂等重放只返回原 Receipt；并发最多产生一组事实。Receipt 必须能从会员页追溯原事实、纠正依据、系统计算和当前结果。

### 7.7 已生效会员订单欠费时的普通收款

- 复用既有 `RECORD_MEMBERSHIP_PAYMENT`，不新增“继续收款”命令或第二套资金入口。页面按钮对 `DRAFT` 和净收款低于成交价的 `ACTIVE` 订单统一显示“收款”；足额、多收或 `VOIDED` 时不显示。
- 打开收款时默认带出当前尚差金额，但允许按真实企微流水登记任意正数分笔收款；若实际收款导致多收，Preview 必须明确显示多收差额，仍保存真实资金事实而不自动改价。普通当天收款不让操作人填写日期，服务端使用当前物业营业日作为企业微信收款日期，精确系统记录时间继续由事务生成。
- Preview 显示成交价、此前实收、本次收款和操作后差额。Confirm 锁定订单与资金事实后按最新净收款重算；若另一操作已改变实收，旧 Preview 以 `PREVIEW_STALE` 失败，避免两人同时依据旧欠款重复操作。
- 对 `ACTIVE` 订单只追加一笔会员 COLLECTION、Audit 和 Receipt；不得修改会员开始日期、有效期、合同、Lot、权益总量、已用数量、余额或生命周期。会员收款更正仍维持既有适用范围；真实退款继续不在本轮。

## 8. 失败测试优先与自动门禁

每个检查点必须先编写并运行能在当前基线失败的测试，再写实现。最低测试集如下：

### 8.1 9.1

- 真实 PostgreSQL 投影：整房/床位、直订/渠道/会员/免费，计划退房日与次日逾期严格分离。
- 断言原 `orderArrivalDate/orderDepartureDate`、`DUE_OUT / 待退房`、阻断冲突与 Quote/Confirm 安全；断言不出现今天至明天普通订单身份。
- 桌面 Grid、快捷框、订单上下文、移动“今日离店”、Tooltip、无障碍名称和返回锚点。
- 创建与退房、跨营业日 Quote/Preview/Confirm 竞态。
- Contract/OpenAPI 对新枚举、`orderDepartureDate`、非法组合与额外字段失败关闭。

### 8.2 9.2

- 每条 command type 参数化验证普通员工/管理员 exact allow/deny，覆盖 Preview、Confirm、stored Preview、replay、Receipt/Command/find/resolve。
- 跨物业、跨主体、同主体不同 Token、READ grant、Token ceiling 升权、Preview 后撤权和撤权/Confirm 竞态。
- 拒绝后业务表、协议表与幂等域零写入，只有一条脱敏拒绝审计。
- runtime 数据库角色直接尝试修改 protected facts、`ALTER TABLE`、`DISABLE TRIGGER` 均失败。

### 8.3 9.3

- 单笔日期纠正、两笔日期交换、房/床边界、集合外冲突、终态/版本/资金/权益依赖拒绝。
- 并发集合顺序相反、重复 Confirm、事务中间失败、Receipt/Audit 失败全部零部分写入。
- 投影只显示新最终安排，详情完整保留 before/after 和旧历史。

### 8.4 9.4

- 会员资料五字段单项/组合纠正、无实际变化、格式错误、手机号唯一冲突、并发抢占同一手机号和禁止会员合并/历史快照改写。
- 生效日前移/后移、未使用与已使用权益；全部服务日仍在新有效期内且纠正前后保持 `ACTIVE` 时成功，任一 coverage/ledger 服务日缺失或越界、已有 `EXPIRE`、需要状态翻转或权益恢复时失败；资金、产品、总量和余额保持不变。
- 历史办卡补录创建完整 order/payment/contract/lot；`recordedAt` 为当前、业务日期为真实日期且链截至营业日仍有效；订单标价/成交价恒等于产品标价且调价恒为零，正数 COLLECTION 少付与多付均成功、差额只显示且资金事实保留真实金额；已有有效链、已过期购买、已被任一资金事实使用或已被另一主管纠错 claim 占用的付款证据、跨会员资金、真实退款、管理员输入成交价/调价和其他派生字段均拒绝。
- 历史办卡补录必须证明会员开始日期与企业微信收款日期可以相同、前者在前或后者在前；两者只要均不晚于营业日即可。API 拒绝精确收款时间字段，合同与权益日期只随会员开始日期变化，收款事实只保存收款自然日。
- `RECORD_MEMBERSHIP_PAYMENT` 覆盖 `DRAFT` 与欠费 `ACTIVE`：默认尚差金额并允许按真实流水分笔登记，收款后少收、足额或多收都在 Preview 明示；Confirm 并发重算，且 `ACTIVE` 收款前后合同、Lot、权益、会员开始日期和生命周期逐值不变。操作前已经足额、多收或作废的订单不提供入口。

### 8.5 9.5

- 完全未使用错误链按不同金额成功，CNY 936.00 只是一组样例；任一 coverage/ledger/transfer/旧冲销、真实退款、金额证据不匹配场景拒绝。
- 历史住宿身份、手机号、房型、有效期、状态、WECOM 资金图、重复转换、混合资金和跨会员边界。
- 系统计算日期、差额、产品权益、历史核销与剩余权益；所有派生字段 API 不接受输入。
- 四条会员命令逐写点故障注入、双人并发、幂等重放、Preview stale、Receipt/Audit 失败；数据库直接构造部分修订、部分作废、重复 bridge、权益不守恒或跨会员关联时拒绝。

## 11. 冻结结论

第 9 步的业务语义已按最窄可交付范围冻结：

- 9.1 不改变住宿半开区间和库存安全，只纠正安全阻断的业务表达。
- 9.2 只增加 exact command grants，不创造广义管理员。
- 9.3 只处理已完成历史安排且保持身份、生命周期和资金不变；“鹏哥/小尚”只作为隔离合成夹具名称，不是特判。生产 108 当前仍在住，必须走另立的一次性过渡程序或专用在住纠错状态机。
- 9.4 提供会员资料、生效日和历史办卡补录三种永久能力。生效日录错或操作员晚录时，主管输入真实日期/原因/证据，系统整体重算合同与 Lot；首版只处理纠正前后都保持有效的链，已使用权益只有在全部服务日仍合法且资金、产品、数量、余额和生命周期状态不变时放行。
- 9.5 只对错误且完全未使用的会员链执行原子作废重建，金额由真实事实与系统规则推导，不绑定 CNY 936.00。真实退款、跨会员身份和不可唯一推导的资金失败关闭。
- 仅本次切换才有的少数异常由版本化、dry-run、幂等、可审计的一次性程序处理，不进入管理员页面。

9.1/9.2 已人工通过并提交为 `e257994`。9.3 至 9.5 的通用状态机、失败关闭边界、实现、自动门禁和高风险终审已经完成，并于 2026-09-04 收到连续组统一人工验收口令 `9.3-9.5 通过`。本次已授权创建本地提交，但仍不推送、部署或修改生产业务数据。隔离合成样例只用于证明通用状态机；生产 108、Cathy、晶晶的当前记录不满足通用命令资格，待权威事实补齐后由固定目标的一次性过渡程序收口。
