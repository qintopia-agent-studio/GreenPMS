## 1. 纠偏结论

本规格取代本文件 2026-08-11 的所有旧口径。旧方案中以下内容明确废止：

1. 不再把所有补录都实现为“先创建普通预订，再补办入住和退房”。
2. 不再强制已经完成的补录订单伪造足额收款；真实欠款必须保留。
3. 不再把历史已完成住宿映射成 `IN_HOUSE`，也不增加历史床位占用或“无住宿”静态样式；历史日期头保留经营汇总，只显示入住率与实际付费住宿人数。
4. 不把“补录”作为日历上的订单生命周期状态或订单条标记。
5. 在住升级会员不能只放开入口；必须同步处理续住、缩短、换房、重价和撤销入住边界。

本需求只处理系统上线后工作人员漏记的单笔真实经营事实，不涉及旧系统数据批量导入。

## 2. 统一业务模型

### 2.1 补录定义

补录表示业务已经真实发生，但工作人员当时忘记录入系统，之后依据真实记录补记。系统必须同时保留：

- 真实入住日、离店日及资金发生事实；
- 实际补录时间、补录人和补录原因；
- 企微或银行转账的交易单号；现金的收款人和备注；
- 暂不要求上传图片附件。

补录来源只在订单详情和审计记录中展示，不在日历订单条上增加“补录”标记。

### 2.2 履约与结算分开

正常订单和补录订单采用完全相同的显示标准：

| 履约事实 | 门店直收结算事实 | 运营显示 |
|---|---|---|
| 在住 | 任意 | 在住 |
| 已退房 | 已收清 | 已结单 |
| 已退房 | 未收清 | 欠款 |

“欠款”只表示本应由门店直接收取、但尚未收齐的住宿款。后续补收达到订单应结金额时，系统自动从“欠款”变为“已结单”。

免费住宿按现有免费类型和原因记录，不产生欠款。真实优惠先形成可追溯的成交价修正，再按修正后的应结金额判断是否欠款。当前不新增审批或坏账核销流程，也不得以虚假收款抹平欠款。

### 2.3 渠道订单

游牧岛、携程、美团等外部渠道订单，无论普通创建还是补录，以下两个字段均为强制必填：

- 渠道订单号：非空；
- 本单渠道应结金额：非空且为有效金额；普通付费渠道订单必须大于 0。

缺少任一字段时，Web、API、领域层和数据库写入均须拒绝且零业务写入。渠道订单不在 PMS 登记门店单笔住宿收款，也不参与门店直收欠款判断；住宿完成且渠道信息完整后显示“已结单”。这只表示住宿履约闭环，不表示渠道已经向门店打款。渠道订单号和渠道应结金额继续在订单详情中供渠道总账核对。

## 3. 日历入口与两类整笔补录

### 3.1 快捷菜单

- 所选区间包含今天以前的日期：快捷菜单显示“补录住宿”。
- 所选区间全部从今天开始或位于未来：快捷菜单显示“创建订单”。
- 历史空白格保持与普通空白格一致的日常视觉，不静态显示“无住宿”。
- 已有订单不再提供“整笔住宿补录”；工作人员进入订单详情处理该订单仍缺失的资金事实或确实存在的履约漏记。

补录表单不询问“客人是否仍在住”。系统依据入住日和离店日自动进入以下唯一路径。

### 3.2 已完成住宿补录

适用条件：`arrivalDate < departureDate <= businessDate`。离店日不计住宿间夜，因此离店日等于今天也属于已经完成。

操作旅程：

1. 操作员在过去日期或日期区间打开快捷菜单并点击“补录住宿”。
2. 一次填写房源、实际入住日、实际离店日、住宿人、订单类型/渠道、真实成交金额、已经发生的真实收款、补录原因和对应凭据字段。
3. 只展示一次中文业务核对。
4. 一次确认原子创建订单、写入历史入住与退房事实、释放当前库存占用，并登记真实资金事实。
5. 成功后直接返回日历：已收清显示“已结单”，未收清醒目显示“欠款”。

该路径不产生需要操作员继续点击的 `RESERVED` 或 `IN_HOUSE` 中间状态，也不显示“补办入住”或“补办退房”。允许零收款、部分收款或足额收款，但必须如实记录；不强制结清。

### 3.3 当前在住住宿补录

适用条件：`arrivalDate < businessDate < departureDate`。

操作旅程：

1. 操作员选择跨越今天的日期区间，点击统一文案“补录住宿”。
2. 一次填写房源、实际入住日、预计离店日、住宿人、订单类型/渠道、真实成交金额、已经发生的真实收款、补录原因和对应凭据字段。
3. 一次确认原子创建订单、写入历史入住事实，并为完整住宿区间建立权威库存占用。
4. 成功后直接返回日历，整条住宿显示为“在住”。
5. 后续使用普通在住订单的续住、缩短、换房和退房流程。

该路径不经过等待操作员办理的“已预订”状态，也不强制提前收清未来尚未履约的住宿款。

### 3.4 已有订单的漏记

整笔住宿补录与已有订单漏记严格分开：

- 已完成补录订单：只允许查看、补记真实收款及处理欠款；不再补办入住或退房。
- 原本已存在、但确实漏办退房的逾期在住订单：才提供受控的退房补记。
- 原本已存在、但确实漏记资金的订单：在订单资金区域补记真实收款或退款。
- 不让所有历史订单普遍出现“补办入住/退房”。

## 4. 房态显示

历史、今天和未来使用同一套日历结构和状态视觉。时间只决定允许的动作，不改变订单状态的含义。

| 订单事实 | 日历表现 |
|---|---|
| 已退房且已结清 | 保留完整订单条，使用统一的低干扰完成色并显示“已结单” |
| 已退房但未收清 | 使用醒目的警示色并显示“欠款” |
| 已预订或在住 | 沿用对应状态色和文字 |
| 跨越今天的补录在住订单 | 从历史部分到未来部分保持同一条“在住”订单条 |

附加约束：

- 不能用 `IN_HOUSE` 表示“过去曾经住过”。
- 已完成历史住宿不计入当前在住人数、床位占用或待办。
- 历史空白格不显示“无住宿”。今天及未来日期头继续显示可售余量；今天以前日期头改为显示经营入住率与实际付费住宿人数，入住率分母按 31 间房 + 46 张可售床位 = 77 个可售卖单元，分子只统计正常应收费订单占用的同口径可售卖单元：只能整间卖的房间按 1 计，床位房整间占用按其活跃床位数计，单床订单按 1 计；排除义工、接待等免费入住。
- 订单是否补录不影响颜色；颜色只表达当前业务结果。
- 不能只依靠颜色，订单条必须同时显示“已结单”或“欠款”等文字/图标。

## 5. 在住订单升级会员

### 5.1 连续操作旅程

订单详情统一使用“升级会员”入口：

1. 点击后按主要住宿人的规范化手机号精确查找会员档案。
2. 主要住宿人无手机号时，引导进入住宿人资料纠错；保存后自动回到原订单继续。
3. 已存在唯一会员档案时，直接进入升级表单。
4. 不存在会员档案时，进入“建立会员档案”，从订单预填姓名、昵称和手机号；建档成功后自动回到原订单并继续升级，不要求重新查找订单。
5. 核对会员、适用会员产品、住宿有效净收款、转入金额、会员成交价、本次企微应收差额和本次住宿权益核销。
6. 最终只确认一次。成功后停留在原订单详情，可查看会员订单、住宿金额归零、原收款转入关系和会员权益结果。

`CREATE_MEMBER` 可作为独立事务；工作人员建档后放弃升级，只留下有效会员档案，不产生资金或权益。其余升级动作必须由单一原子命令完成。

### 5.2 资金规则

- 仅企业微信来源的普通住宿订单可以升级会员；会员费仅支持企业微信收款。
- 有有效住宿净收款时，必须一次转入全部符合条件的企微住宿净收款，不能挑选部分转入。
- 会员成交价不得低于转入金额；差额作为会员订单的新企微收款，必须填写新的交易单号。
- 住宿净收款为 0 时允许升级：转入金额为 0，本次企微新收金额等于全部会员成交价，本次住宿改由会员权益结算。
- 零元转入只形成审计结果，不生成虚假的 0 元收款事实或转入明细。
- 存在非企微、混合、已退款、已冲销或已用于其他转换的资金时，失败关闭并提示先核对资金事实。
- 确认时原子完成会员订单创建与生效、住宿收款转入、差额企微收款、会员权益发放、本次住宿权益核销和住宿合同金额归零；任一步失败均零业务写入。

### 5.3 在住升级后的订单变化

- 升级时按当前完整计划住宿区间一次核销会员间夜/床夜。
- 正常退房不重复扣权益。
- 续住时从会员剩余权益追加扣除新增间夜/床夜；余额不足时阻止续住，并提示先补充会员权益或另建普通住宿订单。
- 缩短时退回尚未实际使用的未来间夜/床夜，已经发生的住宿权益不退。
- 换到同一会员产品适用的房型或床位时，权益数量不变；目标库存仍需通过并发和容量校验。
- 换到会员产品不适用的房型或床位时阻止换房，不自动计算现金差价。
- 升级后禁用普通住宿重价；日期变化通过权益追加/退回处理，会员成交价录错通过会员订单纠错处理。
- 升级后暂时禁止使用普通“撤销入住”。完整撤销升级及会员购买不属于本切片，不得以部分回退方式伪造完成；后续如需支持，必须单独定义原子撤销规则。

## 6. “今天”按钮

“今天”按钮必须同时完成两个动作：

1. 把日期范围恢复为今天起连续 30 天；
2. 把日期表头和房态正文两个同步横向滚动容器恢复到最左侧。

即使当前查询范围已经是今天起 30 天，也必须执行横向归位。保留当前筛选、展开房源、纵向位置和键盘焦点，不使用会改变纵向位置的 `scrollIntoView`。

## 7. 技术边界

### 7.1 原子命令

整笔住宿补录不能使用“普通 `CREATE_ORDER` 成功后，再执行第二条补录命令”的两步方案。应由单次 Preview/Confirm 命令根据日期分支，原子写入：

- 订单与首个计价修订；
- 住宿人与完整住宿区间；
- 已完成路径的入住、退房和真实资金事实；或在住路径的入住事实与完整库存占用；
- 补录人、补录时间、原因和凭据引用。

陈旧 Preview、日期或库存冲突、重复提交、并发确认和命令恢复必须保持幂等，失败时不得留下预订中间态、半笔资金或孤立库存占用。

### 7.2 查询投影

房态 DTO 必须分别表达：

- 历史服务区间曾经发生过住宿；
- 订单当前履约状态；
- 门店直收结算状态；
- 当前是否阻塞库存。

不得借用 `IN_HOUSE` 表达历史发生事实。完成订单条、欠款标记和当前库存阻塞必须由各自事实推导。

## 8. 分步开发与验收门禁

本切片不再开发完后分三组集中验收，改为六个顺序检查点：

1. 每个检查点只开发和返工当前范围，不提前打开后续功能。
2. 完成当前检查点的自动检查后，必须启动真实 Web、API 和 PostgreSQL 版本，由用户在桌面端和手机端进行 UI 人工验收。
3. 未收到当前检查点的明确通过口令时，不开始下一检查点。任一项不通过只返工当前项。
4. 每个检查点完成后，在本文档和总验收计划中记录验收日期、结果和自动检查证据。

### 8.1 历史房态显示

开发范围：

- 过去空白日期不再表达“可售”；8.1 阶段暂不开放补录创建入口，避免进入未完成的补录提交流程。正式“补录住宿”入口、普通/免费/渠道表单与资金凭据在 8.2 开放；历史空白格保持中性，不重复显示“无住宿”。
- 今天及未来日期头显示 `剩 X 间 · Y 床`；今天以前日期头显示 `入住率 X% · N人`。入住率按正常应收费订单占用的同口径可售卖单元数 / 77 计算：只能整间卖的房间按 1 计，床位房整间占用按其活跃床位数计，单床订单按 1 计；N 人按正常应收费订单的实际住宿人数计算。渠道、欠款和零收款正常订单计入，义工、接待等免费入住不计入。
- 已完成订单只投影缩短、换房、改期和退房后最终有效的住宿时间线，不复活已被替代的旧区间。
- 所有普通住宿使用已验收的逐日格呈现，不显示持久住宿文字横条；点击任意一天时按同一 Order/Stay 连续高亮整段住宿。维修/锁房等 Block 横条保持不变。
- 以 2 栋 203 的既定住宿呈现为布局基准；复核 1 栋 102 和 2 栋 205 只显示最终有效日期。
- 已结单使用低干扰完成色并显示“已结单”；有欠款使用醒目警示色并显示“欠款”；逾期待处理、事实冲突或数据未知使用醒目异常样式和明确文字，不伪装成已结单或可售。
- 正常订单与补录订单完全共用上述显示标准；“补录”不作为日历状态标记。
- 同步验证“今天”按钮在当前 30 天范围内横滚后和翻页后，均能将日期范围与表头/正文横向位置一起恢复。

UI 人工验收：直接对比 102、205、203，检查历史空白格、整段选中、无住宿横条、已结单、欠款和异常状态，并验证“今天”按钮。通过口令：`8.1 通过`。

### 8.2 补录入口与表单

开发范围：

- 所选区间含今天以前日期时显示统一入口“补录住宿”；全部从今天或未来开始时显示“创建订单”。
- 普通创建入口保持可用，不因增加补录分流而丢失开单表单。
- 补录使用一个表单，由操作员选择“普通住宿”或“免费入住”；免费入住必选义工/接待并填写原因，不显示渠道和收款字段，不产生欠款。
- 外部渠道必填渠道订单号和本单渠道应结金额；门店直收按已确认规则收集真实收款与凭据：企微/银行转账填交易单号，现金填收款人和备注。
