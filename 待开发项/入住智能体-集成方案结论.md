# 秦托邦入住智能体：主对话结论交接

> 用途：把主对话中已经讨论并基本确认的业务、数据和系统集成结论交给后续对话。
> 本文是决策交接记录，不是最终实施规格。涉及资金、库存、订单生命周期和权限的实现，仍需据此编写 A 级实施规格并通过自动检查和人工验收。

## 1. 总体结论

方案可行，推荐采用以下职责分工：

```text
飞书多维表格（申请入口）
        -> 飞书 Workflow
        -> Hermes/Bridge（事件接收、对话编排、状态、幂等、审计）
        -> 企业微信智能机器人长连接（群内 @Hermes）
        -> PMS 受控命令接口（预订、收款记录、入住）
```

Hermes 的职责是组织对话、补齐信息、查询可售房源、提出安排建议并发起受控 PMS 操作；它不是数据库，也不应直接持有 PMS 或支付系统的高权限密钥。

PMS 继续作为订单、房态、入住、退房、应收和收款事实的权威系统。飞书 Base 主要作为申请入口和运营视图；Bridge 保存跨系统关联、处理状态、提醒、幂等和恢复信息。

## 2. 当前范围和现状

- 飞书 Base：`秦托邦｜入住申请信息表`
- 申请表：`秦托邦入住申请数据`
- table ID：`tbl4OryeWd0Td8jN`
- 当前启用的工作流：`wkf4jJ2PC2cqwRdD`
- 触发器：`AddRecordTrigger`
- 当前工作流目标仍是：`https://qintopia.cn/webhooks/silaoshi-base-notify`
- 该地址是现有通知服务，不是 Hermes。上线 Hermes 时应改为 Hermes/Bridge 的接收地址。
- 历史申请暂不回放或补处理，只处理自动化正式启用、测试或上线后新产生的记录。
- 当前表单约有 18 个问题，已经包含姓名、昵称、手机号、预计入住日期、计划入住天数、期望房型、获知渠道及部分资料字段。

## 3. 已确认的业务流程

### 3.1 申请、核对和预订

1. 申请人提交飞书表单。
2. 飞书 Workflow 只通知一个安全的 Base/table/record 标识；Bridge 再用飞书 API 读取结构化记录。
3. Bridge 为这条申请创建一个处理案例，Hermes 在企业微信群中通过 `@Hermes` 发起核对。
4. 表单中的入住日期和计划入住天数视为申请人的初步意愿，不当作最终订单事实。
5. Hermes 在群里请小客服确认最终入住日、退房日和晚数，并补齐渠道、渠道订单号、价格确认等运营信息。
6. Hermes 查询 PMS 当前可售库存，按照安排原则给出 2～3 个具体房间/床位建议。建议应考虑同房型、连续可住、减少零散空档等因素；最终选择由小客服确认。
7. 小客服明确表示“这个人确实要订，并同意日期、房间和价格”后，才算确认预订、允许占用库存。可用 `@Hermes 确认预订` 或交互按钮实现。
8. Hermes 先调用 PMS 的报价/预览，再调用受控的 `CREATE_ORDER` 建立预订。

“已确认预订”不是让申请人再填一个字段，而是小客服对申请内容、日期、具体房源和价格的业务确认。

### 3.2 收款和入住

预订、收款、入住是 PMS 中相互衔接但不同的步骤，不能把表单提交直接当作入住：

1. 预订建立后，PMS 中形成预订、应收/欠款等状态。
2. Hermes 根据 PMS 订单状态提醒小客服收款；未收、部分收款或逾期都应保留为明确状态，不阻止系统如实展示。
3. 收款事实可以先由小客服提供交易号和金额；有支付权限时，Bridge 可进一步查询并给出匹配建议。
4. 只有匹配到成功状态、金额、商户、时间且无退款等条件后，才可把支付结果标记为已核验；交易号本身不等于到账证明。
5. Bridge 通过定时任务在到店前或当天提醒小客服确认是否已到店。提醒规则可以后续单独确定，也可以先建立固定规则。
6. 小客服在群内确认已到店后，Hermes 再查询 PMS 当前允许动作并调用 `CHECK_IN`。
7. 退房继续使用 PMS 现有 `CHECK_OUT` 流程，不在 Hermes 外另造一套生命周期。

## 4. 申请表结构原则

用户不希望继续增加申请人填写项，以免降低提交率。当前方向是：

- 保留现有公开问题，包括预计入住日期、计划入住天数和期望房型。
- 将这些字段解释为“初步意愿”，而非最终订单字段；如需改名，推荐使用“预计到店日期”和“初步计划住几晚”。
- 不要求申请人填写最终渠道、渠道订单号、具体房间/床位、PMS 订单号、支付交易号等运营字段。
- 缺失或需要确认的信息由 Hermes 通过企业微信群对小客服询问并补齐。
- 对订房和房态安排无关的资料字段，Hermes 可以忽略其业务处理，但应按权限和隐私要求留存在飞书原始记录中，不要擅自删除。
- 可选的运营字段建议放在内部字段或单独的运营表中，而不是增加公开表单问题：最终入住日、最终退房日、最终晚数、预订渠道、渠道订单号、选定房源、价格确认、PMS 订单号、处理状态、缺失字段、最后提醒时间等。

不建议把 `昵称 + 真名 + 手机号` 设为唯一键。现实中可能出现同名、昵称变化、共用手机号、手机号更换、只填一端或人工创建订单等情况。

## 5. 推荐的数据模型

逻辑关系：

```text
Person（一个真实的人）
  0..N Application（飞书申请提交）
  0..N PMS Order Link（PMS 订单关联）
```

### 5.1 Person

- 使用 Bridge 生成的稳定 `person_id`。
- 姓名、昵称、手机号都是资料或匹配候选，不是绝对主键。
- 规范化手机号完全匹配时，可以自动给出匹配建议；冲突、共用、变更或缺失时，必须让小客服确认。

### 5.2 Application

- 一条飞书 record 对应一次申请提交，使用不可变 `application_id`，并保存 `feishu_base_id`、`feishu_table_id`、`feishu_record_id`。
- 一个人可以有多次申请；一次申请也可能最终没有建立订单。
- 保存处理案例状态、缺失字段、确认消息、提醒状态和错误信息。

### 5.3 PMS Order Link

- 一条记录对应一个 PMS 订单，保存 `pms_order_id`、`person_id` 和可选的 `application_id`。
- 订单可能来自飞书申请，也可能直接由小客服、Hermes UI 或其他渠道创建，因此 `application_id` 必须允许为空。
- 应支持一个人查询全部订单、复购次数、总入住时长和历史房间/床位。
- PMS 是订单与入住事实的权威来源，Bridge 保存关联和同步元数据；飞书可以展示结果，但不应成为第二个订单事实源。

### 5.4 轻量化落地

不需要一开始建设一个很重的独立业务数据库。建议 Bridge 使用一个小型关系数据库保存：

- Person、Application、PMS Order Link；
- 案例状态、缺失字段、提醒计划；
- 幂等键、事件 Inbox、重试和失败原因；
- 企微操作者、批准消息、时间和审计关联。

飞书 Base 可以继续作为运营人员查看和补充信息的界面，但长期稳定的关联、恢复和幂等数据不要只放在 Base 公式或备注里。

## 6. 只填一端和数据一致性

需要接受以下情况，而不是假设所有数据都从表单开始：

- 老客不再填写表单，只由小客服发文字或在 UI 建单；
- PMS 中直接改了房态、建立了订单或办理了入住，但飞书没有对应记录；
- 飞书有申请，但尚未建立 PMS 订单；
- 一个人有多次申请或多笔订单。

建议的处理方式：

1. PMS 作为订单、房态和生命周期事实的权威来源。
2. Bridge 定期读取 PMS 订单/入住变化，尝试按现有订单外部引用、规范化手机号和人工确认关联到 Person/Application。
3. 无法可靠匹配时建立“待人工匹配”任务，不自动合并人员。
4. 对直接创建的 PMS 订单，允许先生成没有 `application_id` 的 Order Link，后续由小客服补关联。
5. 对只存在飞书申请的记录，保留案例状态，不伪造 PMS 订单号。

## 7. Base 结构变化对 Hermes 的影响

Base 变更不会必然导致 Hermes 失效，关键取决于变更类型和读取方式：

- 新增字段：如果 Bridge 按稳定的字段 ID 读取并允许未知字段，通常不影响；需要决定是否映射为运营字段。
- 改字段名：如果代码按字段名读取，可能影响；推荐改为按字段 ID 和版本化映射读取。
- 删除字段或改变字段类型：可能造成字段缺失、解析错误或错误下单，应先更新适配器和测试。
- 改表、换 table ID 或更改权限：会影响事件和读取权限，必须更新配置并做端到端测试。

推荐做法是保持公开申请表稳定，新增内部运营字段时使用明确的字段 ID；Bridge 建立一层 Feishu 字段适配器，记录 `schema_version`，并对必需字段缺失采取“进入待补齐状态”，不能直接调用 PMS。

## 8. 企业微信接入

使用企业微信智能机器人长连接，由轻量的 WeCom Gateway/Bridge 负责：

- 单条 WebSocket 长连接；
- 心跳、断线重连和状态监控；
- 群内 `@Hermes` 消息接收与发送；
- 企微用户白名单和身份校验；
- 消息去重、顺序处理和审计。

群内对话是有意选择的，因为它能让小客服、技术人员和运营人员看到同一上下文，方便调试和改进流程。群里应展示案例状态、缺失字段、房源建议、确认结果、PMS 操作结果和失败原因。

手机号、生日、完整支付交易号等敏感值不建议在多人群公开。群里可显示掩码、末几位和“已匹配/待人工核验”；完整值通过白名单客服单聊或受控表单录入。若业务坚持全部在群里调试，也至少要控制群成员和日志留存权限。

## 9. 支付接口选择

### 首期推荐：企业微信“对外收款”接口

官方接口：[获取对外收款记录](https://developer.work.weixin.qq.com/document/path/93667)

优点是贴合当前小客服工作流，Bridge 可以按时间和收款员工获取记录，再按交易号、金额、时间、商户和退款状态匹配订单。需要企业微信自建应用权限、`CorpID`、应用 `Secret` 及收款员工可见范围。

注意：企微机器人的 `BotID/Secret` 与支付查询权限是两套凭证，不能混用。

### 后续增强：微信支付商户 API v3

官方接口：[按微信支付交易单号查询订单](https://pay.weixin.qq.com/doc/v3/merchant/4012791858)

它更适合精确查单，但需要商户号、商户私钥/证书、微信支付平台证书或公钥、API v3 Key 等，部署和轮换成本更高。

因此首期建议先用企业微信对外收款记录做“匹配建议/核验”，再根据资金量和审计要求增加微信支付 API v3。没有相应商户权限时，Hermes 只能根据客服提供的信息给出匹配建议，不能声称已核验到账。

## 10. Bridge 的位置和项目归属

推荐建立独立项目，例如 `qintopia-booking-bridge`：

- 逻辑上属于 Hermes/集成层，不属于 PMS 核心；
- 初期可以与 PMS 部署在同一台物理服务器；
- 使用独立容器、独立数据库/数据库用户、独立配置和凭证；
- 不要把 Bridge 代码、权限和生命周期隐含在 PMS 核心进程里。

Bridge 负责飞书事件入口、企微长连接、Hermes 调用、案例状态和提醒、支付查询、PMS API 适配、幂等恢复以及 Person/Application/Order Link 映射。

## 11. 安全和权限的白话说明

### 11.1 Webhook 密钥是谁创建

当前飞书工作流里有一串固定的“接头密码”，接收方用它判断请求是否来自飞书。能查看工作流配置的人可能看到它；泄露后，别人可能伪造一条申请通知。

这个密码不是 Agent 创建，也不是 Hermes 模型、PMS 或 Base 创建。应由 Bridge 的部署/运维系统生成随机密钥，然后各保存一份：飞书 Workflow 的请求头一份，Bridge 的服务端密钥库一份。Hermes 运行时和模型不应看到它。启用 Hermes 时应生成新密钥并让旧密钥失效。

### 11.2 为什么只传 record ID

如果工作流把姓名等文字直接拼进原始 JSON，姓名里出现引号、换行或特殊字符时，请求可能变成坏格式，导致 Hermes 收不到或误读字段。

所以工作流只发送安全的 `base_id`、`table_id`、`record_id` 和事件时间/版本等标识；Bridge 收到后通过飞书 API 正规读取整行结构化数据。申请表本身不需要因此增加字段。

### 11.3 Hermes 操作人的责任归属

PMS 会记录“哪个账号执行了操作”。如果 Bridge 使用 Hermes 的系统账号创建预订，PMS 默认只会显示 Hermes，而不知道是哪位小客服批准。

首版由 Bridge 同时保存企微操作者 ID、批准消息内容、时间、案例 ID 和 PMS 操作 ID。若以后要求 PMS 内必须显示正式责任客服，则需要让客服在 PMS UI 登录确认，或增加带身份校验的审批协议。群里一句普通文本能证明“谁发过消息”，但不自动等同于 PMS 的正式责任主体。

### 11.4 PMS 写权限和命令门禁

PMS 的 WRITE Token 类似物业级总钥匙，不能直接交给可以自由对话的模型。Bridge 前面必须有一层命令门禁，只允许明确的动作，例如：

- `QUOTE/PREVIEW`：报价和预览；
- `CREATE_ORDER`：建立预订；
- `RECORD_COLLECTION`：记录已核验收款；
- `CHECK_IN`：办理入住；
- `CHECK_OUT`：办理退房（按后续范围开放）。

首期排除退款、会员删除/合并、维修、房态纠错、权限管理、Token 管理等动作。每个命令都要检查案例状态、操作者权限、参数、幂等键和 PMS 当前允许的生命周期迁移。

## 12. 可靠性要求

网络和消息系统可能重复投递、乱序、延迟或临时丢失。必须按以下原则设计：

- 每个飞书事件进入事件 Inbox，先落库再处理；
- 每个申请和每个 PMS 动作用稳定幂等键，重复收到只执行一次；
- 处理失败保留原因和重试次数，支持人工或自动重放；
- 定时补偿扫描寻找卡住、漏投或长期未补齐的案例；
- 建单、收款、入住等关键动作使用 PMS 支持的预览/确认和事务规则；
- 所有外部调用保存请求关联 ID、结果、操作者和时间，但避免记录不必要的完整敏感信息。

## 13. 尚未最终确定的业务决策

以下事项需要在正式实施规格前定下来：

1. 哪些企业微信用户可以确认预订、确认收款和确认到店/入住。
2. 群内 `@Hermes` 是否足以作为业务批准，还是必须再由客服在 PMS UI 确认以形成正式责任记录。
3. 房间/床位推荐规则的具体优先级，例如同房型、连续入住、楼层、床位偏好、减少空档和人工保留房。
4. 首期开放的 PMS 命令集合，以及哪些动作必须二次确认。
5. 缺失字段的提醒频率、超时升级对象和最终关闭规则。
6. 企业微信对外收款 API 的权限范围和可见收款员工。
7. PMS 是否需要新增正式的 `order_external_references`（追加式外部引用）来保存飞书 `record_id`、Bridge `application_id` 等引用；试点阶段可以先由 Bridge 保存。

## 14. 建议实施顺序

1. 固化本文中的业务状态和字段字典，确认待决策项。
2. 为 Bridge 编写 A 级实施规格，先定义数据表、状态机、权限、幂等和恢复策略。
3. 建立独立的 `qintopia-booking-bridge` 项目和小型数据库。
4. 先接飞书 Workflow：仅接收新 record 的 ID，读取记录并创建案例，不调用 PMS 写操作。
5. 接入企微智能机器人长连接，实现群内 @Hermes、白名单和消息去重。
6. 实现“缺失字段询问/补齐/定时提醒”和房源查询建议。
7. 接入 PMS 的 Quote/Preview，再以测试环境或受控账号实现 `CREATE_ORDER`。
8. 接入收款记录匹配，先做人工确认和可解释的匹配建议。
9. 实现到店提醒和客服确认后的 `CHECK_IN`。
10. 用新提交的测试申请做端到端人工验收；历史记录不自动回放。

后续对话应先阅读本文，再读取 PMS 现有契约和测试，重点参考：

- PMS 可售查询：`apps/api/src/server.ts` 中的 availability 路由；
- `CREATE_ORDER` 契约：`apps/api/src/schemas.ts`；
- Agent 旅程契约测试：`tests/contract/agent-core-journey.contract.test.ts`；
- PMS 命令和幂等规则：`README.md`；

不要因为本文提到“建议”就直接改变 PMS 业务规则；先把待决策项转成明确规格。涉及资金、库存、订单生命周期、权限、重试和恢复的内容按 A 级处理。
