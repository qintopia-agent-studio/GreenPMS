# 渠道订单计价、住宿生命周期与后续范围纠偏提案

## 1. 问题摘要

人工验收发现，原计划把所有政策价差都称为“人工改价”，同时把渠道手续费、平台提成、渠道应收、实际到账和银行流水混入 PMS 的未来对账设计。这不符合真实经营关系：对于游牧岛、携程、美团订单，渠道是本住宿订单的客户；渠道针对该订单应结给物业的金额就是订单合同金额，不是操作员临时改价，也不是平台批次打款或银行实际到账。

同一轮审计还发现，原 4.2 把共享命令 UI、阶段 2 创建计价、阶段 7 选择回归、阶段 11 换房和阶段 13 资金规则打包成一个检查点，违反“一阶段一验收”和“不跨层预改”原则。

4.1 人工验收进一步暴露了住宿生命周期缺口：当前普通退房可以提前释放未来库存，却不缩短计划日期、不重价；现有续住/缩短命令只能改退房日，完全不能调整未入住订单的到店日；逾期未到、逾期在住、入住当天退房也没有闭合的日期规则。页面又把不可变的住宿安排版本直接命名为“住宿分段”，容易被理解成实际入住流水。本提案因此补充状态乘营业日期矩阵和订单详情信息模型，但不授权在 4.1 通过前实现后续阶段。

## 2. 已批准业务决定

### 2.1 金额语义

- `YOUMUDAO`、`CTRIP`、`MEITUAN` 是外部渠道订单。
- 工作人员可见字段统一命名为“本单渠道应结金额”。
- “本单渠道应结金额”表示渠道针对这一张订单应当结算给物业的金额；它就是该订单首个计价修订的合同金额。
- 它不是住客向平台支付的金额，不是平台多单合并打款金额，也不是银行实际到账金额。
- 不新增第二个“渠道应结金额”持久字段；订单当前合同金额继续是唯一权威金额。
- 政策基础金额和锁定的政策版本必须保留，用于衡量渠道价格差异。

### 2.2 渠道和原因规则

- 外部渠道订单必须填写渠道订单号和本单渠道应结金额，两者都不得为空；不得把政策价静默伪装成已经确认的渠道应结金额。
- 外部渠道订单的金额与政策价不同，本身不属于人工改价。
- 渠道价格差异率为 `abs(本单渠道应结金额 - 政策基础金额) / 政策基础金额`。
- 差异率不超过 15% 时不要求自由文本原因；正好 15% 仍属于正常范围。
- 差异率超过 15% 时，必须填写“渠道价格差异说明”。服务端使用整数金额判断：`abs(target - policyBase) * 100 > policyBase * 15`，不得使用浮点百分比比较。
- `WECOM` 视为直订来源，渠道订单号必须为 `null`。默认采用政策价；只要工作人员主动偏离政策价，就必须填写人工调价原因。
- 订单创建后更正任何已保存价格，无论差异大小，都必须填写更正原因并追加新 amendment/pricing revision；不得覆盖原始事实。
- 后续续住、缩短或换房产生的新 revision 不继承本次渠道价格或手工调整；如再次偏离当次政策重算金额，按当次业务重新判断并记录原因。
- 免费入住金额始终为 0，不进入渠道价格或人工调价规则；会员住宿继续使用既有权益与现金余量规则。

### 2.3 原子创建

- 工作人员仍只执行“填写 -> 核对确认 -> 界面即时反馈”。
- CREATE_ORDER 的输入必须携带本次目标合同金额；服务端预检展示政策基础金额、目标合同金额和差异。
- 最终确认在同一个 PostgreSQL 事务中创建 Order、Stay、Claim、首个 amendment 和首个完整 pricing revision。
- 禁止先按政策价创建订单，再调用 REPRICE_ORDER 改成渠道价或人工价。任何失败必须保持零业务写入。
- 正常无需解释的创建仍保存与命令类型匹配的稳定业务 reason code，`note` 为空；不能用默认文案伪造成操作员陈述。

### 2.4 PMS 与外部财务对账边界

PMS 只保存并通过 API 输出业务事实：

- PMS 订单号、渠道、渠道订单号；
- 政策基础金额、政策版本、订单合同金额；
- 创建、改价、更正、取消、退款和履约的追加式事实、原因、操作人和时间。

PMS 不为了渠道财务对账新增或分摊以下数据：

- 平台结算单或多单打款批次；
- 银行实际到账、收款账户或银行流水；
- 一笔平台/银行款项与多张 PMS 订单之间的分摊关系；
- “待结算”状态或独立的“预计/实际渠道实得金额”字段。

外部财务对账智能体通过 PMS API 取得上述业务事实，再使用用户在系统外提供的平台结算单、合并打款和银行流水完成总账汇总与差额核对。PMS 不宣称到账、结清、会计分摊或财务核销。

## 3. 影响分析

### 阶段影响

- 阶段 2：重新打开为本次直接实施切片，完成渠道订单应结金额、15% 原因门槛、直订人工调价和原子创建。
- 阶段 7：换房后原/新分段不共同高亮属于已验收稳定 Stay 选择的回归，单独修复；不改变换房计价或服务端订单身份。
- 前置纠偏 U1（原称 4.2A）：只负责当前已支持命令的共享呈现外壳，不改变未来命令业务规则。
- 前置纠偏 U2（原称 4.2B）：先输出当前页面机器信息清单供用户确认，再清理当前已验收页面；未来页面只登记，不提前实现。改名是为了避免与第 4 步正式检查点 `4.2`（住宿变更）冲突。
- 阶段 8：只允许到店营业日办理普通入住、计划退房营业日办理普通退房；提前退房、逾期未到和逾期在住在其权威流程完成前失败关闭。
- 阶段 9：改为“未入住改期与在住续住”，同一订单内支持未入住订单调整入住日和/或退房日，并支持已入住订单延长；不取消、不删除、不重新下单。
- 阶段 10：只处理已入住订单缩短及提前退房，明确 `newDepartureDate` 大于、等于、小于营业日的三分支。
- 阶段 12：负责逾期未到的可见性和最终动作边界；逾期在住还需区分真实超期住宿与迟录退房，未确认前不由普通退房静默处理。
- 阶段 13：保留 PMS 内已确认的人工 COLLECTION/REFUND 事实，但删除“为渠道银行对账建设平台批次、实际到账或跨订单分摊”的推断。

### 技术影响

- CREATE_ORDER Command/OpenAPI 需要接收目标合同金额，并按订单来源执行必填与原因规则。
- CREATE_ORDER effect、Confirm 重验和首个 pricing revision 必须使用同一目标金额；不引入第二条写入路径。
- 现有 pricing revision 的政策基础金额、调整差额和当前合同金额继续保留；无需为同一金额新增渠道结算列。
- Query/DTO/API 必须让外部智能体追溯渠道、渠道订单号、政策基础金额、订单合同金额、计价修订和原因。
- Web 根据来源显示“本单渠道应结金额”“渠道价格差异”“渠道价格差异说明”或直订“人工调价原因”。
- 订单日期变化必须追加新的住宿安排版本、amendment 和完整 pricing revision，并在同一事务中迁移库存 Claim、调整仍为 HELD 的会员覆盖；不得删除原订单、覆盖旧日期或通过取消后重下单模拟改期。
- 订单读模型必须区分原始预订安排、当前有效安排、履约结果和安排变更历史；所有 `stay_segments` 只是不可变安排版本，不能直接当成实际入住流水。

## 5. 验收合同

1. Given 外部渠道订单，when 缺少渠道订单号或本单渠道应结金额，then Web/API/领域拒绝且零业务写入。
2. Given 政策基础金额为 1000 元，when 渠道应结金额为 850 元，then 差异为 15%，不要求说明并可原子创建。
3. Given 政策基础金额为 1000 元，when 渠道应结金额为 840 元或 1160 元，then 差异超过 15%，无说明拒绝；填写说明后原子创建。
4. Given WECOM 直订订单，when 使用政策价，then 无原因创建；when 目标金额与政策价不同，then 人工调价原因必填。
5. Given 免费或会员住宿，when 创建订单，then 不出现或接受外部渠道应结金额输入，继续遵守各自既有规则。
6. Given 任一目标金额创建，when Confirm 失败、库存变化、预检过期或请求重放，then 不留下政策价订单或第二条改价事实；同键同载荷只返回原结果。
7. Given 创建成功，when 查询订单详情和 API，then 可追溯政策基础金额、订单合同金额、差异、渠道、渠道订单号和适用说明；不出现第二个重复渠道金额字段。
8. Given 创建后更正价格，when 未填写更正原因，then 拒绝；填写后追加 revision 并保留原值、新值、操作人和时间。
9. Given 财务对账智能体读取 PMS API，when 汇总渠道订单，then 能取得完整业务事实；PMS API 不返回伪造的平台批次、银行到账或跨订单分摊。

### 5.1 住宿日期与履约验收合同

1. Given 未入住订单需要调整到店日、退房日或同时改期，when 工作人员确认，then 保留同一 `orderId/stayId`，原子追加安排版本、变更记录和完整计价修订，并迁移库存与仍冻结的会员覆盖；不得删除、取消或重新创建订单。
2. Given 任一日期变更，when 形成新计价修订，then 使用原锁定政策版本按变更后的完整连续住宿重新落档；外部渠道重新确认本次渠道应结金额并执行 15% 规则，WECOM 默认政策价且主动偏价才要求人工调价，免费保持 0，会员重新计算覆盖与现金余量。
3. Given 已记录过收款，when 日期变化导致订单金额变化，then 页面只显示新的订单金额、已登记净收款和补收/退款参考差额；系统不自动收款、不自动退款，也不把差额说成到账或结清。
4. Given 已入住订单缩短，when 新退房日晚于营业日，then 订单继续在住并只释放后续日期；when 新退房日等于营业日，then 必须走原子的提前退房流程；when 新退房日早于营业日，then 作为追溯改写失败关闭。
5. Given 到店营业日尚未入住、逾期未到、计划退房日仍在住或已超过计划退房日仍在住，when 查询允许动作，then 由状态与营业日期共同决定，并给出中文业务原因；不得只根据订单状态开放动作。
6. Given 入住当天要求退房，when 最低收费/零夜口径尚未确认，then 提前退房失败关闭，不生成零夜订单或擅自退款。
7. Given 查看订单详情，when 订单经历创建、改期、入住、续住、缩短、换房或退房，then 页面分别显示原始预订安排、当前/最后有效安排、实际履约结果和安排变更历史；不得把全部 segment 顺序表述成实际住宿记录。

## 6. 前置纠偏拆分与停点

### 前置纠偏 U1：共享命令外壳（原称 4.2A）

- 冻结本次适用命令清单，只改已经实现并进入当前验收范围的命令。
- 自动载入服务端预检，取消人工“生成服务端预览”步骤。
- 只显示业务核对信息；成功关闭弹窗并以页面状态变化、非模态提示和可恢复中文状态反馈。
- 保持 Preview/Confirm/Receipt、幂等、版本锁和 API 智能体合同。
- 为自动预检中、可确认、返回修改、预检过期、提交中、结果未知、失败未执行和成功关闭建立状态矩阵及键盘/焦点验收。

### 前置纠偏 U2：当前页面信息减负（原称 4.2B）

- 编码前输出“页面、原文、取消/改写/未来阶段、替代文案、理由”清单并等待用户确认。
- 当前已验收页面移除对操作员判断无用的机器信息；会员模式保留中文覆盖晚数、未覆盖晚数和未覆盖金额。
- 纳入 4.1 人工验收发现的房态右侧窗口可发现性与信息层级问题：避免“窗口”“订单列表”等入口和层级让工作人员误以为订单入口消失；区分分床父房汇总与具体床位订单，并让“查看完整订单”和当前合法动作容易找到。这里只登记并在 U2 编码前清单中确认，不在 4.1 改界面。
- 纳入订单详情的信息归位：住宿状态应在同一业务摘要中显示当前或最后住宿单元，不让工作人员在页面顶部与住宿分段之间寻找；`Amendments` 改为中文“变更历史”，入住、退房等生命周期变更应容易找到，同时隐藏内部类型码、版本号和对象 ID。
- “住宿分段”不得被表述成实际入住日志。底层 segment 是创建、改期、续住、缩短和换房形成的不可变住宿安排版本；所有 segment 顺序列表既可能重叠，也不能证明住客实际履约。
- 订单详情按四层呈现：`原始预订安排` 保留首次房源与日期；`当前住宿安排` 显示最新有效且不重叠的日期/房源时间线，终态订单改称“最后住宿安排”或“取消前安排”；`入住与退房结果` 显示未入住/在住/已退房/已取消/未到以及办理营业日、办理时间和操作人；`住宿安排变更历史` 逐条显示改期、续住、缩短、换房和提前退房的前后值、原因、操作人和时间。
- `INITIAL` 改为“初始预订安排”，不再翻译为“初始入住”；移除 `Segment ID`、Amendment ID、版本号、原始 payload 和内部库存 ID。未来换房必须区分“当前住宿位置”和“计划换至”，不能把最大 sequence 的 segment 直接叫作实际当前位置。
- U2 只增加权威只读投影和工作人员信息层级，不修改未来日期变更命令。CHECK_IN/CHECK_OUT 的办理营业日、记录时间和操作人若当前 DTO 不足，允许做 additive Query/OpenAPI 扩展；不得把 amendment 创建时间虚构成住客实际到店时间。
- 纳入会员与住宿订单的双向可发现性：会员住宿订单应提供关联会员档案入口，会员档案应提供关联住宿订单入口或历史列表；不得继续要求工作人员用订单昵称猜测会员主档姓名。该项只增加导航和既有事实呈现，不在 4.1 改会员权益规则。
- 未开始的续住、缩短、换房、取消、未到、资金和令牌业务页面只登记问题，不提前改变业务规则。

每个检查点独立进入 `in_progress -> awaiting_user_acceptance -> accepted`，不得把 U1、U2 和阶段 2/7 回归合并为一次大交付；U2 通过后才继续第 4 步正式检查点 4.2。
